MuJoCo 自带原生 Python 绑定，使用 `pybind11 <https://pybind11.readthedocs.io/>`__ 以 C++ 开发。Python API 与底层 C API 保持一致。
这会带来一些不够 Pythonic 的代码结构（例如函数参数的顺序），但好处是
:doc:`API 文档<APIreference/index>` 对两种语言都适用。

Python 绑定以 ``mujoco`` 包的形式发布在 `PyPI <https://pypi.org/project/mujoco>`__ 上。这些是底层绑定，目标是尽可能直接地访问
MuJoCo 库。不过，为了提供典型 Python 库中开发者所期望的 API 和语义，这些绑定在若干地方有意与原始的 MuJoCo API 有所不同，
本页各处都对这些差异做了说明。

并将继续由 Google DeepMind 提供支持。对于依赖 1.0.0 之前版本 dm_control 的代码，请参阅
`迁移指南 <https://github.com/google-deepmind/dm_control/blob/main/migration_guide_1.0.md>`__ 。

.. _PyInstallation:

安装
====

推荐通过 `PyPI <https://pypi.org/project/mujoco/>`__ 安装此包：

.. code-block:: shell

   pip install mujoco

软件包中已附带一份 MuJoCo 库， **无需** 单独下载或安装。

从 MuJoCo 4.0.0 开始，顶层的 ``mujoco`` 发行包是一个元包（metapackage），它会安装核心绑定（ ``mujoco-core`` ）、MuJoCo Studio 与 Filament
渲染（ ``mujoco-studio`` ），以及经典 OpenGL 渲染所需的依赖（ ``glfw`` 和 ``pyopengl`` ）。根据你的环境，也可以单独安装各个子包：

- ``pip install mujoco-core`` ：仅依赖 ``numpy`` 的最小化核心仿真绑定（适合无显示器的服务器和强化学习训练）。安装
  ``mujoco-core[rendering]`` 可附带 ``glfw`` 和 ``pyopengl`` ，用于经典 OpenGL 渲染以及不含 MuJoCo Studio 的
  ``mujoco.viewer`` 。
- ``pip install mujoco-studio`` ： `MuJoCo Studio <https://pypi.org/project/mujoco-studio/>`__ 交互式查看器与
  Filament 渲染器绑定（会自动安装 ``mujoco-core`` 和 ``mujoco-studio-wasm`` ）。
- ``pip install mujoco[usd]`` 或 ``pip install mujoco-usd`` ：OpenUSD 导入器、导出器和物理模式（physics schemas）；参见
  :ref:`USD 导出器 <PyUSDexport>` 和 :doc:`OpenUSD/index` 。

.. _PyViewer:

交互式查看器
============

Python 包的 ``mujoco.viewer`` 模块提供了一个交互式 GUI 查看器。它与 MuJoCo 二进制发行版附带的 :ref:`simulate<saSimulate>`
应用基于同一套代码。它支持三种不同的使用场景： :ref:`托管式查看器 <PyViewerManaged>` 、 :ref:`独立应用 <PyViewerApp>` 和
:ref:`被动式查看器 <PyViewerPassive>` 。

.. _PyViewerManaged:

托管式查看器
------------

``viewer.launch`` 函数会启动交互式查看器并*阻塞用户代码*，这有助于精确控制物理循环的时序。如果用户代码以
:ref:`引擎插件 <exPlugin>` 或 :ref:`物理回调 <glPhysics>` 的形式实现，并由 MuJoCo 在 :ref:`mj_step` 期间调用，则应使用此模式。

- ``viewer.launch()`` 启动一个空的可视化会话，可以通过拖放加载模型。
- ``viewer.launch(model)`` 为给定的 ``mjModel`` 启动可视化会话，可视化器在内部创建自己的 ``mjData`` 实例。
- ``viewer.launch(model, data)`` 与上一种方式相同，区别在于可视化器直接操作给定的 ``mjData`` 实例——退出时 ``data`` 对象
  将已被修改。

.. _PyViewerApp:

独立应用
--------

``mujoco.viewer`` Python 包使用 ``if __name__ == '__main__'`` 机制，使 :ref:`托管式查看器 <PyViewerManaged>`
可以作为独立应用直接从命令行调用：

- ``python -m mujoco.viewer`` 启动一个空的可视化会话，可以通过拖放加载模型。
- ``python -m mujoco.viewer --mjcf=/path/to/some/mjcf.xml`` 为指定的模型文件启动可视化会话。

.. _PyViewerPassive:

被动式查看器
------------

``viewer.launch_passive`` 函数以*非阻塞*的方式启动交互式查看器，允许用户代码继续执行。在此模式下，由用户脚本负责控制时序并推进物理状态，
并且除非用户显式同步传入的事件，否则鼠标拖拽扰动不会生效。

.. warning::
  在 MacOS 上， ``launch_passive`` 要求通过专门的 ``mjpython`` 启动器来执行用户脚本，这是为了绕过平台的一项限制：该限制要求主线程必须是负责
  渲染的线程。 ``mjpython`` 命令随 ``mujoco`` 包一同安装，可以直接替代常用的 ``python`` 命令，并支持同样的一组命令行标志和参数。
  例如，可以通过 ``mjpython my_script.py`` 执行脚本，通过 ``mjpython -m IPython`` 启动 IPython 终端。

``launch_passive`` 函数返回一个句柄，可用于与查看器交互。它具有以下属性：

- ``cam`` 、 ``opt`` 和 ``pert`` 属性：分别对应 :ref:`mjvCamera` 、 :ref:`mjvOption` 和 :ref:`mjvPerturb` 结构体。

- ``lock()`` ：以上下文管理器的形式提供查看器的互斥锁。由于查看器在自己的线程中运行，用户代码在修改任何物理或可视化状态之前，必须确保已持有
  查看器锁。这些状态包括传给 ``launch_passive`` 的 ``mjModel`` 和 ``mjData`` 实例，以及查看器句柄的 ``cam`` 、
  ``opt`` 和 ``pert`` 属性。

- ``sync(state_only=False)`` ：在用户的 ``mjModel`` 、 ``mjData`` 与 GUI 之间同步。为了让用户脚本无需持有查看器锁就能对 ``mjModel`` 和
  ``mjData`` 做任意修改，被动式查看器不会在 ``sync`` 调用之外访问或修改这些结构体。如果 ``state_only`` 参数为 ``True`` ，则不会同步全部内容，
  而只同步与 :ref:`mjSTATE_INTEGRATION<mjtState>` 对应的 ``mjData`` 字段，随后调用 :ref:`mj_forward` 。后一种选项要快得多，但不会像默认情况那样
  捕获任意修改。通过 GUI 所做的更改在两种情况下都会被捕获，但例如通过代码修改 ``mjModel.geom_rgba`` 时，
  在 ``state_only=False`` 时会被捕获，在 ``state_only=True`` 时则不会。

  用户脚本必须调用 ``sync`` ，查看器才能反映物理状态的变化。 ``sync`` 函数还会把用户在 GUI 中的输入传回 ``mjOption`` （位于 ``mjModel`` 内）和
  ``mjData`` ，包括启用/禁用标志、控制输入和鼠标扰动。

- ``update_hfield(hfieldid)`` ：更新指定 ``hfieldid`` 处的高度场数据，供后续渲染使用。

- ``update_mesh(meshid)`` ：更新指定 ``meshid`` 处的网格数据，供后续渲染使用。

- ``update_texture(texid)`` ：更新指定 ``texid`` 处的纹理数据，供后续渲染使用。

- ``close()`` ：以编程方式关闭查看器窗口。该方法无需加锁即可安全调用。

- ``is_running()`` ：如果查看器窗口正在运行则返回 ``True`` ，已关闭则返回 ``False`` 。
  该方法无需加锁即可安全调用。

- ``user_scn`` ：一个 :ref:`mjvScene` 对象，允许用户修改渲染标志，并向渲染场景中添加自定义的可视化 geom。它与查看器内部用于渲染最终场景的
  ``mjvScene`` 相互独立，完全由用户控制。用户脚本可以调用例如 :ref:`mjv_initGeom` 或
  :ref:`mjv_connector` 向 ``user_scn`` 添加可视化 geom，在下一次调用 ``sync()`` 时，查看器会把这些 geom 纳入后续渲染的图像。类似地，用户脚本可以修改
  ``user_scn.flags`` ，这些修改会在下一次调用 ``sync()`` 时生效。 ``sync()`` 调用还会把通过 GUI 对渲染标志所做的更改复制回 ``user_scn`` ，以保持一致。例如：

  .. code-block:: python

    with mujoco.viewer.launch_passive(m, d, key_callback=key_callback) as viewer:

      # Enable wireframe rendering of the entire scene.
      viewer.user_scn.flags[mujoco.mjtRndFlag.mjRND_WIREFRAME] = 1
      viewer.sync()

      while viewer.is_running():
        ...
        # Step the physics.
        mujoco.mj_step(m, d)

        # Add a 3x3x3 grid of variously colored spheres to the middle of the scene.
        viewer.user_scn.ngeom = 0
        i = 0
        for x, y, z in itertools.product(*((range(-1, 2),) * 3)):
          mujoco.mjv_initGeom(
              viewer.user_scn.geoms[i],
              type=mujoco.mjtGeom.mjGEOM_SPHERE,
              size=[0.02, 0, 0],
              pos=0.1*np.array([x, y, z]),
              mat=np.eye(3).flatten(),
              rgba=0.5*np.array([x + 1, y + 1, z + 1, 2])
          )
          i += 1
        viewer.user_scn.ngeom = i
        viewer.sync()
        ...

查看器句柄也可以用作上下文管理器，退出时会自动调用 ``close()`` 。下面是一个使用 ``launch_passive`` 的用户脚本的最小示例。（请注意，这只是一个简单的说明性示例，
它 **不一定** 能让物理仿真以正确的墙钟速率运行。）

.. code-block:: python

  import time

  import mujoco
  import mujoco.viewer

  m = mujoco.MjModel.from_xml_path('/path/to/mjcf.xml')
  d = mujoco.MjData(m)

  with mujoco.viewer.launch_passive(m, d) as viewer:
    # Close the viewer automatically after 30 wall-seconds.
    start = time.time()
    while viewer.is_running() and time.time() - start < 30:
      step_start = time.time()

      # mj_step can be replaced with code that also evaluates
      # a policy and applies a control signal before stepping the physics.
      mujoco.mj_step(m, d)

      # Example modification of a viewer option: toggle contact points every two seconds.
      with viewer.lock():
        viewer.opt.flags[mujoco.mjtVisFlag.mjVIS_CONTACTPOINT] = int(d.time % 2)

      # Pick up changes to the physics state, apply perturbations, update options from GUI.
      viewer.sync()

      # Rudimentary time keeping, will drift relative to wall clock.
      time_until_next_step = m.opt.timestep - (time.time() - step_start)
      if time_until_next_step > 0:
        time.sleep(time_until_next_step)

``viewer.launch_passive`` 还可以接受以下可选的关键字参数。

- ``key_callback`` ：一个可调用对象，每当查看器窗口中发生键盘事件时被调用。这使用户脚本能够响应各种按键，例如按下空格键时暂停或恢复运行循环。

  .. code-block:: python

    paused = False

    def key_callback(keycode):
      if chr(keycode) == ' ':
        nonlocal paused
        paused = not paused

    ...

    with mujoco.viewer.launch_passive(m, d, key_callback=key_callback) as viewer:
      while viewer.is_running():
        ...
        if not paused:
          mujoco.mj_step(m, d)
          viewer.sync()
        ...

- ``show_left_ui`` 和 ``show_right_ui`` ：布尔参数，指示查看器启动时 UI 面板应显示还是隐藏。请注意，无论取何值，用户在启动后仍然可以通过按 Tab 或 Shift+Tab
  切换这些面板的可见性。

.. _PyUsage:

基本用法
========

安装完成后，可以通过 ``import mujoco`` 导入该包。结构体、函数、常量和枚举都可以直接从顶层的 ``mujoco`` 模块获取。

.. _PyStructs:

结构体
------

这些绑定包含了暴露 MuJoCo 数据结构的 Python 类。为获得最高性能，这些类直接访问 MuJoCo 使用的原始内存，不做复制或缓冲。
这意味着某些 MuJoCo 函数（例如 :ref:`mj_step` ）会*就地*修改字段的内容。因此建议用户在需要时自行创建副本。
例如，在记录某个刚体（body）的位置时，可以写成
``positions.append(data.body('my_body').xpos.copy())`` 的形式。若省略 ``.copy()`` 这一调用，列表中将包含完全相同的元素，它们全都指向最新的值。
NumPy 切片也是如此。例如，如果创建了局部变量 ``qpos_slice = data.qpos[3:8]`` ，然后调用 :ref:`mj_step` ，那么 ``qpos_slice``
中的值就会被改变。

为了符合 `PEP 8 <https://peps.python.org/pep-0008/>`__ 的命名规范，结构体名称以大写字母开头，例如 ``mjData`` 在 Python 中变为 ``mujoco.MjData`` 。

除 ``mjModel`` 之外，所有结构体在 Python 中都有构造函数。对于带有 ``mj_defaultFoo`` 风格初始化函数的结构体，Python 构造函数会自动调用该默认初始化函数，
因此例如 ``mujoco.MjOption()`` 会创建一个新的 ``mjOption`` 实例，并已用 :ref:`mj_defaultOption` 预先初始化。
否则，Python 构造函数会将底层 C 结构体零初始化。

带有 ``mj_makeFoo`` 风格初始化函数的结构体，在 Python 中有相应的构造函数重载，
例如 Python 中的 ``mujoco.MjvScene(model, maxgeom=10)`` 会创建一个新的 ``mjvScene`` 实例，其初始化方式等同于 C 中的
``mjv_makeScene(model, [the new mjvScene instance], 10)`` 。使用这种形式初始化时，Python 对象被删除时会自动调用相应的释放函数 ``mj_freeFoo/mj_deleteFoo`` ，
用户无需手动释放资源。

``mujoco.MjModel`` 类没有 Python 构造函数。取而代之的是，我们提供三个静态工厂函数来创建新的 :ref:`mjModel` 实例：
``mujoco.MjModel.from_xml_string`` 、 ``mujoco.MjModel.from_xml_path`` 和 ``mujoco.MjModel.from_binary_path`` 。第一个函数接受字符串形式的模型 XML，
后两个函数接受 XML 或 MJB 模型文件的路径。这三个函数都可以选择性地接受一个 Python 字典，该字典会被转换为 MuJoCo
:ref:`虚拟文件系统 <Virtualfilesystem>` ，供模型编译期间使用。

对结构体属性赋值会写入底层的 C 内存，而不是重新绑定该属性。对于数组字段， ``model.opt.gravity = value`` 等价于 ``model.opt.gravity[:] = value`` 。
同样， ``MjModel`` 的子结构体属性（ ``opt`` 、 ``vis`` 、 ``stat`` ）以及 ``MjVisual`` 的子结构体属性（ ``global_`` 、 ``quality`` 、 ``headlight`` 、
``map`` 、 ``scale`` 、 ``rgba`` ）也可以被赋值，例如 ``model.opt = new_opt`` 会把 ``new_opt`` 的各字段就地复制到模型自身的 ``mjOption`` 结构体中。
指向目标结构体的任何现有引用和 NumPy 数组视图仍然有效，并会反映新值；之后对 ``new_opt`` 的修改不会传播过去。



.. _PyFunctions:

函数
----

MuJoCo 函数以同名的 Python 函数形式暴露。与结构体不同，我们不尝试让函数名符合 `PEP 8 <https://peps.python.org/pep-0008/>`__ 规范，因为 MuJoCo
同时使用下划线和驼峰命名。在大多数情况下，函数参数与 C 中完全一致，并且支持与 :ref:`mujoco.h<inHeader>` 中声明的名称相同的关键字参数。
接受数组输入参数的 C 函数，其 Python 绑定要求传入 NumPy 数组，或可转换为 NumPy 数组的可迭代对象（例如列表）。输出参数
（即 MuJoCo 期望向调用方写回数值的数组参数）必须始终是可写的 NumPy 数组。

在 C API 中，接受动态大小数组作为输入的函数需要一个指向该数组的指针参数，以及一个指定数组大小的整数参数。在 Python 中，大小参数被省略，因为我们可以
从 NumPy 数组自动（而且确实更安全地）推断出大小。调用这些函数时，除数组大小外的所有参数都应按它们在 :ref:`mujoco.h<inHeader>` 中出现的顺序传入，
或者使用关键字参数。例如， :ref:`mj_jac` 在 Python 中应这样调用： ``mujoco.mj_jac(m, d, jacp, jacr, point, body)`` 。

这些绑定会在调用底层 MuJoCo 函数之前 **释放 Python 全局解释器锁（GIL）** 。这使得某种程度的基于线程的并行成为可能，但用户应当注意，GIL 仅在
MuJoCo C 函数本身执行期间被释放，在执行任何其他 Python 代码期间不会释放。

.. note::
   绑定确实提供额外功能的一个地方是顶层的 :ref:`mj_step` 函数。由于它经常在循环中被调用，我们增加了一个额外的 ``nstep`` 参数，指示底层的
   :ref:`mj_step` 应被调用多少次。如果未指定， ``nstep`` 取默认值 1。下面两段代码执行相同的计算，但第一段在相邻的物理步之间不会获取 GIL：

   .. code-block:: python

      mj_step(model, data, nstep=20)

   .. code-block:: python

      for _ in range(20):
        mj_step(model, data)

.. _PyEnums:

枚举与常量
----------

MuJoCo 枚举以 ``mujoco.mjtEnumType.ENUM_VALUE`` 的形式提供，例如 ``mujoco.mjtObj.mjOBJ_SITE`` 。MuJoCo
常量以相同的名称直接位于 ``mujoco`` 模块之下，例如 ``mujoco.mjVISSTRING`` 。

.. _PyExample:

最小示例
--------

.. code-block:: python

   import mujoco

   XML=r"""
   <mujoco>
     <asset>
       <mesh file="gizmo.stl"/>
     </asset>
     <worldbody>
       <body>
         <freejoint/>
         <geom type="mesh" name="gizmo" mesh="gizmo"/>
       </body>
     </worldbody>
   </mujoco>
   """

   ASSETS=dict()
   with open('/path/to/gizmo.stl', 'rb') as f:
     ASSETS['gizmo.stl'] = f.read()

   model = mujoco.MjModel.from_xml_string(XML, ASSETS)
   data = mujoco.MjData(model)
   while data.time < 1:
     mujoco.mj_step(model, data)
     print(data.geom_xpos)

.. _PyNamed:

具名访问
--------

大多数设计良好的 MuJoCo 模型都会为感兴趣的对象（关节、geom、刚体等）命名。当模型被编译为 ``mjModel`` 实例时，这些名称会与数字 ID 关联起来，
这些 ID 用于索引各种数组成员。为了方便并提高代码可读性，Python 绑定在 ``MjModel`` 和 ``MjData`` 上提供了“具名访问”API。
``mjModel`` 结构体中的每个 ``name_fooadr`` 字段定义了一个名称类别 ``foo`` 。

对于每个名称类别 ``foo`` ， ``mujoco.MjModel`` 和 ``mujoco.MjData`` 对象都提供一个名为 ``foo`` 的方法，它接受一个字符串参数，并返回一个访问器对象，
该对象涵盖与给定名称的 ``foo`` 实体相对应的所有数组。访问器对象包含的属性，其名称对应于 ``mujoco.MjModel`` 或
``mujoco.MjData`` 的字段名去掉下划线之前的部分。此外，访问器对象还提供 ``id`` 和 ``name`` 属性，可分别用来替代 ``mj_name2id`` 和 ``mj_id2name`` 。例如：

- ``m.geom('gizmo')`` 返回 ``MjModel`` 对象 ``m`` 中与名为 "gizmo" 的 geom 相关联的数组的访问器。
- ``m.geom('gizmo').rgba`` 是长度为 4 的 NumPy 数组视图，指定该 geom 的 RGBA 颜色。
  具体而言，它对应于 ``m.geom_rgba[4*i:4*i+4]`` 这一部分，其中
  ``i = mujoco.mj_name2id(m, mujoco.mjtObj.mjOBJ_GEOM, 'gizmo')`` 。
- ``m.geom('gizmo').id`` 与 ``mujoco.mj_name2id(m, mujoco.mjtObj.mjOBJ_GEOM, 'gizmo')`` 返回的数字相同。
- ``m.geom(i).name`` 是 ``'gizmo'`` ，其中 ``i = mujoco.mj_name2id(m, mujoco.mjtObj.mjOBJ_GEOM, 'gizmo')`` 。

此外，Python API 还为部分名称类别定义了若干别名，这些别名对应于 MJCF 模式中定义该类别实体的 XML 元素名。例如， ``m.joint('foo')`` 与
``m.jnt('foo')`` 相同。下面给出这些别名的完整列表。

关节（joint）的访问器与其他类别的略有不同。某些 ``mjModel`` 和 ``mjData`` 字段（大小为 ``nq`` 或 ``nv`` 的那些）与自由度（DoF）而非关节相关联。
这是因为不同类型的关节具有不同数量的自由度。尽管如此，我们仍把这些字段与对应的关节关联起来，例如通过 ``d.joint('foo').qpos`` 和 ``d.joint('foo').qvel`` ，
不过这些数组的大小会因关节类型的不同而在不同访问器之间有所差异。

具名访问保证相对于模型中实体的数量为 O(1)。换言之，按名称访问某个实体所需的时间不会随模型中名称或实体数量的增加而增长。

- ``body``
- ``jnt`` 或 ``joint``
- ``geom``
- ``site``
- ``cam`` 或 ``camera``
- ``light``
- ``mesh``
- ``skin``
- ``hfield``
- ``tex`` 或 ``texture``
- ``mat`` 或 ``material``
- ``pair``
- ``exclude``
- ``eq`` 或 ``equality``
- ``tendon`` 或 ``ten``
- ``actuator``

.. _PyRender:

渲染
----

MuJoCo 提供两套渲染 API： :ref:`经典渲染 <OpenGLrendering>` API（使用 OpenGL 1.5）和
:ref:`Filament 渲染 <FilamentRendering>` API（提供更现代的基于物理的渲染能力）。

.. _PyFilamentRender:

Filament 渲染
-------------

Python 的 ``mjrf`` 模块把 ``mjrf_`` :ref:`C API <FilamentRenderingApi>` 暴露给 Python。可以通过
``from mujoco import mjrf`` 导入。该模块还围绕 C 库提供了以下便利功能：

- 枚举被直接暴露，但去掉了 ``mjr`` 前缀。例如， :ref:`mjrGraphicsApi` 变为
  ``mjrf.GraphicsApi`` ， ``mjGRAPHICS_API_DEFAULT`` 变为 ``mjrf.GraphicsApi.GRAPHICS_API_DEFAULT`` 。

- 元组/列表/NumPy 数组类型会被自动转换为相应的 C 原生类型（例如 ``float*`` ）。

- ``mjrf`` C 结构体按两种不同方式处理。基本结构体（例如 :ref:`mjrRect` 、 ``mjrCamera`` 等）被视为简单的 POD 数据类型，
  并直接绑定为 Python 类型，允许按需进行复制。

- 在 C API 中具有显式创建/销毁函数的 ``mjrf`` 类型（例如 :ref:`mjrfContext` 、 :ref:`mjrfTexture` 等）被视为“对象”（Objects）。
  在 Python 中创建它们时，其生命周期由 Python 管理；对这些对象调用 ``del`` 会销毁底层的 C 对象。但是，当它们作为 API 调用的返回值时，
  是以引用的形式返回的，Python 不会管理它们的生命周期。

- 如果 ``mjrf_`` C 函数的第一个参数是指向某个对象的指针，我们就把该函数绑定为该对象自身的方法。例如， :ref:`mjrf_setLightActive(mjrfLight*, bool)<mjrf_setLightActive>`
  变为 ``Light.set_active(bool)`` 。

- 某些函数（例如 ``mjrf.ReadRequest.set_buffer`` ）要求用户提供缓冲区。用户有责任确保缓冲区的生命周期长于与之关联的请求。

我们还在 ``mujoco.rendering.filament`` 下提供了一个 `ModelScene
<https://github.com/google-deepmind/mujoco/blob/main/python/mujoco/rendering/filament/model_scene.py>`__ 辅助类。
该类可根据 :ref:`mjModel` 和 :ref:`mjData` 的内容，在 :ref:`mjrfScene` 中添加并更新 :ref:`mjrfRenderable` 和 :ref:`mjrfLight`
对象。

类似地，我们也在 ``mujoco.rendering.filament`` 下提供了一个 `Renderer
<https://github.com/google-deepmind/mujoco/blob/main/python/mujoco/rendering/filament/renderer.py>`__ 类。该类可用于管理关键对象
（例如 :ref:`mjrfContext` 和 :ref:`mjrfScene` ）的生命周期，并提供了用于控制相机和读取像素的实用函数。

下面是使用 Filament 渲染器渲染 mjModel 的最小示例：

.. code-block:: python

   import mujoco
   from mujoco import mjrf
   from mujoco.rendering.filament import model_scene
   from mujoco.rendering.filament import renderer
   import numpy as np

   def render(model: mujoco.MjModel, data: MjData, width: int, height: int) -> np.ndarray:
     # create the rendering context
     ctx = mjrf.Context(mjrf.ContextConfig())

     # create a renderer
     r = renderer.Renderer(ctx)

     # add lights and renderables defined in the model to a scene in the renderer
     ms = model_scene.ModelScene(ctx, model, r.scene("scn"))

     # create the pixel buffer into which we'll render the image
     pixels = np.empty((height, width, 3), dtype=np.uint8)

     # associate the pixel buffer with a render target
     r.target("out", pixels)

     # update the lights and renderables with the current `data` state
     ms.update(data)

     # define the camera for the view we want to render
     vcam = mujoco.MjvCamera()
     mujoco.mjv_defaultFreeCamera(model, vcam)
     vcam.type = int(mujoco.mjtCamera.mjCAMERA_FIXED)
     vcam.fixedcamid = 0
     # define a view that connects the scene we want to render to an output target
     view = renderer.View(
         scene="scn",
         target="out",
         camera=mujoco.mjv_camera2GLCamera(model, data, vcam),
     )

     # render the scene; blocks until the render has completed writing to the render target
     r.render([view])

     # return the pixels
     return pixels

.. _PyClassicRender:

经典渲染
--------

MuJoCo 经典渲染器要求用户在调用任何 ``mjr_`` :ref:`渲染例程 <OpenGLrendering>` 之前，先设置好可用的 OpenGL 上下文。Python 绑定提供了一个基础类
``mujoco.GLContext`` ，帮助用户为离屏渲染设置这样的上下文。要创建上下文，请调用 ``ctx = mujoco.GLContext(max_width,
max_height)``。上下文创建后，必须先将其设为当前上下文，才能调用 MuJoCo 渲染函数，可以通过
``ctx.make_current()`` 完成。请注意，在任意给定时刻，一个上下文只能在一个线程上被设为当前上下文，并且之后所有的
渲染调用都必须在同一个线程上进行。

当 ``ctx`` 对象被删除时，上下文会被自动释放，但在某些多线程场景下，可能需要显式释放底层的 OpenGL 上下文。为此，请调用 ``ctx.free()`` ，
此后用户有责任确保不再对该上下文发起渲染调用。

上下文创建后，用户可以按照 MuJoCo 的标准渲染流程进行，例如 :ref:`可视化 <Visualization>` 一节中所述的方式。

.. _PyError:

错误处理
--------

MuJoCo 通过 :ref:`mju_error` 机制报告不可恢复的错误，该机制会立即终止整个进程。用户可以通过 :ref:`mju_user_error` 回调安装自定义的错误处理程序，但它同样应当
终止进程，否则回调返回后 MuJoCo 的行为是未定义的。实际上，只需确保错误回调不会返回*到 MuJoCo*，但允许使用
`longjmp <https://en.cppreference.com/w/c/program/longjmp>`__ 跳过 MuJoCo 的调用栈，回到外部的调用点。

Python 绑定利用 longjmp，把不可恢复的 MuJoCo 错误转换为 ``mujoco.FatalError`` 类型的 Python 异常，可以用通常的 Pythonic 方式捕获和处理。
此外，它还通过目前尚未公开的 API，以线程局部的方式安装其错误回调，从而允许多个线程并发调用 MuJoCo。

.. _PyCallbacks:

回调
----

MuJoCo 允许用户安装自定义回调函数，以修改其计算流程的某些部分。
例如， :ref:`mjcb_sensor` 可用于实现自定义传感器（sensor）， :ref:`mjcb_control` 可用于
实现自定义执行器（actuator）。回调通过 :ref:`mujoco.h<inHeader>` 中以 ``mjcb_`` 为前缀的函数指针暴露出来。

对于每个回调 ``mjcb_foo`` ，用户可以通过 ``mujoco.set_mjcb_foo(some_callable)`` 将其设置为一个 Python 可调用对象。要
重置它，请调用 ``mujoco.set_mjcb_foo(None)`` 。要获取当前安装的回调，请调用
``mujoco.get_mjcb_foo()`` 。（如果回调不是通过 Python 绑定安装的，则 **不应** 使用这个 getter。）
每次进入回调时，绑定会自动获取 GIL，并在重新进入 MuJoCo 之前将其释放。由于回调在 MuJoCo 的计算流程中会被多次触发，这很可能带来严重的性能影响，
也不太适合“生产”场景。不过，预计这一功能对复杂模型的原型开发会很有用。

另外，如果回调是用原生动态库实现的，用户可以使用
`ctypes <https://docs.python.org/3/library/ctypes.html>`__ 获取指向该 C 函数指针的 Python 句柄，并将其传给 ``mujoco.set_mjcb_foo`` 。
这时绑定会取出底层的函数指针并直接赋给原始的回调指针，每次进入回调时 **不会** 再获取 GIL。

构造
----

``MjSpec`` 对象封装了 :ref:`mjSpec` 结构体，可以通过三种方式构造：

1. 创建一个空的 spec： ``spec = mujoco.MjSpec()``
2. 从 XML 字符串加载 spec： ``spec = mujoco.MjSpec.from_string(xml_string)``
3. 从 XML 文件加载 spec： ``spec = mujoco.MjSpec.from_file(file_path)``

请注意， ``from_string()`` 和 ``from_file()`` 方法只能在构造时调用。

.. _PyVFS:

资源
^^^^

MuJoCo 可以选择使用 :ref:`虚拟文件系统 <Virtualfilesystem>` （VFS）从内存中加载资源（如网格和纹理）。

Python 绑定提供了 ``mujoco.MjVfs`` ，作为 :ref:`mjVFS` C 结构体的封装。

``MjVfs`` 支持上下文管理器协议，可确保离开代码块时正确释放资源：

.. code-block:: python

   with mujoco.MjVfs() as vfs:
       vfs["model.xml"] = b"<mujoco/>"
       spec = mujoco.MjSpec.from_string("model.xml", vfs=vfs)
       spec.compile(vfs=vfs)

你也可以直接创建实例，并在使用完毕后调用 ``close()`` ：

.. code-block:: python

   vfs = mujoco.MjVfs()
   vfs["model.xml"] = some_xml_string.encode("utf-8")
   spec = mujoco.MjSpec.from_file("model.xml", vfs=vfs)
   spec.compile(vfs=vfs)
   vfs.close()

``MjVfs`` 对象支持类似字典的操作来管理缓冲区：

- ``vfs["name"] = data`` ：向 VFS 添加一个缓冲区。 ``data`` 必须是 ``bytes`` 类型。
- ``del vfs["name"]`` ：从 VFS 中删除一个文件。
- ``"name" in vfs`` ：检查某个文件是否存在于 VFS 中。

静态工厂函数 ``mujoco.MjModel.from_xml_string`` 、 ``mujoco.MjModel.from_xml_path`` 、
``mujoco.MjSpec.from_string`` 和 ``mujoco.MjSpec.from_file`` 都接受可选的 ``vfs`` 参数。此外，
``spec.compile()`` 函数也接受可选的 ``vfs`` 参数。

.. warning::
   以前通过将资源名映射到字节的字典来传递资源的方式已 **弃用** ，并将在下一个版本中移除。不能同时指定 ``assets`` 字典和 ``vfs`` 参数。
   应使用 ``MjVfs`` 作为直接替代。

作为参考，已弃用的 ``assets`` 字典方式如下所示：

.. code-block:: python

  assets = {'image.png': b'image_data'}
  spec = mujoco.MjSpec.from_string(xml_referencing_image_png, assets=assets)
  model = spec.compile()

  # Or

  spec = mujoco.MjSpec.from_string(xml_referencing_image_png)
  spec.assets = {'image.png': b'image_data'}
  model = spec.compile()

保存为 XML
----------

``MjSpec`` 对象可以通过 ``to_xml()`` 方法保存为 XML 字符串。默认情况下保存的是编译过程对模型所得出的值；将 ``spec.compiler.savecompiled = False``
设置后，则按 spec 中所写的原样保存模型，参见 :ref:`模型编码与保存 <meSaving>` 。与 :ref:`mj_saveXMLString` 不同，
``to_xml()`` 在保存之前会先编译 spec：spec 必须能连同其资源一起成功编译，并且编译会像 :ref:`mj_compile` 所述的那样修改 spec，例如应用
:ref:`fusestatic<compiler-fusestatic>` 。

.. code-block:: python

   print(spec.to_xml())

.. code-block:: XML

   <mujoco model="my model">
     <compiler angle="radian"/>

     <worldbody>
       <body pos="1 2 3" quat="0 1 0 0">
         <geom name="my_geom" size="1" rgba="1 0 0 1"/>
       </body>
     </worldbody>
   </mujoco>

此外，也可以使用 ``encode()`` 将 spec 或已编译的模型序列化到文件：

.. code-block:: python

   # Save spec directly to an MJCF XML file
   spec.encode('model.xml')

   # Save XML from a compiled model; copies modified model values back to spec prior to saving
   spec.encode('model.xml', model=model)

   # Save compiled model to binary MJB format (serializes mjModel only, not spec)
   spec.encode('model.mjb', model=model)

   # Package spec and all referenced external assets (meshes, textures) into an MJZ zip archive
   spec.encode('robot.mjz', model=model)

``encode()`` 方法接受目标文件名、可选的已编译 ``model`` （ :ref:`MjModel` ）、可选的
``vfs`` （ :ref:`MjVFS` ）以及可选的 ``content_type`` 。目标格式会根据文件扩展名（ ``.xml`` 、 ``.mjb`` 、 ``.txt`` 、 ``.mjz`` ）或内容类型自动确定。

在已编译模型中被修改过的值，可以通过 ``copy_back()`` 写回 spec 本身。此后，这些值会出现在随后由该 spec 编译出的模型中，也会出现在它保存的内容里；
具体复制了什么以及如何复制，参见 :ref:`mj_copyBack` ：

.. code-block:: python

   model = spec.compile()
   model.geom('my_geom').size[0] = 2
   spec.copy_back(model)
   print(spec.geom('my_geom').size[0])  # 2.0

附加
----

可以通过附加（attachment）将多个 spec 组合在一起。支持以下几种方式：

-   将子 spec 中的刚体（body）附加到父 spec 中的坐标系（frame）： ``body.attach_body(body, prefix, suffix)`` ，返回
    所附加刚体的引用，该引用应与作为输入的刚体相同。
-   将子 spec 中的坐标系附加到父 spec 中的刚体： ``body.attach_frame(frame, prefix, suffix)`` ，
    返回所附加坐标系的引用，该引用应与作为输入的坐标系相同。
-   将子 spec 附加到父 spec 中的 site： ``parent_spec.attach(child_spec, site=site_name_or_obj)`` ，返回
    一个坐标系的引用，它是被变换为坐标系的、已附加的世界刚体（worldbody）。该 site 必须属于
    子 spec。前缀和后缀也可以作为关键字参数指定。
-   将子 spec 附加到父 spec 中的坐标系： ``parent_spec.attach(child_spec, frame=frame_name_or_obj)`` ，
    返回一个坐标系的引用，它是被变换为坐标系的、已附加的世界刚体。该坐标系必须
    属于子 spec。前缀和后缀也可以作为关键字参数指定。

附加的默认行为是不进行复制，因此所有子级的引用（世界刚体除外）在父级中仍然有效，因而修改子级也会修改父级。MJCF 中的
:ref:`attach<body-attach>` 和 :ref:`replicate<replicate>` 元元素（meta-element）并非如此，它们在附加时会创建深拷贝。不过，可以通过将
``spec.copy_during_attach`` 设置为 ``True`` 来覆盖默认行为。此时，子 spec 会被复制，对子级的引用将不再指向父级。
在不复制的情况下，一个子 spec 只能整体附加一次，因为它的元素会移动到父级；其中尚未被附加的刚体和坐标系仍可以被附加，前提是它们不包含任何已被附加的内容。
父级的元素（包括附加到它上面的元素）只能以副本的形式附加到父级。

.. code-block:: python

   import mujoco

   # Create the parent spec.
   parent = mujoco.MjSpec()
   body = parent.worldbody.add_body()
   frame = parent.worldbody.add_frame()
   site = parent.worldbody.add_site()

   # Create the child specs.
   child = mujoco.MjSpec()
   child_body = child.worldbody.add_body()
   child_frame = child.worldbody.add_frame()
   child2 = mujoco.MjSpec()
   child3 = mujoco.MjSpec()

   # Attach the children to the parent in different ways.
   body_in_frame = frame.attach_body(child_body, 'child-', '')
   frame_in_body = body.attach_frame(child_frame, 'child-', '')
   worldframe_in_site = parent.attach(child2, site=site, prefix='child2-')
   worldframe_in_frame = parent.attach(child3, frame=frame, prefix='child3-')

.. _PyEditConvenience:

便捷方法
--------

Python 绑定提供了一些 C API 中没有直接提供的便捷方法和属性，使模型编辑更加容易：

具名访问
^^^^^^^^
``MjSpec`` 对象具有 ``.body(), .joint(), .site(), ...`` 等方法，用于按名称访问元素。
``spec.geom('my_geom')`` 将返回名为 "my_geom" 的 :ref:`mjsGeom` ，如果不存在则返回 ``None`` 。

元素列表
^^^^^^^^
可以使用复数形式的具名属性访问 spec 中所有元素的列表。例如，
``spec.meshes`` 返回 spec 中所有网格的列表。已实现的属性有： ``sites`` 、
``geoms`` 、 ``joints`` 、 ``lights`` 、 ``cameras`` 、 ``bodies`` 、 ``frames`` 、 ``materials`` 、 ``meshes`` 、 ``pairs`` 、
``equalities`` 、 ``tendons`` 、 ``actuators`` 、 ``skins`` 、 ``textures`` 、 ``texts`` 、 ``tuples`` 、 ``flexes`` 、 ``hfields`` 、
``keys`` 、 ``numerics`` 、 ``excludes`` 、 ``sensors`` 、 ``plugins`` 。

元素删除
^^^^^^^^
``delete()`` 方法会从 spec 中移除对应的元素，例如 ``spec.delete(spec.geom('my_geom'))`` 将
移除名为 "my_geom" 的 geom，以及所有引用它的元素。对于可以拥有子级的元素（刚体、
坐标系和默认类）， ``delete`` 还会移除它们的所有子级。删除刚体或坐标系时，所有引用被删除子级的元素也会被一并移除。

树遍历
^^^^^^
以下方法有助于遍历运动学树，它们返回与树相关的元素列表：

直接子级：
  与上面介绍的 spec 级元素列表类似，刚体也具有返回其所有直接子级列表的属性。
  例如， ``body.geoms`` 返回作为该刚体直接子级的所有 geom 的列表。这适用于所有
  树内元素，即 ``bodies`` 、 ``joints`` 、 ``geoms`` 、 ``sites`` 、 ``cameras`` 、 ``lights`` 和 ``frames`` 。

递归搜索：
  ``body.find_all()`` 返回给定刚体子树中所有指定类型元素的列表。
  元素类型可以用 :ref:`mjtObj` 枚举指定，也可以用对应的字符串指定。例如，
  ``body.find_all(mujoco.mjtObj.mjOBJ_SITE)`` 或 ``body.find_all('site')`` 都会返回该刚体之下所有 site 的列表。

父级：
  给定元素（包括刚体和坐标系）的父刚体可以通过 ``parent`` 属性访问。
  例如，site 的父级可以通过 ``site.parent`` 访问。

序列化
^^^^^^
``MjSpec`` 对象可以使用 ``spec.to_zip(file)`` 函数连同其所有资源一起序列化，其中 ``file``
可以是文件路径，也可以是文件对象。要从 zip 文件加载 spec，请使用 ``spec =
MjSpec.from_zip(file)\ ``，其中 ``\ file`` 是 zip 文件的路径或 zip 文件对象。

网格创建
^^^^^^^^
:ref:`mjsMesh` 对象包含便捷方法，可用具名属性创建模型，对应于
:ref:`mesh/builtin<asset-mesh-builtin>` 的语义。参见 `specs_test.py
<https://github.com/google-deepmind/mujoco/blob/main/python/mujoco/specs_test.py>`__。

.. code-block:: python

   mesh = spec.add_mesh(name='prism')
   mesh.make_cone(nedge=5, radius=1)

纹理编辑
^^^^^^^^
:ref:`mjsTexture` 的缓冲区选项将纹理字节存储在 ``data`` 属性中。该属性可以被读取和
修改，例如：

.. code-block:: python

  texture = spec.add_texture(name='texture', height=1, width=3, nchannel=3)
  texture.data = bytes([255, 0, 0, 0, 255, 0, 0, 0, 255])  # Assign red, green and blue pixels.
  texture.data[1] = 255  # Change the first pixel to yellow.

.. _PyMJCF:

与 ``PyMJCF`` 和 ``bind`` 的关系
--------------------------------

`dm_control <https://github.com/google-deepmind/dm_control/tree/main>`__ 的
`PyMJCF <https://github.com/google-deepmind/dm_control/blob/main/dm_control/mjcf/README.md>`__ 模块提供了与此处所述原生模型编辑 API 类似的
功能，但由于依赖 Python 对字符串的操作，速度大约要慢两个数量级。

对于熟悉 ``PyMJCF`` 的用户， ``MjSpec`` 对象在概念上类似于 ``dm_control`` 的
``mjcf_model`` 。以后可能会在此处补充更详细的迁移指南；在此之前，请注意“模型编辑”
`colab 笔记本 <https://colab.research.google.com/github/google-deepmind/mujoco/blob/main/python/mjspec.ipynb>`__
中包含了对 ``dm_control``
`教程笔记本 <https://github.com/google-deepmind/dm_control/blob/main/tutorial.ipynb>`__ 中 ``PyMJCF`` 示例的重新实现。

``PyMJCF`` 提供了“绑定”（binding）的概念，可以通过辅助类访问 :ref:`mjModel` 和 :ref:`mjData` 的值。
在原生 API 中不需要这个辅助类，因此可以直接将 ``mjs`` 对象绑定到
:ref:`mjModel` 和 :ref:`mjData` 。例如，假设有多个名称中包含字符串 "torso" 的 geom，
我们想从 ``mjData`` 中获取它们在 XY 平面内的笛卡尔位置。可以这样做：

.. code-block:: python

   torsos = [data.bind(geom) for geom in spec.geoms if 'torso' in geom.name]
   pos_x = [torso.xpos[0] for torso in torsos]
   pos_y = [torso.xpos[1] for torso in torsos]

使用 ``bind`` 方法要求 :ref:`mjModel` 和 :ref:`mjData` 是由 :`ref:`mjSpec` 编译而来的。如果自上次编译以来
:ref:`mjSpec` 中有对象被添加或移除，则会引发错误。

说明
----

- :ref:`mj_recompile` 的工作方式与 C API 中不同。在 C API 中，它会就地修改模型和数据，
  而在 Python API 中，它会返回新的 :ref:`MjModel` 和 :ref:`MjData` 对象。这样做是为了避免悬空引用。

.. _PyBuild:

从源码构建
==========

.. note::
    只有在修改 Python 绑定（或者需要在极其老旧的 Linux 系统上运行）时，
    才需要从源码构建。
    否则，我们建议安装 PyPI 上预构建的二进制包。

1. 请确保已安装 CMake 和支持 C++17 的编译器。

2. 从 GitHub 克隆完整的 ``mujoco`` 仓库。

   .. code-block:: shell

     git clone https://github.com/google-deepmind/mujoco.git

3. 安装 MuJoCo。可以从 GitHub 下载
   `最新的二进制发行版 <https://github.com/google-deepmind/mujoco/releases>`__
   （在 macOS 上，下载的是 DMG 文件，可以双击挂载，或运行 ``hdiutil attach <dmg_file>`` ），
   也可以按照 :ref:`inBuild` 中的说明从源码*构建*并*安装*。

4. ``cd`` 进入所克隆的 MuJoCo 代码库中的 python 目录：

   .. code-block:: shell

      cd mujoco/python

5. 创建虚拟环境：

   .. code-block:: shell

      python3 -m venv /tmp/mujoco
      source /tmp/mujoco/bin/activate

6. 使用 ``make_sdist.sh`` 脚本生成
   `源码发行版 <https://packaging.python.org/en/latest/glossary/#term-Source-Distribution-or-sdist>`__
   压缩包。

   .. code-block:: shell

      bash make_sdist.sh

   ``make_sdist.sh`` 脚本会生成构建核心绑定所需的额外 C++ 头文件，并把仓库中 ``python`` 目录之外的所需文件
   也一并拉入 sdist。
   完成后，脚本会创建一个 ``dist`` 目录，其中包含一个
   ``mujoco_core-x.y.z.tar.gz`` 文件（其中 ``x.y.z`` 为版本号）。

   .. note::
      若还要构建可选子包或顶层元包的源码发行版，请运行 ``(cd studio && bash make_sdist.sh)``
      （ ``studio/dist/mujoco_studio-x.y.z.tar.gz`` ）、 ``(cd studio_wasm && bash make_sdist.sh)``
      （ ``studio_wasm/dist/mujoco_studio_wasm-x.y.z.tar.gz`` ，需先构建
      Emscripten Web 客户端）、 ``(cd usd && bash make_sdist.sh)``
      （ ``usd/dist/mujoco_usd-x.y.z.tar.gz`` ）或 ``(cd mujoco_full && bash make_sdist.sh)``
      （ ``mujoco_full/dist/mujoco-x.y.z.tar.gz`` ）。

7. 使用生成的源码发行版来构建并安装绑定。
   你需要在 ``MUJOCO_PATH`` 环境变量中指定先前下载，或构建并安装的 MuJoCo 库的路径，并在
   ``MUJOCO_PLUGIN_PATH`` 环境变量中指定 MuJoCo 插件目录的路径。你可以把
   ``MUJOCO_PLUGIN_PATH`` 环境变量指向所克隆的 MuJoCo 代码库的 ``plugin``
   文件夹。

   .. note::
      对于 macOS，需要从 DMG 中提取这些文件。
      按步骤 2 挂载之后，可以在 ``/Volumes/MuJoCo`` 中找到 ``mujoco.framework`` 目录，
      在 ``/Volumes/MuJoCo/MuJoCo.app/Contents/MacOS/mujoco_plugin`` 中找到插件目录。
      可以把这两个目录复制到某个方便的位置，也可以使用
      ``MUJOCO_PATH=/Volumes/MuJoCo MUJOCO_PLUGIN_PATH=/Volumes/MuJoCo/MuJoCo.app/Contents/MacOS/mujoco_plugin`` 。

   .. code-block:: shell

      cd dist
      MUJOCO_PATH=/PATH/TO/MUJOCO \
      MUJOCO_PLUGIN_PATH=/PATH/TO/MUJOCO/PLUGIN \
      pip install mujoco_core-x.y.z.tar.gz

现在 Python 绑定应该已经安装好了！要检查是否安装成功，请 ``cd`` 到 ``mujoco`` 目录之外，并运行
``python -c "import mujoco"`` 。

.. tip::
   作为参考，可以在 GitHub 上 MuJoCo 的
   `持续集成配置 <https://github.com/google-deepmind/mujoco/blob/main/.github/workflows/build.yml>`_ 中找到一份可用的构建配置。

.. _PyBuildBazel:

使用 Bazel 构建
---------------

Python 绑定也可以用 Bazel 构建（参见 :ref:`inBuildBazel` ）。 ``@mujoco//python/mujoco`` 目标
提供 ``mujoco`` 包，因此你自己的 Bazel 模块中的 Python 目标可以直接依赖它。在 ``MODULE.bazel`` 中对
``rules_python`` 添加 ``bazel_dep`` 之后：

.. code-block:: python

   load("@rules_python//python:py_binary.bzl", "py_binary")

   py_binary(
       name = "simulate_model",
       srcs = ["simulate_model.py"],
       deps = ["@mujoco//python/mujoco"],
   )

与 wheel 包一样，这些绑定以动态方式链接 MuJoCo（ ``@mujoco//:mujoco_shared`` ），所附带的插件是独立的共享库，在 ``mujoco`` 被导入时加载。
在同一进程中以相同方式链接 MuJoCo 的 C++ 代码，与这些绑定共享同一个引擎。

要在克隆下来的仓库根目录运行这些绑定的测试，请使用 ``bazel test //python/...`` 。

Bazel 构建支持 ``MODULE.bazel`` 中列出的 Python 版本，并从 ``pypi.org`` 安装绑定所依赖的 PyPI 包。它涵盖核心绑定和离屏渲染
（ ``mujoco.Renderer`` 和 GL 上下文，参见 :ref:`PyRender` ）；交互式查看器、MJX 和 USD 导出器目前尚不支持。

.. _PyRollout:

rollout
-------
``mujoco.rollout`` 和 ``mujoco.rollout.Rollout`` 展示了如何通过 pybind11 添加额外的 C/C++ 功能，并将其作为 Python 模块暴露出来。它实现于 `rollout.cc
<https://github.com/google-deepmind/mujoco/blob/main/python/mujoco/rollout.cc>`__，并在 `rollout.py
<https://github.com/google-deepmind/mujoco/blob/main/python/mujoco/rollout.py>`__ 中进行了封装。该模块面向一种常见的用例，即在 Python 之外实现的紧凑循环会带来好处：
给定初始状态和控制序列，推演（rollout）一条轨迹（即在循环中调用
:ref:`mj_step` ），并返回随后的状态和传感器（sensor）数值。如果传入多个 MjData 实例（每个线程一个）作为参数，则这些推演会借助内部管理的线程池并行运行。
这个笔记本展示了如何使用 ``rollout`` |rollout_colab|，并给出了一些基准测试，例如下图。

.. |rollout_colab| image:: https://colab.research.google.com/assets/colab-badge.png
                   :target: https://colab.research.google.com/github/google-deepmind/mujoco/blob/main/python/rollout.ipynb

.. image:: images/python/rollout.png
   :align: right
   :width: 97%

基本用法形式为

.. code-block:: python

   state, sensordata = rollout.rollout(model, data, initial_state, control)

- ``model`` 要么是单个 MjModel 实例，要么是长度为 ``nbatch`` 的同质 MjModel 序列。
  同质模型具有相同的整数尺寸，但浮点数值可以不同。
- ``data`` 要么是单个 MjData 实例，要么是长度为 ``nthread`` 的兼容 MjData 序列。
- ``initial_state`` 是一个 ``nbatch x nstate`` 数组，包含 ``nbatch`` 个大小为 ``nstate`` 的初始状态，其中
  ``nstate = mj_stateSize(model, mjtState.mjSTATE_FULLPHYSICS)`` 是
  :ref:`完整物理状态 <siFullPhysics>` 的大小。
- ``control`` 是一个 ``nbatch x nstep x ncontrol`` 的控制数组。默认情况下，控制是 ``mjModel.nu`` 个标准
  执行器（actuator），但通过传入可选的 ``control_spec`` 位标志，可以指定任意组合的 :ref:`用户输入 <siInput>` 数组。

如果某次推演发散，则用当前状态和传感器数值填充轨迹的其余部分。
因此，可以利用时间值不再递增来检测发散的推演。

``rollout`` 函数被设计为计算上无状态，因此步进流程的所有输入都会被设置，给定的 ``MjData`` 实例中已有的任何值都不会对输出产生影响。

``rollout`` 在各次推演之间使用多线程，因此安装了 :ref:`mju_threadpool` 的 ``MjData`` 会被拒绝。对于在多次调用之间持续存在的
仿真，请参见 :ref:`batch<PyBatch>` 。

默认情况下，如果 ``len(data) > 1`` ，则 ``rollout.rollout`` 每次调用都会创建一个新的线程池。若要在多次调用之间复用线程池，请使用 ``persistent_pool`` 参数。
使用持久线程池时， ``rollout.rollout`` 不是线程安全的。基本用法形式为

.. code-block:: python

   state, sensordata = rollout.rollout(model, data, initial_state, persistent_pool=True)

线程池会在解释器关闭时关闭，或通过调用 ``rollout.shutdown_persistent_pool`` 关闭。

若要在多个线程中使用多个线程池，请使用 ``Rollout`` 对象。基本用法形式为

.. code-block:: python

   # Pool shutdown upon exiting block.
   with rollout.Rollout(nthread=nthread) as rollout_:
    rollout_.rollout(model, data, initial_state)

或者

.. code-block:: python

   # Pool shutdown on object deletion or call to rollout_.close().
   # To ensure clean shutdown of threads, call close() before interpreter exit.
   rollout_ = rollout.Rollout(nthread=nthread)
   rollout_.rollout(model, data, initial_state)
   rollout_.close()

由于全局解释器锁已被释放，该函数也可以使用 Python 线程并行。不过，这
不如使用原生线程高效。线程化操作的示例（以及更一般的用法示例）请参见
`rollout_test.py <https://github.com/google-deepmind/mujoco/blob/main/python/mujoco/rollout_test.py>`__ 中的 ``test_threading`` 函数。

.. _PyBatch:

batch
-----
``mujoco.batch.Batch`` 在线程池上运行同一个模型的大量仿真，并将它们的字段以 NumPy 数组的行的形式暴露出来。它封装了 :ref:`批量 API <Batchedsimulation>` 。

.. code-block:: python

   from mujoco import batch

   b = batch.Batch(model, nsim=1024, nthread=8)
   qpos, ctrl, xpos = b.bind('qpos'), b.bind('ctrl'), b.bind('xpos')
   for _ in range(1000):
     ctrl[:] = policy(qpos, xpos)
     b.step()

每个仿真对应其 :ref:`积分状态 <siIntegrationState>` ，即 ``b.state`` 的一行。一次调用会把每个仿真的行加载到一个 ``MjData`` 中，运行，然后把该行保存回去，
这一过程使用包括调用方线程在内的 ``nthread`` 个线程（默认每个 CPU 一个），并且全局解释器锁已被释放。结果与对每个仿真各用一个
``MjData`` 的循环逐位相同，与线程数无关。

- ``bind(name)`` 返回一个覆盖 ``MjData`` 字段的实时 ``nsim x ...`` 数组。 ``qpos`` 、 ``ctrl``
  和 ``mocap_pos`` 等状态字段是这些行的视图，写入的内容会成为该仿真在下一次调用时的状态。其他字段在对某个仿真每次调用之后被复制出来，
  并且是只读的；在 ``step`` 之后，它们比状态滞后一个子步，这与 :ref:`mj_step` 相同。在标量中，计数 ``ncon`` 、 ``ne`` 、 ``nf`` 、 ``nl`` 、 ``nefc`` 、 ``nJ`` 、 ``nA`` 、
  ``nisland`` 和 ``nidof`` 绑定为长度 ``nsim`` 的整型数组。在非持久（persistent）的 batch 中，两次调用之间绑定的字段
  在下一次调用之前读取为零。
  这些行保存的是 :ref:`mjtNum` 值，因此 ``eq_active`` 绑定为 ``mjtNum`` ，而不是 ``MjData`` 中的字节类型。字段
  也是属性，与 ``MjData`` 上相同： ``b.xpos`` 绑定 ``xpos`` ， ``b.ctrl = u`` 会写入每个仿真的
  控制。 ``mujoco.batch.DATA_FIELDS`` 和 ``mujoco.batch.MODEL_FIELDS`` 列出了 ``bind`` 和 ``expand``
  接受的字段名。
- ``joint(name)`` 、 ``body(name)`` 、 ``site(name)`` 、 ``sensor(name)`` 、 ``actuator(name)`` 、 ``geom(name)`` 、
  ``tendon(name)`` 、 ``camera(name)`` 和 ``light(name)`` 给出某个对象在已绑定字段和已展开字段中的列，
  并带有 ``MjData`` 和 ``MjModel`` 两者的 :ref:`具名访问 <PyNamed>` 属性： ``b.joint('hinge').qpos`` 是
  ``nsim x 1`` ， ``b.body('pole').mass = masses`` 会写入各仿真各自的质量，与 ``expand`` 的效果相同。
  ``equality(name)`` 、 ``pair(name)`` 、 ``material(name)`` 、 ``numeric(name)`` 和 ``keyframe(name)`` 的作用类似，但
  只带有 ``MjModel`` 的属性。
- ``get_model(sim)`` 和 ``get_data(sim)`` 把某个仿真实例化为 ``MjModel`` 和 ``MjData`` ，以便用于渲染
  或任何函数；参见 :ref:`mjb_getModel` 和 :ref:`mjb_getData` 。
- ``set_models(models)`` 让每个仿真在调用方提供的模型上运行（每个仿真一个 ``MjModel`` ，或所有仿真共用一个），
  而不是使用 batch 自己的模型，用来替代展开字段；此后具名视图会从每个仿真各自的模型读取模型属性，而 ``models`` 返回所设置的模型。参见 :ref:`mjb_setModels` 。
- ``expand(name)`` 为某个 ``MjModel`` 字段，或名为 ``opt.<name>`` 的 ``MjOption`` 字段提供逐仿真的取值，
  在每次调用之前应用； ``expanded(name)`` 返回某个字段只读的逐仿真取值而不展开它，
  如果该字段仍为共享则返回 ``None`` 。 ``set_const`` 对每个仿真运行 :ref:`mj_setConst` ，由它推导出的字段
  也会变为逐仿真的。在写入 :ref:`mj_setConst` 所读取的某个字段（即
  ``mujoco.MjModel._setconst_inputs`` 之一，或某个 ``MjOption`` 字段）之后，请调用 ``set_const`` ，以便由它推导出的常量
  随之更新。
- ``step(ids, nstep)`` 、 ``forward(ids)`` 、 ``reset(ids, keyframe)`` 和 ``set_const(ids)`` 在仿真 ``ids`` 上运行，
  ``ids`` 是已排序、唯一且非负的整数或布尔掩码，也可以对全部仿真运行。 ``reset`` 会丢弃它之前
  所做的写入，并可以为本次调用的每个仿真统一指定一个关键帧（keyframe），也可以各指定一个。
- ``step(nstep, stage=mujoco.mjtStage.mjSTAGE_VEL)`` 使位置相关和速度相关的字段与传感器描述的是
  新状态，如同 :ref:`mj_step1` 所做的那样，而不是最后一个子步之前的状态。在持久（persistent）batch 中，
  这不会带来额外开销；参见 :ref:`mjb_step` 。 ``reset`` 和 ``forward`` 也接受 ``stage`` ，默认为
  ``mjSTAGE_ACC`` ： ``reset(ids, stage=mujoco.mjtStage.mjSTAGE_NONE)`` 会跳过重置后的前向计算，适用于重置之后
  接着进行随机化和 ``forward(ids)`` 的情形。
- ``rollout(nstep, control, control_spec, record, ids)`` 的步进方式与 :ref:`rollout<PyRollout>` 相同，在每个子步之后记录任意 ``MjData``
  字段或状态向量，并将它们作为 ``n x nstep x ...`` 数组返回。警告计数器上升的仿真会停止步进，其余的记录会重复它的最后一条记录。
- ``jac(body, point, ids)`` 和 ``ray(pnt, vec, ..., normal=False)`` 对每个仿真分别计算 :ref:`mj_jac` 和 :ref:`mj_ray` ，
  如果给出，则每个仿真对应一个刚体，每条射线对应一个要排除的刚体，并可按需返回命中点的表面法线。它们会先根据状态计算运动学，
  ``jac`` 使用 :ref:`mj_kinematics` 和 :ref:`mj_comPos` ， ``ray`` 使用 :ref:`mj_kinematics` ，并且如果模型有柔性体（flex），还会使用 :ref:`mj_flex` 。状态和已绑定
  的字段保持不变；在持久（persistent）batch 中，仿真的 ``MjData`` 会保留这些运动学结果。
- ``b.warning`` 保存每个仿真的警告计数器，形状为 ``nsim x mjNWARNING x 2`` （ :ref:`mjWarningStat` 的 ``lastinfo`` 和 ``number`` ），
  随其状态一起保存和恢复。

如果 MuJoCo 在某些仿真中引发错误，该调用会引发 ``mujoco.batch.SimulationError`` 并列出这些仿真。它们保持调用之前的状态，
其余仿真则运行到结束。 ``b.status`` 和 ``b.error(i)`` 保存每个仿真上一次调用的结果。 ``SimulationError`` 是一个 ``RuntimeError`` ，其 ``ids`` 属性列出失败的
仿真。无效参数会引发 ``ValueError`` ，若是 batch API 拒绝这些参数，则引发 ``mujoco.FatalError`` 。一个
``Batch`` 不得被多个 Python 线程同时使用：它的各次调用会被串行化，但每次调用都从这份逐仿真的结果中报告其失败情况，而下一次调用会覆盖这份结果。

默认情况下，一个 ``MjData`` 服务于多个仿真，因此内存随线程数而不是仿真数增长，并且某次
调用未计算的字段（例如 ``step`` 之后的 ``qfrc_inverse`` ）保存的是另一个仿真的值。 ``Batch(model, nsim,
persistent=True)\ `` 则改为为每个仿真保留一个 ``\ MjData``，对于启用了
:ref:`sleep<option-flag-sleep>` 或 :ref:`IPC<option-flag-ipc>` 的模型，这是必需的。同样，在 ``plugin_state`` 之外
保存状态的 :ref:`引擎插件 <exPlugin>` ，除非 batch 是持久的，否则会在同一线程所运行的各个仿真之间共享这些状态。

batch 的线程是跨仿真运行的，而 :ref:`mju_threadpool` 是在单个仿真内部进行多线程；两者不能
组合使用。 :ref:`物理回调 <glPhysics>` 必须是通过 ``ctypes`` 安装的 C 函数：如果安装的是 Python
函数，batch 的调用会引发 ``ValueError`` 。包装了 Python 函数的 ``ctypes`` 函数是允许的，但它在运行时会持有全局解释器锁，
从而使 batch 的各线程串行化，并且它的异常只会被打印而不会被抛出。在 batch 线程上引发的警告会交给全局日志处理程序，
只有在调用方线程上引发的警告才会同时到达线程局部的处理程序； ``b.warning`` 的计数器会把它们全部计入。

.. _PyUSDexport:

USD 导出器
----------

`USD 导出器 <https://github.com/google-deepmind/mujoco/tree/main/python/mujoco/usd>`__ 模块允许用户将场景和轨迹保存为 `USD 格式 <https://openusd.org/release/index.html>`__ ，
以便在 NVIDIA Omniverse 或 Blender 等外部渲染器中渲染。这些渲染器提供了默认渲染器所不具备的更高质量的渲染能力。此外，导出为 USD 还允许用户加入不同类型的纹理贴图，
使场景中的物体看起来更加逼真。

.. _PyUSDInstallation:

安装
^^^^

推荐通过 `PyPI <https://pypi.org/project/mujoco/>`__ 安装 OpenUSD 支持：

.. code-block:: shell

   pip install mujoco[usd]

这会安装 ``usd-core`` 和 ``pillow`` （下面的纯 Python ``USDExporter`` 需要它们）；并且在 Linux ``x86_64`` 、Windows ``x86_64`` 和 macOS ``arm64`` 上的 Python 3.11--3.13 中，还会安装
`mujoco-usd <https://pypi.org/project/mujoco-usd/>`__ ，它提供预构建的 C++ OpenUSD 导入器
（ ``usd_decoder`` ）、原生导出器（ ``mujoco.usd.writer`` 和 ``mujoco.usd.layer_sink`` ）以及物理模式
（ ``mujoco.usd.MjcPhysics`` ）。使用 ``mujoco-core`` 的无头（headless）用户也可以直接安装 ``pip install mujoco-usd`` （或
``pip install mujoco-core[usd]`` ）；请注意， ``mujoco-usd`` 会固定它所编译时对应的确切 ``usd-core`` 版本
（ ``usd-core==25.11`` ）。有关原生 OpenUSD 工作流的详情，请参见 :doc:`OpenUSD/index` 。

如果你是从源码构建，请确保先 `构建 Python 绑定
<https://mujoco.readthedocs.io/en/stable/python.html#building-from-source>`__。然后使用 pip 安装所需的
``usd-core`` 和 ``pillow`` 包（或参见 :doc:`OpenUSD/building` 从源码构建 C++ OpenUSD 绑定）。

.. _PyUSDExporter:

USDExporter
^^^^^^^^^^^

``mujoco.usd.exporter`` 模块中的 ``USDExporter`` 类除了可以定义自定义相机和灯光之外，还允许保存完整的轨迹。 ``USDExporter`` 实例的构造函数参数如下：

- ``model`` ：一个 MjModel 实例。USD 导出器会从模型中读取相关信息，包括相机、灯光、纹理和物体几何体的详细信息。

- ``max_geom`` ：场景中 geom 的最大数量，在实例化内部的 :ref:`mjvScene` 时需要。

- ``output_directory`` ：用于存放导出的 USD 文件及所有相关资源的目录名称。
  将场景/轨迹保存为 USD 文件时，导出器会创建如下目录结构。

  .. code-block:: text

      output_directory_root/
      └-output_directory/
        ├-assets/
        | ├-texture_0.png
        | ├-texture_1.png
        | └-...
        └─frames/
          └-frame_301.usd

  使用这种文件结构，用户可以方便地归档 ``output_directory`` 。USD 文件中所有指向资源的路径都是相对路径，
  便于在另一台机器上使用该 USD 归档。

- ``output_directory_root`` ：USD 轨迹所添加到的根目录。

- ``light_intensity`` ：所有灯光的强度。请注意，不同渲染器对强度单位的定义可能不同，
  因此可能需要针对具体的渲染器调整这个值。

- ``camera_names`` ：要存储在 USD 文件中的相机列表。在每个时间步，对于定义的每个相机，我们
  计算其位置和朝向，并把该值添加到 USD 中对应的那一帧。USD 允许我们存储
  多个相机。

- ``verbose`` ：是否打印导出器的日志信息。

如果你希望导出直接从 MJCF 加载的模型，我们提供了一个
`演示 <https://github.com/google-deepmind/mujoco/blob/main/python/mujoco/usd/demo.py>`__ 脚本，展示了具体做法。该
演示文件同时也是 USD 导出功能的一个示例。

.. _PyUSDBasicUsage:

基本用法
^^^^^^^^

安装好可选依赖之后，可以通过 ``from mujoco.usd import exporter`` 导入 USD 导出器。

下面我们演示 ``USDExporter`` 的一个简单示例。在初始化期间， ``USDExporter`` 会创建
一个空的 USD stage，并在 assets 和 frames 目录尚不存在时创建它们。此外，它会
为模型中定义的每个纹理生成 .png 文件。每次调用 ``update_scene`` 时，导出器都会记录
场景中所有 geom、灯光和相机的位置与朝向。

``USDExporter`` 通过维护一个帧计数器在内部跟踪帧。每次调用 ``update_scene`` 时，
计数器都会递增，并为对应的帧保存所有 geom、相机和灯光的位姿。需要注意的是，在调用 ``update_scene`` 之前，你可以多次推进仿真。
最终的 USD 文件只会存储最后一次 update_scene 调用时 geom、灯光和相机的位姿。

.. code-block:: python

    import mujoco
    from mujoco.usd import exporter

    m = mujoco.MjModel.from_xml_path('/path/to/mjcf.xml')
    d = mujoco.MjData(m)

    # Create the USDExporter
    exp = exporter.USDExporter(model=m)

    duration = 5
    framerate = 60
    while d.time < duration:

      # Step the physics
      mujoco.mj_step(m, d)

      if exp.frame_count < d.time * framerate:
        # Update the USD with a new frame
        exp.update_scene(data=d)

    # Export the USD file
    exp.save_scene(filetype="usd")



.. _PyUSDExportAPI:

USD 导出 API
^^^^^^^^^^^^

- ``update_scene(self, data, scene_option)`` ：用用户传入的最新仿真数据更新场景。该函数会更新场景中的 geom、相机和灯光。

- ``add_light(self, pos, intensity, radius, color, obj_name, light_type)`` ：事后向 USD 场景中添加一个具有
  给定属性的灯光。

- ``add_camera(self, pos, rotation_xyz, obj_name)`` ：事后向 USD 场景中添加一个具有给定属性的相机。

- ``save_scene(self, filetype)`` ：使用 USD 文件类型扩展名 ``.usd`` 、 ``.usda``
  或 ``.usdc`` 之一导出 USD 场景。

.. _PyMjpy_migration:

mujoco-py 迁移
==============

在 mujoco-py 中，主要入口是 `MjSim <https://github.com/openai/mujoco-py/blob/master/mujoco_py/mjsim.pyx>`_
类。用户从 MJCF 模型构造一个有状态的 ``MjSim`` 实例（类似于 ``dm_control.Physics`` ），该
实例持有对一个 ``mjModel`` 实例及其关联的 ``mjData`` 的引用。相比之下，MuJoCo Python
绑定（ ``mujoco`` ）采取了更底层的方式，如上文所述：遵循 C 库的设计原则， ``mujoco`` 模块本身是无状态的，仅仅封装了底层的原生结构体和函数。

虽然对 mujoco-py 的全面梳理超出了本文档的范围，但我们在下面针对 mujoco-py 的一份非穷尽的具体功能清单，给出了实现说明：

``mujoco_py.load_model_from_xml(bstring)``
   这个工厂函数会构造一个有状态的 ``MjSim`` 实例。使用 ``mujoco`` 时，用户应调用 :ref:`上文 <PyStructs>` 所述的工厂函数 ``mujoco.MjModel.from_xml_*`` 。随后由用户负责
   持有得到的 ``MjModel`` 结构体实例，并通过调用 ``mujoco.MjData(model)`` 显式生成对应的 ``MjData`` 。

``sim.reset()``, ``sim.forward()``, ``sim.step()``
   与上文一样， ``mujoco`` 用户需要调用底层库函数，并传入 ``MjModel`` 和 ``MjData`` 实例：
   :ref:`mujoco.mj_resetData(model, data) <mj_resetData>` 、 :ref:`mujoco.mj_forward(model, data)
   <mj_forward>` 和 :ref:`mujoco.mj_step(model, data) <mj_step>` 。

``sim.get_state()``, ``sim.set_state(state)``, ``sim.get_flattened_state()``, ``sim.set_state_from_flattened(state)``
   如 :ref:`编程部分 <Simulation>` 所述，给定特定输入时，MuJoCo 库的计算是确定性的。mujoco-py 实现了用于获取和设置部分相关字段的方法（
   类似地， ``dm_control.Physics`` 提供了对应于展平情形的方法）。这些功能在 :ref:`状态与控制 <siStateControl>` 一节中有说明。

``sim.model.get_joint_qvel_addr(joint_name)``
   这是 mujoco-py 中的一个便捷方法，返回与该关节对应的一组连续索引的列表。该
   列表从 ``model.jnt_qposadr[joint_index]`` 开始，其长度取决于关节类型。 ``mujoco`` 不
   提供这一功能，但可以很容易地用 ``model.jnt_qposadr[joint_index]`` 和
   ``xrange`` 构造出这个列表。

``sim.model.*_name2id(name)``
   mujoco-py 在 ``MjSim`` 中创建了字典，可高效地查找不同类型对象的索引：
   ``site_name2id`` 、 ``body_name2id`` 等。这些函数取代了函数 :ref:`mujoco.mj_name2id(model,
   type_enum, name) <mj_name2id>`。 ``mujoco`` 提供了另一种使用实体名称的方式——
   :ref:`具名访问 <PyNamed>` ，同时也提供对原生 :ref:`mj_name2id` 的访问。

``sim.save(fstream, format_name)``
   这是 MuJoCo 库（因而也是 ``mujoco`` ）唯一有状态的场合：它在内存中保存着最近一次编译的 XML 的副本，供
   :ref:`mujoco.mj_saveLastXML(fname) <mj_saveLastXML>` 使用。请注意，
   mujoco-py 的实现有一个便利的额外特性：保存之前，位姿（由 ``sim.data`` 的
   状态确定）会被转换为一个关键帧并添加到模型中。目前 ``mujoco`` 中尚无这一额外特性。
