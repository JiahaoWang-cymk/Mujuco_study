## 11.1 回头看：这套课程停在了哪里

前 10 课全部在 CPU 上、用一个 `MjData` 仿真一台 G1：

| 课 | 做了什么 | 谁在“出主意” |
|---|---|---|
| 2–6 | 站立、吊起来挥手、读传感器、推它、算重力补偿力矩 | 你写的 PD、逆动力学 |
| 7–8 | 逆运动学够球、LQR 单腿平衡 | 你写的优化与线性控制 |
| 9 | 让它走起来 | **别人训练好的神经网络**（宇树 `motion.pt`） |
| 10 | 离屏渲染、批量推力实验 | 站立时的位置伺服 + 你写的统计 |

第 9 课是一个分水岭：走路这件事，我们没有手写控制器，而是“部署”了一个训练好的策略。宇树 `unitree_rl_gym` 仓库把流程写成四步：

```text
Train（在 Isaac Gym 里训练）→ Play（在训练用的仿真器里回放）→ Sim2Sim（换到 MuJoCo 里验证）→ Sim2Real（上真机）
```

第 9 课做的正是其中的 **Sim2Sim**：策略在别的仿真器里练成，到 MuJoCo 里检验它是否依赖了训练仿真器的“特性”。往后要学的，是最前面那一步 **Train**。

训练强化学习策略要海量样本：机器人一遍遍摔倒、重来。官方文档在 MJX 一页里说得很直接：这类工作负载“需要海量数据吞吐”，而 GPU 可以把几千个相同的场景放在一起并行仿真。这就是本附录的主角都和 GPU 有关的原因。

## 11.3 同一台 G1，三个模型版本

Menagerie 的 `unitree_g1/` 目录里，同一台机器人有三份 MJCF。它们的身体、关节、质量都一样，区别在“为谁准备”：

| 文件 | 给谁用 | 碰撞 | 执行器与求解器 |
|---|---|---|---|
| `g1.xml` | CPU 仿真，本课程第 1–8 课 | 网格碰撞体 + 每只脚 4 个小球，自动检测所有可能的碰撞对 | 29 个 position 执行器，kp=500；默认求解器参数 |
| `g1_mjx.xml`（由 `scene_mjx.xml` 引用） | MJX / MuJoCo Playground | 手工设计的胶囊体和盒子；默认关闭碰撞，只用 49 个显式 `<pair>` | 增益更低（多数关节 kp=75，踝和腕 kp=20，README 称“更真实”）；`timestep=0.004`、`iterations=5`、`ls_iterations=8`、关闭 `eulerdamp` |
| `g1_mjlab.xml` | mjlab | 脚改成胶囊体，打开自碰撞，用 4 个 `<exclude>` 排除相邻部件 | **去掉了**执行器和求解器选项，由 mjlab 在代码里补上 |

这张表背后有两条规律：

- **GPU 喜欢简单的碰撞。** 官方文档的 MJX 性能调优一节建议：用 `<contact><pair>` 显式列出需要的碰撞对；网格碰撞要控制顶点数；求解器迭代次数降到“刚好稳定”。`g1_mjx.xml` 几乎是这几条建议的逐条落地。
- **GPU 版模型更“粗”。** 迭代上限从 100 降到 5，让每一步更便宜；步长翻倍，同样的仿真时间只用算一半的步数。强化学习本来就会加入域随机化（随机改摩擦、质量等），对单步精度没那么敏感。

> 第 3 课用 MjSpec 改过模型。`g1_mjlab.xml` 把这件事推到了极致：XML 里只留机器人本体（外加 5 个传感器），执行器、求解器选项、地形都由训练代码程序化地加。

## 11.4 四个入口

### 一张表看全

| 名字 | 是什么 | 编程框架 | 硬件 | G1 相关 |
|---|---|---|---|---|
| **MJX** | MuJoCo 的 JAX 接口，`pip install mujoco-mjx` | JAX | MJX-JAX：NVIDIA/AMD GPU、Apple Silicon、TPU；MJX-Warp：NVIDIA GPU | Menagerie 的 `g1_mjx.xml` |
| **MuJoCo Warp（MJWarp）** | 用 NVIDIA Warp 写的 MuJoCo，`pip install mujoco-warp` | Warp，可与 PyTorch、JAX 互操作 | NVIDIA GPU（也能用 `wp.set_device("cpu")` 在 CPU 上跑，适合调试） | 它是 Playground 1.0 和 mjlab 的物理后端 |
| **MuJoCo Playground** | DeepMind 的开源机器人学习环境套件 | 1.0 版用 PyTorch；2025 年论文版用 JAX/MJX | 训练建议 NVIDIA GPU | 论文版有 `G1JoystickFlatTerrain`、`G1JoystickRoughTerrain`；1.0 版仓库有 `robots/g1` |
| **mjlab** | Isaac Lab 风格的接口 + MuJoCo Warp 的训练框架 | PyTorch | 训练需要 NVIDIA GPU | `Mjlab-Velocity-Flat-Unitree-G1`、`Mjlab-Tracking-Flat-Unitree-G1`；模型用 `g1_mjlab.xml` |

前两个是**仿真器**（只管物理），后两个是**训练框架**（环境、奖励、PPO 都配好了）。想尽快让 G1 学会走路，从后两个入手；想理解底层或写自己的框架，再看前两个。

### MJX：JAX 接口，有两种实现

MJX 现在有两种实现，用 `impl` 参数选：

- **MJX-JAX**：用 JAX 重写的 MuJoCo，能跑在 XLA 支持的各种硬件上，**大部分可微分**。缺点在官方文档“锋利之处”一节写得很清楚：单个场景可能比 CPU 版慢 10 倍；大网格碰撞和接触很多的场景性能会掉得很快。
- **MJX-Warp**（`mjx.put_model(m, impl='warp')`）：底层换成 MuJoCo Warp，专为 NVIDIA GPU 优化，接触和约束的性能瓶颈缓解了，但**不支持自动微分**。官方的建议是：除非需要梯度、场景又小，否则用 MJX-Warp。

入门教程 10.1 节有一段完整的 MJX 小球示例。资料包里还有官方的 MJX 教程 notebook（`官方仓库_模型与教程/mjx/tutorial.ipynb`），从 `mjx.step` 讲到用 Brax 的 PPO 训练 Humanoid 和四足机器人。它要在有 GPU 的环境里运行，但现在就可以先读。

### MuJoCo Warp：吞吐量优先

官方文档对它的定位有三句话值得记住：

1. MJWarp 优化的是**吞吐量**（单位时间的总步数），CPU 版 MuJoCo 优化的是**延迟**（一步要多久）。所以单步比不过 CPU 版，适合强化学习；实时控制（比如 MPC）、交互式界面还是用 CPU 版。
2. 接触和约束缓冲区要预先分配（`nconmax` / `naconmax`、`njmax`），**溢出会导致未定义行为**，要用 `mjwarp-testspeed` 或检查 `Data.overflow` 来调。
3. 用 float32 计算，GPU 上结果**不完全确定**（原子操作顺序不定）；`wp.set_device("cpu")` 可以得到确定结果，代价是失去 GPU 的并行速度。

另外两条和 G1 有关：MJWarp **没有按名字访问**（第 1 课推荐的 `d.joint("left_knee_joint")` 用不了）；文档说“把单个连通机构的性能提升到约 60 个自由度以上仍是当前的优先事项”，G1 的 `nv=35` 低于这个数，不受这条限制影响。

### 动手：让 MuJoCo Warp 自己找 GPU

`code/11_gpu_rollout.py` 把上面这几条落到 G1 上，分三步：

1. **识别设备。** 先看有没有 `nvidia-smi`（装了 NVIDIA 驱动才有），再问 Warp 识别到几个 CUDA 设备。Warp 的 wheel 自带编译 GPU 内核所需的组件，有显卡和驱动就能用，不用另外装 CUDA。
2. **CPU 版对照。** 用 11.2 节的 `mujoco.rollout` 多线程跑同样数量的 G1，得到 CPU 的步数/秒，也记下结束时骨盆的平均高度。
3. **MuJoCo Warp。** `mjw.put_model` 把模型拷到设备上，`mjw.put_data(..., nworld=N)` 一次开 N 个世界，再反复调用 `mjw.step`。在 GPU 上，脚本会把一步录成 CUDA graph 反复重放，省掉每步启动几十个内核的开销。最后检查 `Data.overflow`，看接触、约束缓冲区有没有溢出。

```bash
python code/11_gpu_rollout.py                   # 自动识别：有 GPU 用 GPU（默认 4096 台），没有就 CPU 模式（16 台）
python code/11_gpu_rollout.py --nworld 8192     # GPU 上加大规模，看吞吐量还涨不涨
python code/11_gpu_rollout.py --model full      # 换成第 1–8 课的 g1.xml
```

读输出时注意三点：

- **核对物理是否一致。** 两边结束时的骨盆平均高度应当接近（Warp 用 float32，每台的初速度还加了一点随机扰动，所以不会完全相同）。在没有显卡的机器上实测，`g1.xml` 两边都是 0.792 m，`g1_mjx.xml` 是 0.683 m 对 0.691 m。
- **“求解器迭代达到上限”不是错误。** `g1_mjx.xml` 故意只给 5 次迭代（11.3 节），脚本会单独说明这一项；真正要处理的是缓冲区溢出，按提示调大 `nconmax`、`njmax`。
- **没有显卡时，比值没有意义。** Warp 的 CPU 模式比 CPU 版 MuJoCo 慢得多（实测约 1,400 对 220,000 步/秒），它只用来调试和确认代码能跑。要看 GPU 的数字，得在有 NVIDIA 显卡的机器上运行。显卡初始化失败时（例如驱动太旧、显存不够），脚本会打印原因并自动退回 CPU 模式。

第一次在某个设备上运行要编译 Warp 内核，CPU 上约半分钟到一分钟，之后用缓存（Windows 上在 `%LOCALAPPDATA%\NVIDIA\warp\Cache`），几秒钟就开始计时。

### MuJoCo Playground：带 G1 的环境套件

Playground 论文（2025）的摘要说，它可以用 pip 安装，在**单块 GPU 上几分钟内**训练出策略，并支持四足、人形、灵巧手、机械臂，能零样本迁移到真机。Menagerie 的 G1 README 也写着：`g1_mjx.xml` 这个模型已经在 Playground 里成功迁移到了真机。

要注意它有两代：

- **论文版**（仓库里的 `rss2025` 目录，PyPI 上是 `playground==0.2.0`）：JAX + MJX + Brax PPO。G1 的两个行走环境 `G1JoystickFlatTerrain`、`G1JoystickRoughTerrain` 在这一版里。
- **1.0 版**（入门教程 10.3 节介绍的就是它）：改用 PyTorch，物理后端是 MuJoCo 或 MuJoCo Warp。README 要求 Python 3.12–3.13，训练用 CUDA 12 或 13 的 NVIDIA GPU；仓库的 `robots/` 下有 `g1`，任务里有全身动作跟踪（`whole_body/tracking`）。

### mjlab：最贴近“训练 G1 走路”的入口

mjlab 把 Isaac Lab 的“管理器式”环境接口搬到了 MuJoCo Warp 上，训练用 PyTorch。它的 README 直接给出了 G1 的任务和命令：

```bash
# 在满足要求的 Linux + NVIDIA GPU 机器上
uv run train Mjlab-Velocity-Flat-Unitree-G1 --env.scene.num-envs 4096   # 平地速度跟踪（走路）
uv run play  <任务名> ...                                                  # 回放训练结果
```

`num-envs 4096` 就是“同时仿真 4096 台 G1”。11.2 节的 CPU 一次只有 16 个线程在推进 16 条轨迹；几千个环境一起推进、数据一直留在显存里，才是 GPU 训练的工作方式。

| 入口 | GPU | 操作系统（查阅官方说明时） |
|---|---|---|
| MJX-JAX | NVIDIA/AMD GPU、TPU 等 | JAX 的 NVIDIA GPU 版只正式支持 Linux；Windows 原生不支持，WSL2 属实验性；CPU 版在 Windows 上可用 |
| MJX-Warp / MuJoCo Warp | NVIDIA GPU | 本地文档没有单独限定系统，以 Warp、MJWarp 的安装说明为准；MJWarp 只依赖 `mujoco-core` |
| Playground 1.0 | 训练建议 NVIDIA GPU（CUDA 12 或 13） | 文档以 Linux 和 macOS 为例；macOS 适合 CPU 上跑通 |
| mjlab | 训练需要 NVIDIA GPU（Turing 架构或更新） | 训练：Linux；只做评估：Linux、macOS 或 Windows（WSL） |

一句话：**想在 GPU 上训练，准备一台 Linux + NVIDIA 显卡的机器**；只有 Windows 的话，用 WSL2 是最常见的折中，但要接受“实验性”的风险。

显存没有统一的门槛，官方也没有给出硬性数字。显存占用主要由**并行环境数**和**每个环境预留的接触/约束缓冲区**决定：显存不够，先把 `num-envs`（或 `nworld`）调小，再按 MJWarp 文档调小 `nconmax`、`njmax`。

> 离线安装提醒：这些框架依赖很多（CUDA 版的 JAX 或 PyTorch、`warp-lang` 等），而且 wheel 和操作系统、Python 版本、CUDA 版本都绑定。要在目标机器上离线安装，得在**同样系统和 Python 版本**的联网机器上把整套依赖下载好，再一起拷过去，思路和第 0 课相同，只是包多得多。

### 训练要多久：只说量级

可以核实的数字都来自具体的任务和显卡，换一个就不成立，只能当量级参考：

| 来源 | 任务 | 说法 |
|---|---|---|
| 资料包里的 MJX 教程 notebook | Humanoid 用 PPO 学跑 | 在 Tesla A100 上约 6 分钟 |
| 同上 | Barkour 四足，带域随机化 | 在 Tesla A100 上约 6 分钟 |
| `training_apg.ipynb`（可微仿真训练） | 四足模仿参考步态、学习行走 | 在 RTX 3060 Ti 上各约 15 分钟 |
| Playground 论文摘要 | 多种机器人 | 单块 GPU 上“几分钟内” |

所以合理的预期是：**一个调好的任务，在一块现代 NVIDIA 显卡上训练是“分钟到小时”的量级，而不是“天”**。真正花时间的是设计奖励、调参数、反复做 Sim2Sim 验证。第一次运行时 JIT 编译（JAX）或内核编译（Warp）也会多等一会儿，这是正常的。

吞吐量的量级也可以对比一下。官方 MJX 文档给过几组数字（用的是 MuJoCo 自带的 humanoid 模型，不是 G1）：

- 1 个 humanoid 场景，64 核 AMD 3995WX 上的 CPU 版 MuJoCo（线程数取核心数的 2 倍）约每秒 180 万步，A100 上的 MJX-JAX（批量 8192）约 95 万步。
- MJX-Warp 图模式对比表里，纯 Warp 跑 Humanoid 约每秒 335 万步。

对照 11.2 节在 8 核笔记本上测出的约 20 万步/秒：GPU 的优势要在**几千个环境同时跑**时才显现；而一台核数很多的 CPU，配合 `mujoco.rollout`，也能达到可观的吞吐量。

## 11.6 和本课程 CPU 仿真的关系

GPU 训练不是“另一套东西”，前面 10 课学的全都用得上：

- **模型是同一种 MJCF。** MJX 和 MJWarp 都先用 `mujoco.MjModel.from_xml_path` 编译模型，再用 `put_model` 拷到显卡上。第 1 课读 XML、第 3 课用 MjSpec 改模型的本事，原样有效。
- **API 一一对应。** `mj_step` 对应 `mjx.step` / `mjw.step`；`MjData` 的字段名不变，只是多了一个批量维度。第 1 课那张 `qpos` / `qvel` 排布表，在 GPU 上照样是你取数据的依据。
- **训练在 GPU，验证回到 CPU。** 训练用 float32、更大的步长、更少的求解器迭代；部署前要回到 float64 的 CPU 版 MuJoCo 里检验，这就是第 9 课的 Sim2Sim。第 9 课的推力测试、第 10 课的批量统计摔倒率，正是你将来检验自己策略的工具。
- **CPU 版本身也能批量。** 11.2 节用的 `mujoco.rollout` 就是 CPU 多线程批量仿真（入门教程 9.5 节）。官方文档也指出：在 CPU 仿真、GPU 学习的方案里，整体性能可能受限于主机和显卡之间的数据搬运。
- **实时控制留在 CPU。** 第 8 课的 LQR、将来想做的 MPC，追求的是单步延迟，CPU 版 MuJoCo 更合适。

两点建议：

- **每个阶段都要有“回到 CPU 验证”这一步。** GPU 上训练曲线好看，不代表策略在 float64、默认求解器参数下也能走。第 9 课的 Sim2Sim 就是在做这件事。
- **先复现，再修改。** 先用官方任务和默认参数跑通一次，确认环境没问题，再动奖励和模型。否则出了问题，你分不清是环境装错了还是改坏了。

## 练习

1. **测你自己的基线。** 运行 `code/11_model_variants.py` 两三次，记下 `g1.xml` 单线程和多线程的步数/秒。多线程比单线程快了几倍？和你的 CPU 线程数比，是“线性加速”吗？
2. **算一笔账。** 假设训练一个行走策略需要 10 亿个仿真步（这是一个假设的数字，只用来练习换算），按你测到的多线程吞吐量，光物理仿真就要跑多久？这还没算神经网络前向、反向传播的时间。
3. **对照功能表。** 打开官方文档 MJX 页面的“功能对等”表，检查 `g1_mjx.xml` 用到的特性（几何类型、`condim`、积分器、求解器）是否都在 MJX-JAX 的支持范围内。再看看 `g1.xml`：它的碰撞体主要是什么类型？按“锋利之处”一节的说法，这对 MJX-JAX 意味着什么？
4. **（有 NVIDIA 显卡时）找到吞吐量的拐点。** 用 `code/11_gpu_rollout.py --skip-cpu` 依次试 `--nworld` 1024、4096、16384、65536，记下步数/秒。规模翻倍时吞吐量还跟着涨吗？到哪里开始不涨，或者显存不够报错？
5. **读一读 `g1_mjlab.xml`。** 找到那 4 个 `<exclude>`，说说它们排除的是哪几对部件、为什么要排除。（提示：打开自碰撞以后，相邻、本来就挨着的部件会一直“碰”在一起）

## 如果报错

| 现象 | 可能原因 | 解决 |
|---|---|---|
| `AttributeError: module 'mujoco' has no attribute 'rollout'` 或 `No module named 'mujoco.rollout'` | `mujoco` 版本太旧或没装全 | 回第 0 课核对版本，脚本里用 `from mujoco import rollout` |
| 测速数字比文中小很多，或者每次差别很大 | 笔记本省电模式、后台程序占用 CPU、睿频变化 | 接上电源、选高性能模式、关掉其他程序，多跑几次取中间值 |
| 加载 `g1_mjlab.xml` 后仿真里什么都不动 | 它本来就没有执行器（`nu=0`）和地面 | 这是设计如此，执行器由 mjlab 用代码添加；只用它做对比 |
| （将来在 GPU 机器上）JAX 只认出 CPU，`jax.default_backend()` 打印 `cpu` | 装的是 CPU 版 JAX，或在 Windows 原生环境里 | 在 Linux 或 WSL2 里安装 CUDA 版 JAX |
| （将来）MJWarp 打印 `nconmax` / `njmax` 溢出警告 | 预留的接触/约束缓冲区不够 | 调大 `make_data` 的对应参数；用 `mjwarp-testspeed --measure_alloc` 看实际需要多少 |
| （将来）升级 MJWarp 后物理表现异常 | Warp 内核缓存与新代码不兼容 | 删除 `~/.cache/warp`，或 `wp.clear_kernel_cache()` |

**11.2 先猜一猜**：① 每秒步数只多了约 45%（35,482 对 24,508），但每步走 4 ms，所以仿真时间约快 2.9 倍。迭代上限从 100 降到 5，并不等于每步便宜 20 倍：站稳时 Newton 求解器本来就只需要很少几次迭代，一步的时间还有不少花在碰撞检测、动力学计算上。② 不是，示例里约 8.6 倍，原因见练习 1 的答案。③ 只有 `g1.xml` 还站着，`g1_mjx.xml` 1 到 2 秒内就倒了，原因见观察 3。

**11.2 观察 1**：三个版本的 body、关节一样（`nbody=31`、`nq=36`、`nv=35`），不同在于：碰撞（`g1.xml` 有 37 个可碰撞 geom、自动检测碰撞对；`g1_mjx.xml` 28 个、49 个显式 pair；`g1_mjlab.xml` 33 个、4 个 exclude）；求解器参数（`timestep`、`iterations`、`ls_iterations`）；执行器（29 / 29 / 0）；传感器（4 / 14 / 5）；关键帧（`stand` / `home`、`knees_bent` / 无）。

**观察 2**：`g1_mjx.xml` 的 `timestep=0.004`、`iterations=5`、`ls_iterations=8`。示例输出里单线程 35,482 对 24,508 步/秒，多了约 1.1 万步（约 45%）；实时倍数 141.9× 对 49.0×，约 2.9 倍。快的原因一是每步更便宜，二是步长翻倍，同样的步数覆盖两倍的仿真时间。不过它这时已经倒在地上，接触情况和站着时不同，这个对比只能看个大概。多线程时两者差不多（示例里 208,531 对 210,345），连跑 6 次谁快谁慢不固定，测速波动盖过了模型差别。

**观察 3**：README 写着 MJX 版本“用了更低、更真实的 PD 增益”（多数关节 kp=75，踝和腕只有 20，而 `g1.xml` 全是 500）。只靠这么软的 PD 保持关键帧的目标角，身体先往前倾，大约 1.5 秒内就倒下。脚本里的对照实验把 29 个 kp 全改成 500，其他都不动，10 秒后骨盆高度 0.784 m，仍然站着，说明主因就是增益。在 Playground 里，站稳和走路是策略的工作：它根据传感器不断调整目标角。这也是 `g1_mjx.xml` 多了 10 个传感器的原因（速度计、`framequat`、`framelinvel` 等），它们是给策略准备的观测。

**观察 4**：CHANGELOG 写明 `g1_mjlab.xml` 去掉了执行器和求解器选项，“以便程序化地指定”。mjlab 在训练代码里用 MjSpec 一类的方式加上执行器、设置步长和求解器、放地形。所以这份 XML 单独加载时，积分器回到 MuJoCo 的默认值 `EULER`。

**练习 1**：示例机器上，同一次运行里多线程和单线程之比在 7–10 倍之间（示例输出 210,345 ÷ 24,508 ≈ 8.6），达不到 16 倍。主要原因：这台机器的 16 个逻辑线程来自 8 个物理核心（超线程），真正能并行干活的核心只有 8 个；另外，多核同时满载时频率可能降低，线程池调度也有开销。

**练习 2**：按示例的 210,345 步/秒，10⁹ ÷ 210,345 ≈ 4,750 秒，约 1.3 小时；按 6 次里最低的 199,859 步/秒算约 5,000 秒，约 1.4 小时。这只是物理仿真，还没算策略网络前向、反向传播，以及 CPU 和 GPU 之间来回搬数据的时间。GPU 方案的意义在于：仿真和网络都在显卡上，几千个环境一起推进，数据不出显存。

**练习 3**：`g1_mjx.xml` 用的几何类型是 mesh（只做显示，不参与碰撞）、capsule、sphere、box、plane；`condim` 为 1 和 3；积分器 `implicitfast`、求解器 Newton、锥 pyramidal，都在 MJX-JAX 的支持列表里（`implicitfast` 只是不能和流体阻力一起用，G1 没用流体）。`g1.xml` 的碰撞体主要是 24 个网格（另有 4 个圆柱、8 个脚底小球）。“锋利之处”一节说 MJX-JAX 的凸网格碰撞用的是 SAT，对大网格在时间和内存上都吃力；功能表的脚注还写着，MJX-JAX 不支持圆柱和球、盒子、网格之间的碰撞。这就是要单独做一份手工碰撞体的 `g1_mjx.xml` 的原因。

**练习 4**：4 个 `<exclude>` 排除的是：左肘和左腕 pitch、右肘和右腕 pitch、骨盆和右髋 roll、骨盆和左髋 roll。脚本第 4 部分把它们删掉后，在全零的零位姿态下就出现 6 个接触：
