MuJoCo Warp (MJWarp)#

MuJoCo Warp (MJWarp) 是用 Warp 编写的 MuJoCo 实现，针对 NVIDIA 硬件和并行仿真进行了优化。MJWarp 位于 google-deepmind/mujoco_warp GitHub 仓库中。

MuJoCo Warp (MJWarp) is an implementation of MuJoCo written in Warp and optimized for NVIDIA hardware and parallel simulation. MJWarp lives in the google-deepmind/mujoco_warp GitHub repository.

MJWarp 由 NVIDIA 与 Google DeepMind 共同开发和维护。

MJWarp is developed and maintained as a joint effort by NVIDIA and Google DeepMind.

何时使用 MJWarp？#

When To Use MJWarp?

高吞吐量#

High throughput

MuJoCo 生态系统提供了多种批量仿真方案。

The MuJoCo ecosystem offers multiple options for batched simulation.

  • mujoco.rollout：用于在 CPU 上多线程调用 mj_step 的 Python API。使用核心速度快、线程数多的硬件可以实现高吞吐量，但对于需要频繁进行主机<>设备传输的应用（例如在 CPU 上仿真、在 GPU 上学习的强化学习），整体性能可能受限于传输开销。

    mujoco.rollout: Python API for multi-threaded calls to mj_step on CPU. High throughput can be achieved with hardware that has fast cores and large thread counts, but overall performance of applications requiring frequent host<>device transfers (e.g., reinforcement learning with simulation on CPU and learning on GPU) may be bottlenecked by transfer overhead.

  • mjx.step： jax.vmap 和 jax.pmap 使得可以借助 JAX 在 CPU、GPU 或 TPU 上进行多线程和多设备仿真。

    mjx.step: jax.vmap and jax.pmap enable multi-threaded and multi-device simulation with JAX on CPUs, GPUs, or TPUs.

  • mujoco_warp.step：面向 NVIDIA GPU 的高吞吐量仿真 Python API。几乎在所有工作负载上都比 MJX 扩展性更好，尤其是复杂的仿真场景。与 PyTorch 配合良好。

    mujoco_warp.step: Python API for high throughput simulation targeting NVIDIA GPUs. Scales better than MJX on nearly every workload, in particular complex simulation scenes. Works well with PyTorch.

低延迟#

Low latency

MJWarp 针对吞吐量进行了优化，即单位时间内仿真步数的总量；而 MuJoCo 针对延迟进行了优化，即一个仿真步所需的时间。可以预期，对于同一仿真，MJWarp 的单个仿真步性能不如 MuJoCo 的单步。

MJWarp is optimized for throughput: the total number of simulation steps per unit time whereas MuJoCo is optimized for latency: time for one simulation step. It is expected that a simulation step with MJWarp will be less performant than a step with MuJoCo for the same simulation.

因此，MJWarp 非常适合需要大量样本的应用，如强化学习；而 MuJoCo 可能更适用于实时应用，如在线控制（例如模型预测控制）或交互式图形界面（例如基于仿真的遥操作）。

As a result, MJWarp is well suited for applications where large numbers of samples are required, like reinforcement learning, while MuJoCo is likely more useful for real-time applications like online control (e.g., model predictive control) or interactive graphical interfaces (e.g., simulation-based teleoperation).

复杂场景#

Complex scenes

对于含有许多 geom 或自由度（degrees of freedom）的场景，MJWarp 的扩展性优于 MJX，但对于单个大型运动学树（kinematic tree），则不如 MuJoCo。只要启用了 休眠，并且场景可以划分为含有休眠刚体（body）的独立岛，MJWarp 就可以扩展到含有数百个自由度的场景。将单个连通机构的性能提升到约 60 个自由度以上，仍是当前的优先事项。

MJWarp scales better than MJX for scenes with many geoms or degrees of freedom, but not as well as MuJoCo for single large kinematic trees. MJWarp can scale to scenes with hundreds of degrees of freedom as long as sleeping is enabled and the scene can be partitioned into independent islands with dormant bodies. Improving performance for single connected mechanisms beyond ~60 DoFs remains an active priority.

可微性#

Differentiability

MJX 中的动力学（dynamics）API 可通过 JAX 自动微分。我们正在考虑是否通过 Warp 在 MJWarp 中支持这一功能——如果该功能对您很重要，请在 这个 issue 中表达您的意见。

The dynamics API in MJX is automatically differentiable via JAX. We are considering whether to support this in MJWarp via Warp - if this feature is important to you, please chime in on this issue here.

基本用法#

Basic Usage

安装完成后，可以通过 import mujoco_warp as mjw 导入该包。结构体、函数和枚举可直接从顶层 mjw 模块获得。

Once installed, the package can be imported via import mujoco_warp as mjw. Structs, functions, and enums are available directly from the top-level mjw module.

结构体#

Structs

在 NVIDIA GPU 上运行 MJWarp 函数之前，必须通过 mjw.put_model 以及 mjw.make_data 或 mjw.put_data 函数将结构体复制到设备上。将 mjModel 放到设备上会得到 mjw.Model。将 mjData 放到设备上会得到 mjw.Data。

Before running MJWarp functions on an NVIDIA GPU, structs must be copied onto the device via mjw.put_model and mjw.make_data or mjw.put_data functions. Placing an mjModel on device yields an mjw.Model. Placing an mjData on device yields an mjw.Data.
mjm = mujoco.MjModel.from_xml_string("...")
mjd = mujoco.MjData(mjm)
m = mjw.put_model(mjm)
d = mjw.put_data(mjm, mjd)

这些 MJWarp 版本与对应的 MuJoCo 结构体相似，但有几个关键区别：

These MJWarp variants mirror their MuJoCo counterparts but have a few key differences:

  1. mjw.Model 和 mjw.Data 包含已复制到设备上的 Warp 数组。

    mjw.Model and mjw.Data contain Warp arrays that are copied onto device.

  2. 由于某些功能不受支持，mjw.Model 和 mjw.Data 中缺少部分字段。

    Some fields are missing from mjw.Model and mjw.Data for features that are unsupported.

批大小#

Batch sizes

MJWarp 针对并行仿真进行了优化。一批仿真可以用三个参数指定：

MJWarp is optimized for parallel simulation. A batch of simulations can be specified with three parameters:

  • nworld ：要仿真的世界（world）数量。

    nworld: Number of worlds to simulate.

  • nconmax：每个世界的预期接触（contact）数。所有世界的最大接触数为 nconmax * nworld 。

    nconmax: Expected number of contacts per world. The maximum number of contacts for all worlds is nconmax * nworld.

  • naconmax：作为 nconmax 的替代，为所有世界的最大接触数。如果同时设置了 nconmax 和 naconmax，则忽略 nconmax。

    naconmax: Alternative to nconmax, maximum number of contacts over all worlds. If nconmax and naconmax are both set then nconmax is ignored.

  • njmax：每个世界的最大约束（constraint）数。

    njmax: Maximum number of constraints per world.

nconmax 和 njmax 的语义差异。

Semantic difference for nconmax and njmax.

只要所有世界的接触总数不超过 nworld x nconmax ，每个世界的接触数就可能超过 nconmax。然而，每个世界的约束数受 njmax 严格限制。

It is possible for the number of contacts per world to exceed nconmax if the total number of contacts for all worlds does not exceed nworld x nconmax. However, the number of constraints per world is strictly limited by njmax.

XML 解析

XML parsing

nconmax 和 njmax 的值不会从 size/nconmax 和 size/njmax 解析得到（这些参数已弃用）。这些参数的值必须提供给 mjw.make_data 或 mjw.put_data。

Values for nconmax and njmax are not parsed from size/nconmax and size/njmax (these parameters are deprecated). Values for these parameters must be provided to mjw.make_data or mjw.put_data.

函数#

Functions

MuJoCo 函数以同名的 MJWarp 函数形式提供，但名称遵循符合 PEP 8 规范的命名风格。主仿真 的大部分函数以及用于正向仿真的 子组件 中的一部分函数，可从顶层 mjw 模块获得。

MuJoCo functions are exposed as MJWarp functions of the same name, but following PEP 8-compliant names. Most of the main simulation and some of the sub-components for forward simulation are available from the top-level mjw module.

最小示例#

Minimal example
# Throw a ball at 100 different velocities.

import mujoco
import mujoco_warp as mjw
import warp as wp

_MJCF=r"""
<mujoco>
  <worldbody>
    <body>
      <freejoint/>
      <geom size=".15" mass="1" type="sphere"/>
    </body>
  </worldbody>
</mujoco>
"""

mjm = mujoco.MjModel.from_xml_string(_MJCF)
m = mjw.put_model(mjm)
d = mjw.make_data(mjm, nworld=100)

# initialize velocities
wp.copy(d.qvel, wp.array([[float(i) / 100, 0, 0, 0, 0, 0] for i in range(100)], dtype=float))

# simulate physics
mjw.step(m, d)

print(f'qpos:\n{d.qpos.numpy()}')

功能对等#

Feature Parity

MJWarp 支持 MuJoCo 的大部分主要仿真功能，但有少数例外。如果要求将字段值引用了不受支持功能的 mjModel 复制到设备，MJWarp 会抛出异常。关于最新的功能可用性，请参见 MuJoCo API 兼容性。

性能调优#

Performance Tuning

以下是优化 MJWarp 性能时的一些注意事项。

The following are considerations for optimizing the performance of MJWarp.

图捕获#

Graph capture

MJWarp 函数（例如 mjw.step）通常由一组内核启动组成。如果直接调用函数，Warp 会逐个启动这些内核。为提高性能，尤其是函数将被多次调用时，建议将构成该函数的操作捕获为 CUDA 图

MJWarp functions, for example mjw.step, often comprise a collection of kernel launches. Warp will launch these kernels individually if the function is called directly. To improve performance, especially if the function will be called multiple times, it is recommended to capture the operations that comprise the function as a CUDA graph
with wp.ScopedCapture() as capture:
  mjw.step(m, d)

随后可以启动或重新启动该图

The graph can then be launched or re-launched
wp.capture_launch(capture.graph)

并且与直接调用该函数相比，通常会显著更快。详情请参见 Warp 图 API 参考。

and will typically be significantly faster compared to calling the function directly. Please see the Warp Graph API reference for details.

批大小#

Batch sizes

接触数和约束数的最大值，分别为 nconmax / naconmax 和 njmax，在使用 mjw.make_data 或 mjw.put_data 创建 mjw.Data 时指定。内存和计算量随这些参数的取值而增长。为获得最佳性能，这些参数的值应在确保仿真不超出这些限制的前提下尽可能小。

The maximum numbers of contacts and constraints, nconmax / naconmax and njmax respectively, are specified when creating mjw.Data with mjw.make_data or mjw.put_data. Memory and computation scales with the values of these parameters. For best performance, the values of these parameters should be set as small as possible while ensuring the simulation does not exceed these limits.

可以预期，这些限制的合适取值与具体环境相关。在实践中，选择合适的值通常需要反复试验。带有 --measure_alloc 标志（用于在每个仿真步打印接触数和约束数）和 --overflow_behavior=error （默认，用于检测溢出）的 mjwarp-testspeed ，以及通过 溢出检测 进行的程序化检查，都是迭代测试这些参数取值的有用手段。

It is expected that good values for these limits will be environment specific. In practice, selecting good values typically involves trial-and-error. mjwarp-testspeed with the flag --measure_alloc for printing the number of contacts and constraints at each simulation step, --overflow_behavior=error (default) for detecting overflows, and programmatic inspection via Overflow detection can all be useful techniques for iteratively testing values for these parameters.

求解器迭代次数#

Solver iterations

MuJoCo 对 求解器迭代次数 和 线搜索迭代次数 最大值的默认求解器（solver）设置预计能提供合理的性能。减小 MJWarp 的 Option.iterations 和/或 Option.ls_iterations 限制可能会提升性能，应当在调好 nconmax / naconmax 和 njmax 之后再作为次要考虑。

MuJoCo’s default solver settings for the maximum numbers of solver iterations and linesearch iterations are expected to provide reasonable performance. Reducing MJWarp’s settings Option.iterations and/or Option.ls_iterations limits may improve performance and should be secondary considerations after tuning nconmax / naconmax and njmax.

过度减小这些限制可能导致约束求解器无法收敛，并可能造成仿真不准确或不稳定。

Reducing these limits too much may prevent the constraint solver from converging and can lead to inaccurate or unstable simulation.

对性能的影响：MJX (JAX) 与 MJWarp

Impact on Performance: MJX (JAX) and MJWarp

在 MJX 中，这些求解器参数是控制仿真性能的关键。与之相比，在 MJWarp 中，一旦所有世界都已收敛，求解器就可以提前退出，避免不必要的计算。因此，这些设置的取值对性能的影响相对较小。

In MJX these solver parameters are key for controlling simulation performance. With MJWarp, in contrast, once all worlds have converged the solver can early exit and avoid unnecessary computation. As a result, the values of these settings have comparatively less impact on performance.

接触传感器匹配#

Contact sensor matching

包含 接触传感器 的场景有一个参数，用于指定每个传感器（sensor）的最大匹配接触数 Option.contact_sensor_max_match 。为获得最佳性能，该参数的值应在确保仿真不超出该限制的前提下尽可能小。超出该限制的匹配接触将被忽略。

Scenes that include contact sensors have a parameter that specifies the maximum number of matched contacts per sensor Option.contact_sensor_max_match. For best performance, the value of this parameter should be as small as possible while ensuring the simulation does not exceed the limit. Matched contacts that exceed this limit will be ignored.

该参数的值可以直接设置，例如 model.opt.contact_sensor_maxmatch = 16 ，也可以通过 XML 自定义数值字段设置

The value of this parameter can be set directly, for example model.opt.contact_sensor_maxmatch = 16, or via an XML custom numeric field
<custom>
  <numeric name="contact_sensor_maxmatch" data="16"/>
</custom>

与接触数和约束数的最大值类似，该设置的合适取值预计也与具体环境相关。 mjwarp-testspeed 和 mjwarp-viewer 可能有助于调整该参数的值。

Similar to the maximum numbers of contacts and constraints, a good value for this setting is expected to be environment specific. mjwarp-testspeed and mjwarp-viewer may be useful for tuning the value of this parameter.

内存#

Memory

仿真吞吐量常常受限于大量世界所需的内存。优化内存使用的考虑因素包括：

Simulation throughput is often limited by memory requirements for large numbers of worlds. Considerations for optimizing memory utilization include:

  • CCD 碰撞器比基元碰撞器需要更多内存，有关碰撞器的信息请参见 成对碰撞器表。

    CCD colliders require more memory than primitive colliders, see the pair-wise colliders table for information about colliders.

  • multiccd 比 CCD 需要更多内存。

    multiccd requires more memory than CCD.

  • CCD 的内存需求随 Option.ccd_iterations 线性增长。

    CCD memory requirements scale linearly with Option.ccd_iterations.

  • 至少含有一个网格（mesh）geom 并使用 multiccd 的场景，其内存需求随每个面的最大顶点数以及每个顶点的最大边数线性增长，这两个最大值是在所有网格上计算得到的。

    A scene with at least one mesh geom and using multiccd will have memory requirements that scale linearly with the maximum number of vertices per face and with the maximum number of edges per vertex, computed over all meshes.

testspeed 提供 --memory 标志，用于报告仿真的总内存使用量，以及需要大量内存的 mjw.Model 和 mjw.Data 字段的信息。内联分配的内存（包括用于 CCD 和约束求解器的内存）也可能很可观，并作为 Other memory 报告。

testspeed provides the flag --memory for reporting a simulation’s total memory utilization and information about mjw.Model and mjw.Data fields that require significant memory. Memory allocated inline, including for CCD and the constraint solver, can also be significant and is reported as Other memory.

每个碰撞器的最大接触数

Maximum number of contacts per collider

部分 MJWarp 碰撞器的最大接触数与 MuJoCo 不同 (参见 成对碰撞器表)：

Some MJWarp colliders have a different maximum number of contacts compared to MuJoCo (see the pair-wise colliders table):

  • PLANE<>MESH ：4 对 3

    PLANE<>MESH: 4 versus 3

  • HFieldCCD ：4 对 mjMAXCONPAIR

    HFieldCCD: 4 versus mjMAXCONPAIR

稀疏雅可比（Jacobian）(例如 efc.J, ten_J, flexedge_J 和 actuator_moment) 仅存储可能非零的元素，从而减少内存并跳过零运算。对于高自由度场景（\(n_v > 60\)），稀疏性使得原本在稠密模式下不受支持的仿真成为可能。例如，在 Aloha clutter 基准测试（\(n_v = 136\)，2048 个世界， njmax = 384 ）中， efc.J 及其列索引 efc.J_colind 的稀疏表示合计需要约 84 MB（各约 42 MB），而稠密 efc.J 约需 408 MB，内存减少约 4 倍。

Sparse Jacobians (e.g., efc.J, ten_J, flexedge_J, and actuator_moment) store only potentially non-zero entries, reducing memory and skipping zero arithmetic. For high-DoF scenes (\(n_v > 60\)), sparsity enables simulations that are unsupported in dense mode. For example, in the Aloha clutter benchmark (\(n_v = 136\), 2048 worlds, njmax = 384), the sparse representation of efc.J and its column indices efc.J_colind requires ~84 MB combined (~42 MB each) compared to ~408 MB for dense efc.J, a +4x reduction in memory.

mjw.make_data 或 mjw.put_data 的参数 nccdmax / naccdmax 可以设置为小于 nconmax / naconmax 的值，以减少 CCD 的内存需求。该参数的值应分别为每个世界或所有世界中 CCD 碰撞器产生的最大接触数。例如，一个含 10 个世界、共产生 80 个接触的批量仿真，其各碰撞器的接触数为：mesh-mesh：30（CCD），ellipsoid-ellipsoid：10（CCD），sphere-sphere：40 （基元），则应将 nconmax / naconmax 设为至少 8 / 80（粗测阶段可能需要更多），并将 nccdmax / naccdmax 设为 3 / 30。

The mjw.make_data or mjw.put_data argument nccdmax / naccdmax can be set to a value less than nconmax / naconmax in order to reduce the memory requirements for CCD. The value for this parameter should be the maximum number of contacts generated by a CCD collider, per world or for all worlds, respectively. For example, a batched simulation with 10 worlds that generates 80 total contacts with per-collider contacts: mesh-mesh: 30 (CCD), ellipsoid-ellipsoid: 10 (CCD), and sphere-sphere: 40 (primitive) should set nconmax / naconmax to at least 8 / 80 (may require more for broadphase) and nccdmax / naccdmax to 3 / 30.

大型场景#

Large scenes

仿真具有许多自由度（即 nv ）的场景，计算开销可能很大。然而，在许多情形下，场景中相当一部分可能是静止的。MJWarp 可以使静止物体进入 休眠 （参见 休眠岛），将它们排除在许多计算的工作集之外。此外，MJWarp 将刚体分组为独立的 岛；如果某个岛中的所有刚体都静止，则整个岛进入休眠。目前，碰撞流水线和约束求解器都受益于休眠，将来可能会加入更多能感知休眠的组件。

Simulating scenes with many DoFs (i.e., nv) can be computationally expensive. However, in many scenarios, a significant portion of the scene may be stationary. MJWarp can put stationary objects to sleep (see Sleeping islands), excluding them from the working set of many of its calculations. Furthermore, MJWarp groups bodies into independent islands; if all bodies in an island are stationary, the entire island is put to sleep. Currently, both the collision pipeline and the constraint solver benefit from sleeping, and more sleeping-aware components may be added in the future.

紧凑求解器#

Compact solver

为了优化总自由度很多但活跃自由度相对较少（通常少于 64 个，例如两个带夹爪的机械臂（16 个自由度）加 8 个活跃物体（48 个自由度））的场景的性能，MJWarp 提供了利用该休眠机制的 紧凑求解器：

To optimize performance in scenes with many total DoFs but a relatively small number of active DoFs (typically fewer than 64, such as two robot arms with grippers (16 DoFs) and 8 active objects (48 DoFs)), MJWarp provides a compact solver that leverages this sleeping mechanism:

  1. 确定每个世界的活跃自由度集合，由活跃的岛决定。

    Identifies the set of active DOFs for each world, determined from the active islands.

  2. 将这些活跃自由度 压缩 到一个大小已知的最大值（ nvmax ）的连续稠密工作区中。

    Compacts these active DOFs into a single, contiguous dense workspace of a known maximum size (nvmax).

  3. 在该压缩空间上，使用针对 GPU 优化的固定大小 tile 运算（如分块 Cholesky 分解）执行约束求解器（Newton）。

    Executes the constraint solver (Newton) using GPU-optimized tile operations (such as blocked Cholesky factorization) of fixed size on this compacted space.

  4. 将结果散射回全局状态，冻结不活跃的自由度。

    Scatters the results back to the global state, freezing the inactive DOFs.

通过使用固定大小的压缩工作区，求解器避免了 GPU 线程发散，并利用了针对固定 tile 大小优化的高性能张量/矩阵运算。

By using a fixed-size compacted workspace, the solver avoids GPU thread divergence and leverages high-performance tensor/matrix operations optimized for fixed tile sizes.

溢出检测#

Overflow detection

MJWarp 依赖固定大小的缓冲区分配 (nconmax / naconmax, njmax, nccdmax / naccdmax, nvmax, Option.contact_sensor_maxmatch) 来实现高吞吐量的 GPU 执行。当仿真需求超出这些预分配的限制时，就会发生溢出，导致未定义行为。

MJWarp relies on fixed-size buffer allocations (nconmax / naconmax, njmax, nccdmax / naccdmax, nvmax, Option.contact_sensor_maxmatch) for high-throughput GPU execution. When simulation demands exceed these pre-allocated limits, an overflow occurs, leading to undefined behavior.

MJWarp 按世界在 Data.overflow 中跟踪溢出，它是形状为 (nworld,) 的一维 Warp 数组，存储 mjw.OverflowType 的位掩码。

MJWarp tracks overflows per world in Data.overflow, a 1D Warp array of shape (nworld,) storing bitmasks of mjw.OverflowType.

Data.overflow 在创建时初始化为零，并在 mjw.reset_data 时清零。

Data.overflow is initialized to zero upon creation and cleared on mjw.reset_data.

以编程方式检查溢出

Checking for overflows programmatically
mjw.step(m, d)

# device-to-host transfer
overflow = d.overflow.numpy()

# check worlds for any overflow
any_overflow = np.any(overflow != 0)

# check for each world for (narrowphase) contact overflow
has_contact_overflow = (overflow & mjw.OverflowType.NARROWPHASE) != 0

控制警告

Controlling warnings

默认情况下， Option.warn_overflow 为 True ，这会使内核在发生溢出时通过 wp.printf 向标准输出打印警告消息。设置 m.opt.warn_overflow = False 会抑制这些 GPU 端的警告打印，同时仍会在 Data.overflow 中记录溢出位掩码。

By default, Option.warn_overflow is True, causing kernels to print warning messages to stdout via wp.printf when an overflow occurs. Setting m.opt.warn_overflow = False suppresses these GPU-side warning prints while still recording the overflow bitmasks in Data.overflow.

在 testspeed 中，命令行标志 --overflow_behavior=error （默认）会自动检查 Data.overflow ，并在任何世界溢出时以诊断错误中止；而 --overflow_behavior=continue 则允许在启用警告的情况下继续执行。

In testspeed, the command-line flag --overflow_behavior=error (default) automatically checks Data.overflow and aborts with a diagnostic error if any world overflows, while --overflow_behavior=continue allows execution to proceed with warnings enabled.

性能影响

Performance implications

  • 设备端 printf 开销：从 GPU 内核打印警告 (m.opt.warn_overflow = True) 会使各线程的执行串行化，引入 CUDA 设备同步，并且在许多并行世界溢出时会严重降低仿真吞吐量。禁用警告 (m.opt.warn_overflow = False) 可消除这种 GPU I/O 开销。

    Device printf overhead: Printing warnings from GPU kernels (m.opt.warn_overflow = True) serializes execution across threads, introduces CUDA device synchronizations, and can severely degrade simulation throughput when many parallel worlds overflow. Disabling warnings (m.opt.warn_overflow = False) eliminates this GPU I/O overhead.

  • 主机-设备同步：通过 d.overflow.numpy() 在 CPU 上读取 Data.overflow 需要进行设备到主机的内存复制和流水线同步。在高吞吐量的强化学习流水线中，应避免在每个仿真步都进行同步；而应定期（例如在环境重置或 rollout 边界处）检查 Data.overflow，或直接在设备上检查该张量。

    Host-device synchronization: Reading Data.overflow on CPU via d.overflow.numpy() requires a device-to-host memory copy and pipeline synchronization. In high-throughput reinforcement learning pipelines, avoid synchronizing on every simulation step; instead, check Data.overflow periodically (e.g., at environment reset or rollout boundaries) or inspect the tensor directly on device.

  • 仿真保真度：如果禁用了警告且没有检查 Data.overflow ，溢出将导致未定义行为。

    Simulation fidelity: If warnings are disabled and Data.overflow is not checked, overflows will lead to undefined behavior.

批量化的 Model 字段#

Batched Model Fields

为了支持使用不同模型（model）参数值的批量仿真，许多 mjw.Model 字段带有前导批维度。默认情况下，前导维度为 1（即 field.shape[0] == 1 ），并且相同的值会应用于所有世界。可以按字段设置批大小

To enable batched simulation with different model parameter values, many mjw.Model fields have a leading batch dimension. By default, the leading dimension is 1 (i.e., field.shape[0] == 1) and the same value(s) will be applied to all worlds. It is possible to set batch sizes per field
m = mjw.put_model(mjm, batch_sizes={"dof_damping": 2})
m.dof_damping.assign(np.array([[0.1], [0.2]], dtype=float))

然后覆盖默认值。批量化字段将通过世界 id 与批维度的取模运算来索引： field[worldid % field.shape[0]] 。

and then override the default values. Batched fields will be indexed with a modulo operation of the world id and batch dimension: field[worldid % field.shape[0]].

修改字段#

Modifying fields

修改 mjModel 字段的推荐工作流程是：先修改对应的 mjSpec，再编译以创建带有更新字段的新 mjModel。然而，编译目前需要主机调用：每个新的字段实例需要 1 次调用，即 nworld 个实例需要 nworld 次主机调用。

The recommended workflow for modifying an mjModel field is to first modify the corresponding mjSpec and then compile to create a new mjModel with the updated field. However, compilation currently requires a host call: 1 call per new field instance, i.e., nworld host calls for nworld instances.

某些字段可以安全地直接修改而无需编译，从而实现设备上的更新。有关具体字段的详细信息，请参见 mjModel 的变更。此外，GitHub issue 893 跟踪了为部分字段添加设备上更新的工作。

Certain fields are safe to modify directly without compilation, enabling on-device updates. Please see mjModel changes for details about specific fields. Additionally, GitHub issue 893 tracks adding on-device updates for a subset of fields.

按世界划分的资产（Per-world assets）#

Per-world assets

按世界划分的资产（per-world assets）支持异构世界，即不同的世界仿真不同的 资产，包括网格（mesh）、高度场、材质和纹理。通用工作流程如下：

Per-world assets enable heterogeneous worlds where different worlds simulate different assets including meshes, height fields, materials, and textures. The general workflow is:

  1. 创建包含 全部 资产的 mjSpec。

    Create an mjSpec with all assets.

  2. 通过修改 spec 并调用 spec.compile() 来编译每个变体。

    Compile each variant by mutating the spec and calling spec.compile().

  3. 编译一个 基础 模型，并由它创建 mjw.Model。

    Compile a base model and create mjw.Model from it.

  4. 用由已编译变体构建的按世界划分的数组，覆盖 mjw.Model 的相关字段。

    Override the relevant mjw.Model fields with per-world arrays built from the compiled variants.

3D 高斯泼溅（3D Gaussian Splatting，3DGS）#

3D Gaussian Splatting (3DGS)

MJWarp 支持渲染 3D 高斯泼溅（3DGS）场景，并将其与仿真的 MuJoCo 物理对象合成。泼溅点通过专用的、以 SAH 构建的 BVH（build_splat_bvh）进行光线追踪，并沿每条光线使用单次命中的平面切片近似来求值。

MJWarp supports rendering 3D Gaussian Splatting (3DGS) scenes composited with simulated physical MuJoCo objects. Splats are raytraced via a dedicated SAH-constructed BVH (build_splat_bvh) and evaluated using a single-hit planar slice approximation along each ray.

物理遮挡#

Physical Occlusion

泼溅点在与 MuJoCo 实体几何求交 之前 进行光线追踪和 alpha 合成。如果相机光线击中了某个物理刚体（例如网格、基本几何体或 flex），则位于命中距离（dist）之后的泼溅点会被该物理对象遮挡，而位于命中距离之前的泼溅点则会混合叠加在该物理对象的表面颜色之上。

Splats are raytraced and alpha-composited prior to solid MuJoCo geometry intersection. If a camera ray hits a physical body (such as a mesh, primitive, or flex), splats located behind the hit distance (dist) are occluded by the physical object, while splats in front of the hit distance are blended over the physical object’s surface color.

性能与光线投射阈值#

Performance & Raycasting Thresholds

  • BVH 响应截断：泼溅点的包围盒大小被设定为能够容纳低至 SPLAT_MIN_RESPONSE = 0.01 的密度响应。

    BVH Response Cutoff: Splat bounding boxes are sized to contain density responses down to SPLAT_MIN_RESPONSE = 0.01.

  • 有界合成：光线投射对每条光线最多累积按深度排序的前 _MAX_SPLAT_HITS = 32 次 BVH 相交。

    Bounded Compositing: Raycasting accumulates up to the first _MAX_SPLAT_HITS = 32 BVH intersections per ray ordered by depth.

  • 提前终止：一旦剩余的光线透射率降到 0.005 以下，或单个泼溅点的 alpha 低于 8 位量化精度（1 / 255），合成就会提前停止。

    Early Termination: Compositing stops early once remaining ray transmittance drops below 0.005 or individual splat alpha is below 8-bit quantization (1 / 255).

为什么没有发生碰撞时仍会报告接触？

Why are contacts reported when there are no collisions?

对于任何一个参与了某个碰撞传感器的唯一 geom 对，即使该 geom 对并未发生碰撞，也会报告 1 个接触。在 MuJoCo 或 MJX 中，碰撞传感器 在计算传感器数据时会单独调用碰撞例程；与之不同，MJWarp 在运行其主碰撞流水线的同时，就在接触中计算并存储这些传感器的数据。

1 contact will be reported for each unique geom pair that contributes to any collision sensor, even if this geom pair is not in collision. Unlike MuJoCo or MJX where collision sensors make separate calls to collision routines while computing sensor data, MJWarp computes and stores the data for these sensors in contacts while running its main collision pipeline.

接触传感器 会对影响物理的接触报告正确的信息。

Contact sensors will report the correct information for contacts affecting the physics.

为什么有些数组的形状与 mjModel 或 mjData 中的不同？

Why do some arrays have different shapes compared to mjModel or mjData?

对于批量仿真，默认情况下许多 mjw.Data 字段带有一个前导的批量维度，其大小为 Data.nworld 。一些 mjw.Model 字段带有一个大小为 1 的前导批量维度，表示该 字段可以被一个批量参数数组覆盖，以实现域随机化。

By default for batched simulation, many mjw.Data fields having a leading batch dimension of size Data.nworld. Some mjw.Model fields having a leading batch dimension with size 1, indicating that this field can be overridden with an array of batched parameters for domain randomization.

此外，包括 Model.M 、 Data.efc.J 和 Data.efc.D 在内的某些字段经过了填充，以便在 GPU 上快速加载。

Additionally, certain fields including Model.M, Data.efc.J, and Data.efc.D are padded to enable fast loading on GPU.

为什么 MJWarp 与 MuJoCo 的数值结果不同？

Why are numerical results from MJWarp and MuJoCo different?

MJWarp 使用单精度 float32，而 MuJoCo 对 mjtNum 默认使用双精度（float64）表示。求解器（solver）设置，包括迭代次数、碰撞检测和较小的摩擦值，可能对浮点表示的差异比较敏感。

MJWarp utilizes single precision float32 in contrast to MuJoCo’s default double precision (float64) representation for mjtNum. Solver settings, including iterations, collision detection, and small friction values may be sensitive to differences in floating point representation.

如果遇到意外结果，包括 NaN，请提交 GitHub issue。

If you encounter unexpected results, including NaNs, please open a GitHub issue.

For programmatic inspection of these overflow conditions, check Data.overflow and mjw.OverflowType. To suppress stdout warning prints during high-throughput runs, set Option.warn_overflow to False. See Overflow detection for details.

与 MuJoCo 的差异#

Differences from MuJoCo

本节记录 MJWarp 与 MuJoCo 之间的差异。

This section notes differences between MJWarp and MuJoCo.

热启动#

Warmstart

如果热启动（warmstart）没有被 禁用，MJWarp 求解器的热启动总是用 qacc_warmstart 来初始化加速度。相比之下，MuJoCo 会对 qacc_smooth 和 qacc_warmstart 进行比较，以确定使用哪一个来初始化。

If warmstarts are not disabled, the MJWarp solver warmstart always initializes the acceleration with qacc_warmstart. In contrast, MuJoCo performs a comparison between qacc_smooth and qacc_warmstart to determine which one is utilized for the initialization.

惯性矩阵分解#

Inertia matrix factorization

MJWarp 对存储在 qLD 中的惯性矩阵（inertia matrix）逐树进行分解，并根据树的大小，决定采用 Warp 的 U'U Cholesky 分解 wp.tile_cholesky、MuJoCo 的稀疏逆序 L'DL 例程，还是简单的对角求逆例程。

MJWarp performs a per-tree factorization of the inertia matrix that is stored in qLD where the size of the tree determines if Warp’s U'U Cholesky factorization wp.tile_cholesky, MuJoCo’s sparse reverse-mode L'DL routine, or a simple diagonal inverse routine is employed.

SDF 插件#

SDF plugins

SDF 碰撞支持插件（plugin）。下面针对 plugin/sdf/bowl.xml 的示例，说明了如何实现 bowl.cc 中的 SDF 插件：

SDF collisions support plugins. The following example for plugin/sdf/bowl.xml illustrates how to implement the SDF plugin implementation in bowl.cc:
import mujoco_warp as mjw
import warp as wp

# distance function
@wp.func
def bowl(p: wp.vec3, attr: wp.vec3) -> float:
  """Signed distance function for a bowl shape.

  attr[0] = height
  attr[1] = radius
  attr[2] = thickness
  """
  height = attr[0]
  radius = attr[1]
  thick = attr[2]
  width = wp.sqrt(radius * radius - height * height)

  # q = (norm_xy(p), p.z)
  q0 = wp.sqrt(p[0] * p[0] + p[1] * p[1])
  q1 = p[2]

  # qdiff = q - (width, height)
  qdiff0 = q0 - width
  qdiff1 = q1 - height

  if height * q0 < width * q1:
    dist = wp.sqrt(qdiff0 * qdiff0 + qdiff1 * qdiff1)
  else:
    q_norm = wp.sqrt(q0 * q0 + q1 * q1)
    dist = wp.abs(q_norm - radius)

  return dist - thick


# gradient of distance function
@wp.func
def bowl_sdf_grad(p: wp.vec3, attr: wp.vec3) -> wp.vec3:
  """Gradient of bowl SDF via finite differences."""
  eps = float(1e-6)
  f0 = bowl(p, attr)

  px = wp.vec3(p[0] + eps, p[1], p[2])
  py = wp.vec3(p[0], p[1] + eps, p[2])
  pz = wp.vec3(p[0], p[1], p[2] + eps)

  grad = wp.vec3(
    (bowl(px, attr) - f0) / eps,
    (bowl(py, attr) - f0) / eps,
    (bowl(pz, attr) - f0) / eps,
  )
  return grad


# register the bowl SDF plugin
@wp.func
def user_sdf(p: wp.vec3, attr: wp.vec3, sdf_type: int) -> float:
  return bowl(p, attr)


@wp.func
def user_sdf_grad(p: wp.vec3, attr: wp.vec3, sdf_type: int) -> wp.vec3:
  return bowl_sdf_grad(p, attr)


# override the module-level hooks
mjw._src.collision_sdf.user_sdf = user_sdf
mjw._src.collision_sdf.user_sdf_grad = user_sdf_grad

盒-盒碰撞#

Box-box collisions

默认情况下，盒-盒碰撞使用通用凸体碰撞流水线（GJK/EPA）。通过设置 NATIVECCD 禁用标志，可以使用基于 engine_collision_box.c 的专用基本碰撞器：

By default, box-box collisions use the general-purpose convex collision pipeline (GJK/EPA). A specialized primitive collider based on engine_collision_box.c is available by setting the NATIVECCD disable flag:
m.opt.disableflags |= mjw.DisableBit.NATIVECCD

该专用碰撞器最多生成 8 个接触点，而凸体流水线最多生成 4 个，并且可能提高涉及盒体堆叠或操作的任务的接触稳定性。

The specialized collider generates up to 8 contact points, compared to up to 4 for the convex pipeline, and may improve contact stability for tasks involving box stacking or manipulation.
