第 10 课　录视频、批量做实验

对应入门教程：6.4、9.5

本课目标

  • 用 mujoco.Renderer 离屏渲染，把 G1 被推倒的过程录成 MP4；分清跟踪相机和自由相机。
  • 在画面上叠加自己的标记（推力箭头）。
  • 设计一个批量实验：随机方向、随机大小、随机时刻推 G1 几百次，画出“摔倒率—推力”曲线。
  • 用多进程和 mujoco.batch 两种办法并行加速，比较耗时，并确认结果逐位相同。
  • 搞清楚随机种子和可复现：同一个种子，在同一台机器、同一个 MuJoCo 版本上，结果一个比特都不差。

预计用时：2–2.5 小时　前置：第 2 课（关键帧、position 执行器）、第 5 课（用 xfrc_applied 推它）

10.2 离屏渲染：从 MjData 到一张图

mujoco.Renderer 在后台建一个看不见的画布，每次调用返回一张 NumPy 图像。三步走：

with mujoco.Renderer(m, height=720, width=1280) as renderer:
    renderer.update_scene(d, camera=cam)   # ① 按当前 d 和相机，整理出要画的几何体
    frame = renderer.render()              # ② 真正画出来，返回 (720, 1280, 3) 的 uint8 数组
                                           # ③ 拿 frame 去存图、写视频、喂给神经网络都行

有两个细节，新手几乎都会踩：

① 画布大小有上限。 离屏缓冲区默认 640×480。G1 的 scene.xml 没改过它，直接要 1280×720 会报错：

ValueError: Image width 1280 > framebuffer width 640. Either reduce the image
width or specify a larger offscreen framebuffer in the model XML ...

两种改法，效果一样：在 XML 里加 <visual><global offwidth="1280" offheight="720"/></visual>；或者像本课脚本这样，加载模型后在 Python 里改，模型文件不用动：

m.vis.global_.offwidth = 1280      # 注意是 global_，带下划线（global 是 Python 关键字）
m.vis.global_.offheight = 720

② 仿真频率和视频帧率不一样。 G1 的时间步长是 2 ms，也就是每秒 500 步；视频只要每秒 30 帧。每步都渲染既慢又没用。做法是：仿真时间追上下一帧该出现的时刻，才渲染一帧。

nframe = 0
while d.time < T_END:
    if d.time >= nframe / fps:     # 第 nframe 帧应该出现在 nframe/fps 秒
        ...渲染、写入一帧...
        nframe += 1
    mujoco.mj_step(m, d)

这样 5 s 的仿真正好得到 150 帧，播放速度和真实时间一致。

10.3 相机：跟着走，还是站着拍

update_scene 的 camera 参数可以给三种东西：模型里定义的相机名字或编号；-1（默认的自由相机）；或者一个自己配置的 mujoco.MjvCamera 对象。G1 的模型里没有定义相机，所以我们自己造：

def make_camera(kind, m):
    cam = mujoco.MjvCamera()
    if kind == "track":
        cam.type = mujoco.mjtCamera.mjCAMERA_TRACKING
        cam.trackbodyid = m.body("pelvis").id    # 跟踪哪个 body（看的是它所在子树的质心）
        cam.distance = 2.2                       # 相机到注视点的距离 m
        cam.azimuth = 135.0                      # 水平方位角（度）
        cam.elevation = -15.0                    # 俯仰角（度），负数表示从上往下看
    else:
        cam.type = mujoco.mjtCamera.mjCAMERA_FREE
        cam.lookat[:] = [0.0, 0.0, 0.6]          # 注视点固定在世界坐标里
        cam.distance = 3.5
        cam.azimuth = 90.0
        cam.elevation = -10.0
    return cam
字段 含义 自由相机 跟踪相机
type 相机类型 mjCAMERA_FREE mjCAMERA_TRACKING
lookat 注视点（世界坐标） 自己设，固定不动 每帧自动设成被跟踪子树的质心
trackbodyid 跟踪哪个 body 不用 必填
distance / azimuth / elevation 相机离注视点多远、从哪个方位、多高的角度看 自己设 自己设，相机只平移不转动

想象相机挂在一根以 lookat 为中心的杆子上：distance 是杆长，azimuth 是杆子在水平面上转到哪个方向，elevation 是杆子抬起的角度。自由相机的杆子钉死在地上；跟踪相机的杆子跟着机器人平移。

  • 跟踪相机适合机器人会走动、会倒的场景，人始终在画面里，但背景在“滑动”，不容易看出它移动了多少。
  • 自由相机适合看位移和倒下的方向：地面格子不动，倒在哪里一目了然。azimuth=90 是从 G1 的右侧（−y 方向）看过去，正好是侧视图。

10.4 在画面上画推力箭头

推力本身是看不见的。update_scene 之后、render 之前，renderer.scene 里已经放好了这一帧要画的所有几何体，我们可以往里面再追加一个：

def add_arrow(scn, d, body_id, force, scale=0.004):
    if np.linalg.norm(force) < 1e-9 or scn.ngeom >= scn.maxgeom:
        return
    tip = d.xipos[body_id].copy()               # 躯干质心（力就作用在这里）
    tail = tip - force * scale                  # 箭尾在外面，箭头扎向身体
    g = scn.geoms[scn.ngeom]                    # 取下一个空位
    mujoco.mjv_initGeom(g, mujoco.mjtGeom.mjGEOM_ARROW, np.zeros(3), np.zeros(3),
                        np.zeros(9), np.array([1, 0.1, 0.1, 1], dtype=np.float32))
    mujoco.mjv_connector(g, mujoco.mjtGeom.mjGEOM_ARROW, 0.03, tail, tip)
    scn.ngeom += 1                              # 别忘了：不加 1 就等于没画

mjv_initGeom 设好类型和颜色，mjv_connector 按“从哪到哪”算出箭头的位置、方向和长度。比例 0.004 m/N 表示 100 N 画成 0.4 m 长。实时查看器里也是同一套写法，只是场景换成 viewer.user_scn（见 10.5 的 --view）。

xfrc_applied 的力作用在 body 的质心上（世界坐标系），所以箭头尖端放在 d.xipos（质心位置），而不是 d.xpos（body 坐标系原点）。

主循环的核心（完整代码见脚本）：

with mujoco.Renderer(m, height=args.height, width=args.width) as renderer, \
        imageio.get_writer(path, fps=args.fps, codec="libx264", quality=8) as writer:
    while d.time < T_END:
        d.xfrc_applied[torso, :3] = current_force(d.time)   # 先定好这一步的力，画面上的箭头才对得上
        if d.time >= nframe / args.fps:
            renderer.update_scene(d, camera=cam)
            add_arrow(renderer.scene, d, torso, d.xfrc_applied[torso, :3])
            writer.append_data(renderer.render())
            nframe += 1
        mujoco.mj_step(m, d)
  • imageio.get_writer(..., codec="libx264") 借助 imageio-ffmpeg 自带的 ffmpeg 编码成 H.264，像素格式默认 yuv420p，Windows 自带播放器、浏览器都能直接放。
  • quality 取 0–10，越大越清晰、文件越大。
  • 宽和高最好是 16 的倍数（1280×720 正好是），否则 imageio 会自动缩放一点并给出警告。
  • 用 with 打开 writer，退出时会自动收尾。忘了关，最后几帧可能写不进去，文件甚至打不开。

--view 走的是另一条路：mujoco.viewer.launch_passive 打开查看器，仿真循环仍由我们控制，每步 viewer.sync() 一次，并按真实时间 sleep；箭头画在 viewer.user_scn 里，每步先把 user_scn.ngeom 清零再画，修改时要在 with viewer.lock(): 里进行。macOS 上要用 mjpython 启动。

10.6 批量实验：怎样设计才算数

录视频只能看一两次推力。想回答“推多大会倒”，得做几百次。先把实验设计写清楚：

项目 设置 理由
站姿 stand 关键帧，执行器目标不变 和视频、第 5 课一致
推哪里 躯干 torso_link 质心，水平方向 最像被人从肩膀推一把
推力大小 0–200 N 均匀随机 预实验发现 200 N 时几乎必倒
方向 −180°–180° 均匀随机 0° 是 +x，也就是从背后往前推
时刻 0.5–1.5 s 随机，精确到 10 ms 避开开头的落地晃动；随机化避免巧合
持续 0.1 s 一次短促的推
仿真时长 5 s（2500 步） 推完至少还剩 3.4 s。预实验跑到 10 s 发现：判到 4 s 会漏掉 3 次“慢慢倒”的实验，判到 5 s 以后结果不再变
判据 结束时骨盆高度 < 0.5 m 算摔倒 5 s 时站着的都在 0.79 m 左右，倒下的都在 0.06–0.09 m，中间一个都没有

全部随机参数一次性生成好：

def make_trials(n, seed):
    rng = np.random.default_rng(seed)
    force = rng.uniform(0.0, F_MAX, n)                # 推力大小 N
    angle = rng.uniform(-np.pi, np.pi, n)             # 水平方向
    start = rng.integers(50, 150, n)                  # 开始推的 chunk 序号：0.5–1.5 s
    fvec = np.stack([force * np.cos(angle), force * np.sin(angle), np.zeros(n)], axis=1)
    return force, angle, start, fvec

“chunk”是什么？每次实验要跑 2500 步，如果每一步都回到 Python 判断“该不该推”，Python 的开销比物理计算本身还大。所以脚本每 5 步（10 ms）检查一次，中间用 mujoco.mj_step(m, d, nstep=5) 一口气走完。推力的开始时刻因此精确到 10 ms，对这个实验来说足够了。

10.7 三种跑法：串行、多进程、mujoco.batch

方式 1：串行。 一个 MjData，一次一次地跑（下面三段是简化版；脚本里的函数多一个 push_chunks 参数，给练习 2 用）：

def run_serial(m, key, torso, fvec, start):
    d = mujoco.MjData(m)
    nchunk = round(T_END / (CHUNK * m.opt.timestep))
    z = np.empty(len(fvec))
    for i in range(len(fvec)):
        mujoco.mj_resetDataKeyframe(m, d, key)        # qpos、ctrl 都恢复成 stand
        for c in range(nchunk):
            pushing = start[i] <= c < start[i] + PUSH_CHUNKS
            d.xfrc_applied[torso, :3] = fvec[i] if pushing else 0.0
            mujoco.mj_step(m, d, nstep=CHUNK)
        z[i] = d.qpos[2]
    return z

方式 2：多进程。 Python 的 GIL 让多个线程不能同时跑 Python 代码，最直接的绕法是开多个进程，每个进程自己加载模型、跑一部分：

def run_multiprocess(fvec, start, nworker):
    parts = np.array_split(np.arange(len(fvec)), nworker * 4)   # 切成小块，进程之间负载更均匀
    jobs = [(fvec[p], start[p]) for p in parts]
    with cf.ProcessPoolExecutor(nworker, initializer=_init_worker) as pool:
        return np.concatenate(list(pool.map(_work, jobs)))      # map 按提交顺序返回

MjModel 可以在进程之间传，但每个任务都传一遍很浪费，所以用 initializer 让每个进程启动时自己加载一次。Windows 上新进程启动时会把脚本重新导入一遍，所以主程序必须放在 if __name__ == "__main__": 下面，否则每个子进程又会去开进程池。另外，传给子进程的参数要随任务一起传（脚本里的 push_chunks 就是这样），子进程看不到主进程运行时改过的全局变量。

方式 3：mujoco.batch。 MuJoCo 3.17 起新增的批量 API。Batch(m, nsim, nthread) 把 nsim 个仿真放进 C++ 线程池，每个仿真的状态是一个大 NumPy 数组的一行：

def run_batch(m, key, torso, fvec, start, nthread):
    n = len(fvec)
    b = batch.Batch(m, nsim=n, nthread=nthread)       # nthread=0 表示用全部 CPU 核
    b.reset(keyframe=key)                             # 所有仿真都重置到 stand 关键帧
    xfrc = b.bind("xfrc_applied")                     # 形状 (n, nbody, 6)，写它就是给每个仿真施力
    qpos = b.bind("qpos")                             # 形状 (n, nq)
    nchunk = round(T_END / (CHUNK * m.opt.timestep))
    for c in range(nchunk):
        pushing = (start <= c) & (c < start + PUSH_CHUNKS)      # (n,) 布尔数组
        xfrc[:, torso, :3] = fvec * pushing[:, None]
        b.step(nstep=CHUNK)
    return qpos[:, 2].copy()

对比串行版：外层“对每次实验”的循环消失了，变成对整列数组操作；b.step 期间 GIL 被释放，几百个仿真分给各个线程同时算。bind 返回的状态字段（qpos、ctrl、xfrc_applied 等）是活的视图，写进去就是下一次 step 的输入。官方文档还保证：结果和“每个仿真一个 MjData 的循环”逐位相同，与线程数无关。

为什么不用 mujoco.rollout？ rollout 也是 C++ 多线程，但它是“无状态的开环推演”：要事先给出每一步的全部输入。推力要通过 control_spec 带上 mjSTATE_XFRC_APPLIED，每步 31 个 body × 6 = 186 个数，500 次 × 2500 步就是 2.3 亿个 float64，约 1.9 GB。它更适合采样式 MPC 这种“短时域、成批试控制序列”的场合。需要在循环里边跑边改输入时，用 batch。

耗时和机器有关，同一台机器上每次也会波动（我们跑了几遍，多进程在 10–15 s 之间，batch 在 7.4–7.7 s 之间）；摔倒的统计结果则每次都一样。

读懂耗时

  • 多进程只快了 4 倍多。 一是这颗 CPU 只有 8 个物理核，16 个逻辑核是超线程，两个逻辑核共用一套运算单元；二是每个进程都要启动 Python、导入 mujoco、加载模型，Windows 上这部分开销不小；三是进程之间要来回传数据。
  • batch 快了 7 倍多。 线程不用重复加载模型，Python 那层循环只跑一遍（每 10 ms 一次，对 500 个仿真一起写数组），真正的计算全在 C++ 里。
  • 线程数的影响：同样的 500 次实验，--nthread 1 时 batch 用了 57.08 s，和串行差不多；--nthread 4 时 16.72 s。所以 batch 的提速来自多线程，而不是什么魔法。
  • 三种方式的骨盆高度最大差为 0，逐位相同。并行只改变“谁来算”，不改变“算什么”。

10.8 摔倒率曲线

打开 output/10_fall_rate_seed0.png。左图是全部方向混在一起的摔倒率，竖线是误差棒（二项分布的标准误 \(\sqrt{p(1-p)/n}\)，每个区间只有 50–75 次，中段的误差约 ±5%–7%）；右图按方向分三组。

几个规律：

  • 曲线不是一个台阶，而是一段 S 形过渡：0–50 N 基本不倒，150 N 以上几乎必倒，中间这段倒不倒取决于方向和时机。
  • 从正面推最不经推（50% 摔倒推力约 50 N），从背后推稍好（约 58 N），侧推最经推（约 106 N）。
  • 注意“侧推”这一组包括 45°–135° 之间所有方向，斜着推（带一点往后的分量）的也算在里面，所以它的 50% 推力比纯侧推低。第 5 课纯侧推（正对 +y）、推 0.2 s 的临界推力是 82 N；做完练习 2 可以拿本课推 0.2 s 的侧推组和它比一比。

原因可以从支撑区域找（第 4 课讲过）。站稳以后整机质心在 x = 0.003 m（和第 5 课说的“比支撑区中心偏后 3.2 cm”是一回事），脚底 8 个小球的 x 范围是 −0.05 到 0.12 m，y 范围是 ±0.149 m：

质心往后到脚跟：约 5 cm   → 从正面推（往后倒）最容易越界
质心往前到脚尖：约 12 cm  → 从背后推（往前倒）好一些
质心往侧面到脚外沿：约 15 cm → 侧推最经推

这些位置伺服只会“把关节拉回目标角度”，不会主动迈步、也不会调整重心。推力让质心冲出支撑区域，它就倒了。第 9 课的行走策略会迈步，抗推能力完全是另一个量级。

10.9 随机种子与可复现

“跑几百次随机实验”最怕的是：今天跑出 62%，明天跑出 58%，不知道是代码改了还是运气变了。本课脚本这样保证可复现：

  1. 只有一个随机源：np.random.default_rng(seed)。不用 np.random.rand 这类全局函数，也不在子进程里另外生成随机数。
  2. 先生成，后分发：全部参数在主进程里一次性生成好，再切块交给进程或 batch。怎么切、几个线程，都不影响每次实验拿到的参数。
  3. MuJoCo 本身是确定的：同样的初始状态、同样的输入，mj_step 的结果逐位相同。mj_resetDataKeyframe 和 b.reset 会把热启动（qacc_warmstart）等状态一起清掉，上一次实验不会“渗”到下一次。
  4. 把种子和原始数据存下来：种子写进文件名，每次实验的参数和结果写进 output/10_push_trials_seed0.csv，事后可以挑出任何一次单独重放、录成视频。

官方文档对第 3 点有个限制：逐位相同只在同一个 MuJoCo 版本、同一种 CPU 架构上成立。换版本、换操作系统，个别处于临界的实验可能翻转，但统计曲线应该基本不变。

如果确实需要在每个子进程里生成随机数（比如每个进程自己随机化摩擦），用 np.random.SeedSequence(seed).spawn(n) 给每个进程派生一个独立的种子，不要让它们都用同一个种子，也不要不设种子。
