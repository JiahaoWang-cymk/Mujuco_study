第 3 课　把它吊起来挥手

对应入门教程：4.7、5.8、6.3、7.3、9.3、9.4

本课目标

  • 用 MjSpec 改模型：删掉骨盆的 freejoint，把 G1 “吊”在半空，再存成新的 XML。
  • 给右臂设计一条挥手轨迹：五次多项式抬手、正弦挥手、五次多项式放下。
  • 记录目标角和实际角，画出跟踪误差，看清楚误差从哪里来。
  • 对比三种控制方式：纯位置伺服、伺服 + qfrc_bias 前馈、伺服 + MuJoCo 内置重力补偿。

预计用时：2 小时　前置：第 1 课（qpos 排布、执行器）、第 2 课（position 执行器的力公式、关键帧）

3.1 为什么要先吊起来

第 1 课说过，G1 是浮动基机器人：骨盆靠 freejoint 在空间里自由移动，全靠脚和地面的接触“站”住。想调手臂的时候，这就很麻烦：

  • 手臂一动，质心跟着动，整个人可能晃，甚至倒下。
  • 手臂的误差和“站不稳”的误差搅在一起，分不清是谁的问题。

真机调试也是这么做的：先把机器人吊在架子上，只调上肢，确认没问题再放到地上。在仿真里，“吊起来”就是把骨盆和世界焊死。有两种办法：

办法 做法 效果
删掉 freejoint spec.delete(spec.joint("floating_base_joint")) 骨盆没有关节，就和父 body（world）固定在一起，是硬固定
加 weld 约束 <equality><weld body1="pelvis"/></equality> freejoint 还在，靠约束力把骨盆拉住，是软约束，会有一点点下沉（练习 4）

本课用第一种。它还有个附带好处：qpos 里少了 7 个数，关节下标从 0 开始，取数据更直观。

3.2 用 MjSpec 改模型

第 1 课是用文本编辑器读 XML。这一课用代码改：MjSpec 把整个模型读成一棵可以增删改的对象树，改完再 compile() 成 MjModel（入门教程 9.4）。

spec = mujoco.MjSpec.from_file(str(XML))      # 读 scene.xml，include 的 g1.xml 也一起读进来

# ① 删掉 freejoint：pelvis 没有关节，就和父 body（world）焊死了
spec.delete(spec.joint("floating_base_joint"))
spec.body("pelvis").pos = [0, 0, HANG_Z]      # 吊在离地 1.2 m 处

# ② 关键帧里的 qpos 原来有 7 + 29 = 36 个数，去掉 freejoint 的 7 个
key = spec.key("stand")
key.qpos = list(key.qpos)[7:]

# ③ 加一根“吊绳”：只用来看，不参与碰撞
spec.worldbody.add_geom(
    name="rope", type=mujoco.mjtGeom.mjGEOM_CYLINDER,
    fromto=[0, 0, HANG_Z + 0.45, 0, 0, 3.0], size=[0.006, 0, 0],
    contype=0, conaffinity=0, rgba=[0.9, 0.8, 0.5, 1])

m = spec.compile()

几个要点：

  • 第 ② 步不能省。 关键帧存的是整段 qpos，长度必须等于新模型的 nq。忘了改，compile() 会报 keyframe 'stand': invalid qpos size, expected 29, got 36。改模型时，所有“按下标存的数据”都要跟着检查：关键帧、你自己代码里写死的下标。
  • 改的是 spec，不是文件。 models/ 里的 XML 一个字节都没动，下次 from_file 读到的还是原版。想留下修改，要自己存（3.6 节）。
  • 吊绳挂在 worldbody 上。 world 不会动，挂在它上面的 geom 不算质量；contype=0 conaffinity=0 让它不和任何东西碰撞。它纯粹是给人看的。

骨盆离地 1.2 m，比站立时（0.79 m）高了约 0.4 m，脚悬空，整个仿真过程中接触数一直是 0。

先猜一猜

  1. 删掉 freejoint 后，nq 和 nv 各是多少？它们还会不一样吗？
  2. 关节都还在执行器的控制下。腿会保持站姿，还是像吊着的木偶一样垂下来？

3.3 设计挥手轨迹

位置伺服的 ctrl 是目标角。所谓“轨迹”，就是每个时刻该给 ctrl 写多少。挥手分三段：

 0 ── 0.5 s ────── 2.0 s ─────────────── 6.0 s ────── 7.5 s ── 8.0 s
 静止 │ 抬手（五次多项式）│ 挥手（肘关节正弦，1.5 Hz）│ 放下（五次多项式）│ 静止

抬手姿势（右臂 7 个关节，单位 rad）：

Q_RAISE = np.array([0.0, -1.3, -1.57, 0.0, 0.0, 0.0, 0.0])
#                   肩pitch 肩roll 肩yaw  肘  腕roll 腕pitch 腕yaw
  • 肩 roll = −1.3：大臂向外侧抬起，接近水平。右臂往外是负方向，左臂正好相反（第 1 课练习 3 讲过这种镜像）。
  • 肩 yaw = −1.57：大臂绕自己的轴转 90°。G1 的肘关节在 0 时，小臂朝前伸；转过这 90°，小臂就朝上了。
  • 挥手靠肘关节：在 0 附近做幅度 0.5 rad 的正弦。

这组数不是一眼看出来的。做法是：先猜一组角度，mj_forward 后打印肘和手的 xpos，看手是不是在肘的上方，不对再改。机器人的关节零位和转轴方向千差万别，先算再看，比凭想象可靠。

五次多项式负责“从 A 平滑地走到 B”：

def quintic(t, t0, t1):
    """s 从 0 平滑地走到 1，起止点速度、加速度都是 0。"""
    tau = np.clip((t - t0) / (t1 - t0), 0.0, 1.0)
    return 10 * tau**3 - 15 * tau**4 + 6 * tau**5

q_target = q_start + quintic(t, 0.5, 2.0) * (Q_RAISE - q_start)

为什么不直接线性插值？线性插值在起点和终点速度会突变，相当于一下子要无穷大的加速度，电机会“咯噔”一下。五次多项式的位置、速度、加速度在两端都连续，是机器人轨迹规划里最常用的形式。

挥手段用正弦：q[肘] = Q_RAISE[肘] + 0.5 * sin(2π · 1.5 · (t − 2.0))。正弦在起点位置连续，但速度从 0 突然跳到最大值。等会儿在误差图上能看到这一下。

3.4 三种跟踪方式

同一条轨迹，用三种方式去跟：

方式 做法 控制量
servo 只用模型自带的 position 执行器 ctrl = 目标角
ff 再把 qfrc_bias 原样写进 qfrc_applied 前馈：抵消重力和科氏力 / 离心力
gravcomp 每个 body 设 gravcomp=1，每个关节设 actuatorgravcomp MuJoCo 自己算重力，加到执行器力里

位置伺服为什么会有误差

第 2 课讲过 position 执行器的力：

\[\tau = k_p\,(\text{ctrl} - q) - k_v\,\dot q\]

它没有“提前知道”要出多少力，只能先产生误差，再按误差出力。两个后果：

  • 重力下垂。 手臂要一直顶住重力矩 \(\tau_g\)，误差就得一直存在：\(q_{\text{目标}} - q \approx \tau_g / k_p\)。
  • 运动滞后。 关节在动时，\(-k_v\dot q\) 一直在“拖后腿”。要抵消它，也得靠误差：\(q_{\text{目标}} - q \approx (k_v/k_p)\,\dot q\)。

前馈：把“该出的力”直接给上

d.qfrc_bias 是 MuJoCo 算好的“重力 + 科氏力 / 离心力”（入门教程 7.3）。在运动方程 \(M\ddot q + c(q,\dot q) = \tau\) 里，它就是 \(c\)。把它原样加到关节上，重力就被抵消了，伺服只需要管剩下的部分。

关键是时机。mj_step 在一步的开头算 qfrc_bias，而我们写控制量要在这之前。入门教程 7.3 用的是“上一步留下的 qfrc_bias”，差一个时间步。这里用更严谨的写法：把 mj_step 拆成两半。

def step(self):
    m, d = self.m, self.d
    mujoco.mj_step1(m, d)                           # 算到速度阶段，qfrc_bias 已更新
    self.q_des = arm_target(d.time, self.q_start)   # 这一步的目标角
    d.ctrl[self.arm_u] = self.q_des
    if self.mode == "ff":
        d.qfrc_applied[:] = d.qfrc_bias             # 重力 + 科氏力/离心力，全部前馈
    mujoco.mj_step2(m, d)                           # 用新的 ctrl、qfrc_applied 完成这一步

mj_step1 算完位置和速度相关的量（包括 qfrc_bias）就停下；你在中间写 ctrl、qfrc_applied；mj_step2 再算力和加速度、做积分。官方文档说明，这种拆分只适用于单步积分器（Euler、implicit、implicitfast）。G1 用的是 implicitfast，没问题；如果换成 RK4，就不能这么写了。

内置重力补偿：gravcomp

MuJoCo 还有一套现成的机制，两个属性配合使用：

for body in spec.bodies:
    body.gravcomp = 1.0          # XML: <body gravcomp="1">，加一个等于自身重量的向上的力
for joint in spec.joints:
    joint.actgravcomp = True     # XML: <joint actuatorgravcomp="true">
  • gravcomp="1" 单独用时，这个力算在被动力 qfrc_passive 里，相当于物体“失重”了，像气球一样。
  • 再加上 actuatorgravcomp="true"，同样的力改为算进执行器力 qfrc_actuator，意思是“这是电机出的力”。这样传感器读数、力矩统计都更接近真实情况。
  • 注意 MjSpec 里的属性名是 actgravcomp，XML 里是 actuatorgravcomp，两边不一样。

它和 ff 的区别：gravcomp 只补偿重力，不管科氏力 / 离心力；qfrc_applied 是你自己加的力，MuJoCo 不会替你检查电机上限。另外，Menagerie 的力矩上限写在执行器的 forcerange 上，它只截断伺服本身的输出；重力补偿那部分要靠关节上的 actuatorfrcrange 才能一起截断。

先猜一猜

  1. 挥手时，哪个关节的误差更大：肩 roll 还是肘？
  2. 加了重力补偿以后，肩 roll 的误差会变小多少？肘的误差呢？
  3. ff 和 gravcomp 的结果会差很多吗？

3.6 把改好的模型存下来

MjSpec 改出来的模型用 spec.to_xml() 导出为 XML 文本。入门教程 5.8 的 mj_saveLastXML 只认“最近一次直接从 XML 文件加载的模型”，本课脚本全程用 MjSpec，调用它会报 No XML model loaded。脚本里的保存函数：

def save_model(mode, path):
    spec = build_spec(mode)
    xml = spec.to_xml()
    old = 'meshdir="assets"'
    assert old in xml
    xml = xml.replace(old, 'meshdir="../models/unitree_g1/assets"')
    path.write_text(xml, encoding="utf-8")
    m = mujoco.MjModel.from_xml_path(str(path))         # 重新加载核对
    return xml, m

输出：

已保存 output/g1_hanging.xml：316 行，重新加载 nq=29 nu=29，含 gravcomp 属性的行 0 行
已保存 output/g1_hanging_gravcomp.xml：316 行，重新加载 nq=29 nu=29，含 gravcomp 属性的行 59 行

59 行 = 30 个 body 的 gravcomp="1" + 29 个关节的 actuatorgravcomp="true"。

存模型时有三件事要知道：

  • 网格路径。 原模型写的是 meshdir="assets"，相对 g1.xml 所在目录。新文件存到 output/，这个相对路径就找不到网格了。to_xml() 会先编译一遍，编译时还得按原来的路径找网格，所以不能事先改 spec.meshdir（会报 Error opening file '../models/unitree_g1/assets/pelvis.STL'），只能导出后在文本里替换。
  • include 被展开了。 原来的 scene.xml 只有一行 <include file="g1.xml"/>；导出的文件是一个完整的单文件，机器人和场景都在里面（入门教程 4.7）。
  • 存的是编译后的值。 打开 g1_hanging.xml 看执行器，原来的 <position kp="500" dampratio="1" inheritrange="1"> 变成了 <general ... ctrlrange="..." biasprm="0 -500 ...">。比如右肘那一行是 ctrlrange="-1.0472 2.0944" forcerange="-25 25" biasprm="0 -500 -7.17685"：ctrlrange 是按关节范围算好的，biasprm 的第三个数就是算出来的 \(-k_v\)（3.5 节观察记录第 3 题会用到这个 7.18）。这是因为 spec.compiler.savecompiled 默认是 True。设成 False 会尽量保留原来的写法（执行器仍写成 <general>，但不再展开 ctrlrange 和 biasprm）。

存好的文件可以直接用查看器打开：

python -m mujoco.studio.viewer --model=output/g1_hanging.xml

打开时 ctrl 全是 0，各关节会转向 0 位；在 Keyframe 下拉框里选 stand 再点 Reset，就回到站姿。查看器里没有我们的控制器，想看挥手，用下一节的 --view。

3.7 实时观看

python code/03_wave.py --view              # 默认 servo
python code/03_wave.py --view --mode ff
python code/03_wave.py --web 8790 --mode ff  # 同上，但显示在网页里：浏览器打开 http://127.0.0.1:8790/

脚本里的写法和入门教程 6.3 一样，用 launch_passive，仿真循环自己控制：

with mujoco.viewer.launch_passive(w.m, w.d) as viewer:
    while viewer.is_running():
        step_start = time.time()
        if w.d.time >= T_END:          # 8 s 一轮，跑完从头再来
            w.reset()
        w.step()                       # 里面是 mj_step1 → 写控制量 → mj_step2
        viewer.sync()                  # 不调用它，画面不会动
        dt = w.m.opt.timestep - (time.time() - step_start)
        if dt > 0:
            time.sleep(dt)

用 Studio 打开 XML 时，它只按模型本身仿真。要在每一步执行自己的控制代码，就得用 launch_passive 这类“你来推进、它只负责画”的查看器。

不同方式肉眼看起来几乎一样：它们之间的差别不到 1°，眼睛分辨不出来。这正说明了为什么要记录数据、画误差图。

练习

  1. 软一点的伺服。 在 build_spec 里把右臂 7 个执行器的 kp 从 500 改成 100（要同时改 gainprm[0] 和 biasprm[1]，biasprm[2] 存的是 dampratio，保持 1 不动，编译时会重新算 kv）。重跑，对比三种方式的肩 roll 误差和静止误差，看看 kp 变小以后，重力补偿的作用是不是更明显了。

参考答案（跑完再看） 3.2 先猜一猜：nq=29、nv=29，两者相等了。不等的根源是 freejoint 的四元数（4 个数表示 3 个转动自由度），删掉它，剩下 29 个铰链关节，每个都是 1 个位置、1 个速度。腿会保持站姿：29 个执行器都还在，关键帧的 ctrl 让它们各自顶在站立角度上。 3.4 先猜一猜：肘的误差更大（RMS 2.80° 对 0.58°）。加重力补偿后，肩 roll 的 RMS 误差从 0.58° 降到 0.13°（ff）/ 0.14°（gravcomp），最大误差从 0.93° 降到 0.28°；肘的误差几乎不变（2.80° → 2.78°）。ff 和 gravcomp 几乎一样。 观察记录 1. 误差 = 目标 − 实际 < 0，说明实际角比目标角大。肩 roll 的目标是 −74.5°（往外抬，是负的），实际比它大，就是更靠近 0，也就是手臂偏低，被重力往下拽了。 2. 8.27 / 500 = 0.0165 rad ≈ 0.95°，和表里纯伺服的最大误差 0.93° 基本一致。重力下垂就是这么来的。放下后静止时，肩 roll 还有 −0.158° 的误差，同样是重力造成的；加了补偿以后只剩 0.001°。 3. 肘的误差主要是运动滞后，不是重力：手臂举起后小臂朝上，肘的重力矩很小。滞后误差约为 \((k_v/k_p)\,\dot q\)。肘的 \(k_v/k_p = 7.18/500 \approx 0.0144\) s，挥手的最大角速度是 \(0.5 \times 2\pi \times 1.5 \approx 4.71\) rad/s，估出来约 0.068 rad ≈ 3.9°，实测最大 3.9–4.0°，对得上（纯伺服多出的 0.1° 来自小臂的重力）。重力补偿只管重力，当然治不了它。2.0 s 处的尖峰也是同一个原因：正弦一开始，目标速度从 0 突然跳到 4.71 rad/s。 4. 科氏力和离心力跟速度的平方成正比。这么慢的挥手，它们比重力小得多，所以只补重力和全补，结果几乎一样。 练习 1：在 build_spec 的 return spec 之前加： 
for name in ARM:
    act = spec.actuator(name)
    act.gainprm[0] = 100      # kp
    act.biasprm[1] = -100     # -kp
结果（挥手段 RMS / 最大，单位度）： | 方式 | 肩 roll | 肘 | 静止时肩 roll | |---|---|---|---| | 纯位置伺服 | 2.94 / 4.70 | 6.58 / 9.77 | −0.723 | | ff | 0.72 / 1.38 | 6.36 / 9.00 | +0.035 | | gravcomp | 0.75 / 1.37 | 6.36 / 9.05 | +0.035 | kp 降为原来的 1/5，纯伺服的重力下垂大约放大了 5 倍（静止误差 −0.158° → −0.723°），重力补偿的效果也就更明显。肘的 kv 跟着从 7.18 变成了 3.21（dampratio=1 在编译时按新的 kp 重算），\(k_v/k_p\) 从 0.0144 变成 0.032，所以肘的滞后也变大了。真机上常把 kp 设得比较软（更安全、更柔顺），这时前馈就更重要了。 练习 2：在 step() 里 d.ctrl[self.arm_u] = self.q_des 之后加： 
if self.mode == "lead":
    h = 1e-4
    qd_des = (arm_target(d.time + h, self.q_start) - self.q_des) / h
    kp = m.actuator_gainprm[self.arm_u, 0]
    kv = -m.actuator_biasprm[self.arm_u, 2]
    d.ctrl[self.arm_u] = self.q_des + kv / kp * qd_des
    d.qfrc_applied[:] = d.qfrc_bias
再把 "lead" 加进 MODES 和 MODE_NAME。结果：肘的误差从 2.78 / 3.93 降到 0.20 / 0.30，肩 roll 是 0.14 / 0.28，静止误差 0.000°。代入执行器公式：\(k_p(q_{des} + \frac{k_v}{k_p}\dot q_{des} - q) - k_v\dot q = k_p(q_{des}-q) + k_v(\dot q_{des}-\dot q)\)，这正是带速度参考的 PD 控制。剩下的误差来自加速度项 \(M\ddot q\)，第 6 课的逆动力学会把它也补上。 为什么不能把 \(k_v\dot q_{des}\) 直接写进 qfrc_applied？因为执行器的 forcerange 截断的是整个伺服输出，包括 \(-k_v\dot q\) 这一项。肘的上限是 ±25 N·m，而 \(k_v\dot q\) 最大有 7.18 × 4.71 ≈ 34 N·m：伺服的阻尼被截断了，你在外面加的 34 N·m 却原封不动，两边抵消不掉，手臂会被甩出去。实测肘的误差最大超过 100°。改目标角的做法，力矩始终经过执行器、始终受上限约束，就没有这个问题。 练习 3：参考脚本 code/03_compare_models.py。运行结果要点： | | Menagerie g1.xml | rl_gym g1_12dof.xml | |---|---|---| | nbody / njnt | 31 / 30 | 14 / 13 | | nq / nv / nu | 36 / 35 / 29 | 19 / 18 / 12 | | 总质量 | 33.341 kg | 32.107 kg | - 关节：12 个腿关节（加上 freejoint 共 13 个）两边都有，范围完全相同；腰 3 个、手臂 14 个只在 Menagerie 里。rl_gym 版把腰、躯干、手臂全部焊在骨盆上。 - 关节参数：armature 都是 0.01；frictionloss Menagerie 是 0.3，rl_gym 是 0.1；damping Menagerie 是 0，rl_gym 是 0.001。力矩上限两边一致（88 / 139 / 50 N·m）。 - 质量：两条腿一模一样（都是 14.372 kg），只有 pelvis 不同：rl_gym 的 pelvis 是 17.735 kg，它对应的是 Menagerie 的骨盆加上腰以上整棵子树（18.969 kg）。两者差 1.234 kg，正好是总质量之差，说明两个版本上半身的质量数据不一样（比如 rl_gym 的手臂末端只有一块 wrist_roll_rubber_hand 网格，没有手腕 pitch / yaw 两节）。 - 执行器：Menagerie 是 position 伺服（kp=500，biastype=affine）；rl_gym 是 motor（biastype=none，增益 1），ctrl 直接就是力矩，PD 控制写在 Python 里。第 9 课会详细讲。 - URDF 的痕迹：力矩上限写在关节的 actuatorfrcrange 上（URDF 的 effort 转过来就是它）；有 MuJoCo 自动生成的 <statistic meansize=... extent=... center=...>；每个外观 geom 都重复写着一长串 contype="0" conaffinity="0" group="1" density="0" rgba=...，geom 没有用 default 类（文件里只有一条给 joint 的全局默认值）；外观和碰撞是成对的同一个网格。这些特征都像是把 URDF 加载进 MuJoCo 后直接导出、再手工补上执行器的样子。Menagerie 版则是人工整理过的：用 default 类、脚底换成小球、加了关键帧和传感器。 练习 4：

nq=36、nv=35，freejoint 还在。仿真 2 s 后骨盆在 [0.0014, 0, 1.1995]，下沉约 0.49 mm，x 方向也偏了 1.4 mm。weld 是软约束：约束力和下沉量相关，所以总会有一点误差。 有个坑：add_equality 返回的 data 默认是 [0, 1, 0, 0, …, 1, 0]，第 2 个数是 1（所有等式约束共用这一个默认值）。直接用的话，焊点会带上一个偏移，实测骨盆跑到了 y = −0.33 m、z = 0.82 m 的位置。XML 里写 <weld body1="pelvis"/> 时，解析器给的是全零（只有 data[10]=1），就没有这个问题。 为什么 pelvis.pos 和关键帧都要改？relpose 不指定时，weld 会把 qpos0（模型的参考姿势，由 body 的 pos 决定）下的相对位姿当作目标。只改关键帧，weld 会把骨盆拉回 0.79 m，脚又落回地面。
