渲染#

Rendering

MuJoCo 提供两个内置的 3D 渲染（rendering）后端，同时支持交互式的屏上查看器和无头离屏渲染：

MuJoCo provides two built-in 3D rendering backends that support both interactive onscreen viewers and headless offscreen rendering:

  • Filament 渲染 (mjrf)：一个现代的、基于物理的渲染（PBR）引擎，支持 OpenGL、Vulkan、Metal 和 WebGL。它采用 保留模式 （retained-mode）的异步架构，其中网格（mesh）、纹理、光源和 可渲染对象 一次性从 mjModel 创建，并在每一帧中根据 mjData 就地更新。Filament 为 MuJoCo Studio 提供支持，也是新应用推荐使用的渲染器。

    Filament rendering (mjrf): A modern, physically-based rendering (PBR) engine supporting OpenGL, Vulkan, Metal, and WebGL. It uses a retained-mode, asynchronous architecture in which meshes, textures, lights, and renderables are created once from mjModel and updated in place from mjData each frame. Filament powers MuJoCo Studio and is the recommended renderer for new applications.

  • OpenGL 渲染 (mjr)：经典的固定功能 OpenGL 1.5 渲染器，目前处于维护模式。它采用 立即模式 场景架构，其中每一帧都由 mjv_updateScene 用所有几何对象和光源填充一个 mjvScene，再由 mjr_render 绘制。它为经典的 simulate.cc 和 basic.cc 示例提供支持。

    OpenGL rendering (mjr): The classic fixed-function OpenGL 1.5 renderer, now in maintenance mode. It uses an immediate-mode scene architecture in which mjv_updateScene populates an mjvScene with all geometric objects and lights on every frame, and mjr_render draws it. It powers the classic simulate.cc and basic.cc samples.

两个渲染器共享与图形无关的 可视化 (mjv) 层，用于相机控制 (mjvCamera)、可视化（visualization）选项 (mjvOption)、对象拾取 (mjv_select) 和交互式扰动 (mjvPerturb)。经典 OpenGL 渲染器依赖 mjvScene 来描述整个场景，而 Filament 渲染器直接根据 mjData 更新模型几何，仅将 mjvScene 用于瞬态装饰性叠加层 (mjCAT_DECOR)。下表给出了两个渲染器主要概念之间的对应关系：

Both renderers share the graphics-independent Visualization (mjv) layer for camera control (mjvCamera), visualization options (mjvOption), object picking (mjv_select), and interactive perturbations (mjvPerturb). While the classic OpenGL renderer relies on mjvScene for the entire scene, the Filament renderer updates model geometry directly from mjData and uses mjvScene only for transient decorative overlays (mjCAT_DECOR). Filament 渲染#

Filament rendering

MuJoCo 提供了一个基于 Filament 的渲染器，Filament 是 Google 的实时、基于物理的渲染引擎。Filament 运行时小巧而快速，可在 Linux、Windows、macOS、Android、iOS 和 Web 上运行，并支持 OpenGL、Vulkan、Metal 和 WebGL 图形后端。Filament 渲染器为 MuJoCo Studio 和 live.mujoco.org 提供支持。

MuJoCo provides a renderer based on Filament, Google’s real-time physically based rendering engine. Filament has a small and fast runtime, runs on Linux, Windows, macOS, Android, iOS and the Web, and supports the OpenGL, Vulkan, Metal and WebGL graphics backends. The Filament renderer powers MuJoCo Studio and live.mujoco.org.

Filament 渲染器是一个可选的、自包含的库，名为 mujoco_filament 。它实现了 mjrf 类型 和 函数，这些类型和函数定义于 mjrfilament.h 中。

The Filament renderer is an optional, self-contained library named mujoco_filament. It implements the mjrf types and functions defined in mjrfilament.h.

虽然 Filament 运行时非常小巧高效，但它是一个相当庞大的构建依赖项。因此，如果你打算 从源码构建 MuJoCo，则需要设置 CMake 的 MUJOCO_USE_FILAMENT 选项，才能包含 Filament 渲染器。

While the filament runtime is very small and efficient, it is a rather large build dependency. As such, if you intend to build MuJoCo from source, you will need to set the CMake MUJOCO_USE_FILAMENT option in order to include the Filament renderer.

也可以通过额外设置 MUJOCO_USE_FILAMENT_MJR_COMPAT CMake 选项，在经典的 mjr API 中使用 Filament 渲染。该选项实际上是将基于 OpenGL 的 mjr 函数替换为基于 Filament 的实现。这对于无需重写应用代码即可试用 Filament 渲染器很有用。但是，这种兼容模式不支持 Filament 运行时提供的全部定制功能和效果，并且会带来轻微的性能开销。

It is also possible to use Filament rendering with the classic mjr API by additionally setting the MUJOCO_USE_FILAMENT_MJR_COMPAT CMake option. This option effectively replaces the OpenGL-based mjr functions with Filament-based implementations. This is useful for experimenting with the Filament renderer without having to rewrite application code. However, this compatibility mode does not support the full range of customization and effects available in the Filament runtime and comes with a slight performance overhead.

你可以在 render.cc 示例中找到使用 Filament 渲染器的例子，具体位于 RenderFilament() 函数中。

You can find an example of using the Filament renderer in the render.cc sample and, specifically, in the RenderFilament() function.

光强度决定光照模型

Light intensity switches the lighting model

Filament 渲染器仅凭一个属性来决定如何为 整个场景 打光：模型中是否有任何 光源 具有正的 intensity。

The Filament renderer decides how to light the entire scene from a single property: whether any light in the model has a positive intensity.

  • 如果 没有 任何光源具有正强度，则假定模型是为经典渲染器编写的。此时会添加默认的环境光，启用头灯，并将固定的总强度分配给模型的各个光源。

    If no light has positive intensity, the model is assumed to be authored for the classic renderer. A default environment light is added, the headlight is enabled, and a fixed total intensity is distributed among the model’s lights.

  • 如果 任何 光源具有正强度，则所有光源都被视为光度学光源：每个光源恰好贡献其自身的强度（因此强度保持为零的光源会变暗），头灯被关闭，并且除非模型定义了 image 光源，否则没有环境照明。

    If any light has positive intensity, all lights are treated as photometric: each light contributes exactly its own intensity (so lights left at zero go dark), the headlight is turned off, and there is no ambient illumination unless the model defines an image light.

因此，在单个光源上设置 intensity 会改变其他所有对象的外观。详情参见下文的 光照。

Setting intensity on a single light therefore changes the appearance of everything else. See Lighting below for details.

编程#

Programming

Filament 渲染器分为三层。最底层是外部开发的 Filament 库 本身，它提供基于物理的渲染管线和图形 API 后端。渲染器的公共接口是 mjrf C API，声明于 mjrfilament.h 中。与每帧都重绘一个 mjvScene 的经典 mjr API 不同， mjrf 是 保留模式 且 异步 的：应用程序创建长期存在的对象，对其进行增量修改，并提交成批的渲染和像素回读请求。在 C API 之上是 C++ 支持层，位于 src/render/filament/support （同时也绑定到 Python 的 mujoco.mjrf 下），可根据 mjModel、mjData 和 mjvOption 自动创建和更新 mjrf 场景对象。

The Filament renderer is organized in three layers. At the base is the externally developed Filament library itself, which provides the physically-based rendering pipeline and graphics API backends. The public interface to the renderer is the mjrf C API, declared in mjrfilament.h. Unlike the classic mjr API, which redraws an mjvScene every frame, mjrf is retained-mode and asynchronous: applications create long-lived objects, mutate them incrementally, and submit batches of render and pixel-readback requests. On top of the C API, the C++ support layer in src/render/filament/support (also bound in Python under mujoco.mjrf) automates creating and updating mjrf scene objects from mjModel, mjData, and mjvOption.

下面是一个简化的 C++ 概要 (改编自 render.cc 中的 RenderFilament())，说明这些组件如何配合完成离屏渲染：

Below is a simplified C++ outline (adapted from RenderFilament() in render.cc) illustrating how these components fit together for offscreen rendering:
// create Filament context and scene
mjrfContextConfig context_cfg;
mjrf_defaultContextConfig(&context_cfg);
auto ctx = mujoco::CreateContext(context_cfg);

mjrfSceneParams scene_params;
mjrf_defaultSceneParams(&scene_params);
auto scene = mujoco::CreateScene(ctx.get(), scene_params);
mjrf_configureSceneFromModel(scene.get(), m);

// create retained model components and decoration helper
auto model_resources   = std::make_unique<ModelResources>(m, ctx.get());
auto model_lights      = std::make_unique<ModelLights>(scene.get(), model_resources.get());
auto model_renderables = std::make_unique<ModelRenderables>(scene.get(), model_resources.get());
auto model_decorations = std::make_unique<ModelDecorations>(ctx.get(), scene.get(), m);

// create offscreen render target
mjrfRenderTargetConfig target_cfg;
mjrf_defaultRenderTargetConfig(&target_cfg);
target_cfg.width        = width;
target_cfg.height       = height;
target_cfg.color_format = mjPIXEL_FORMAT_RGB8;
target_cfg.depth_format = mjPIXEL_FORMAT_DEPTH32F;
auto render_target      = mujoco::CreateRenderTarget(ctx.get(), target_cfg);

// update retained lights, renderables, and transient decorations from mjData
mjrRect viewport = {0, 0, width, height};
model_renderables->SetOptions(opt);
model_lights->Update(d);
model_renderables->Update(d);
model_decorations->Update(d, &opt, nullptr, &cam, viewport);

// submit render and pixel-readback requests and wait for completion
mjrfRenderRequest request;
mjrf_defaultRenderRequest(&request);
request.scene               = scene.get();
request.camera              = mjv_camera2GLCamera(m, d, &cam);
request.viewport            = viewport;
request.target              = render_target.get();
request.headlight    = m->vis.headlight.active;
request.headlight_intensity = model_lights->GetHeadlightIntensity();

mjrfReadRequest read_request;
mjrf_defaultReadRequest(&read_request);
read_request.target    = render_target.get();
read_request.output    = rgb.data();
read_request.num_bytes = width * height * 3;

mjrfFrameHandle frame = mjrf_render(ctx.get(), &request, 1, &read_request, 1);
mjrf_waitForFrame(ctx.get(), frame);

// remove transient decorations before destroying the scene
model_decorations->Clear();

核心概念#

Core concepts

mjrf C API 围绕七种不透明对象类型展开，每种都用 mjrf_create* 函数创建，并用 mjrf_destroy* 释放：mjrfContext、mjrfScene、mjrfMesh、mjrfTexture、mjrfRenderable、mjrfLight 和 mjrfRenderTarget。创建时需要传入由 mjrf_default* 初始化的结构体，其名称编码了一条规则： *Config （上下文、纹理、网格、渲染目标）在对象的生命周期内保持固定，而 *Params （场景、光源、可渲染对象）是初始值，之后可以通过 mjrf_set* 函数更改。mjrfMaterial 和 mjrfRenderRequest 等普通结构体描述这些对象如何配置和绘制。

The mjrf C API revolves around seven opaque object types, each created with an mjrf_create* function and freed with mjrf_destroy*: mjrfContext, mjrfScene, mjrfMesh, mjrfTexture, mjrfRenderable, mjrfLight, and mjrfRenderTarget. Creation takes a struct initialized by mjrf_default*, whose name encodes a rule: a *Config (context, texture, mesh, render target) is fixed for the lifetime of the object, while *Params (scene, light, renderable) are initial values that can later be changed with mjrf_set* functions. Plain structs such as mjrfMaterial and mjrfRenderRequest describe how these objects are configured and drawn.
上下文与场景 (mjrfContext, mjrfScene)
Context and scene (mjrfContext, mjrfScene)

mjrfContext 是 Filament 渲染器的入口。与经典的 mjrContext 不同，它管理自己的图形上下文（OpenGL 或 Vulkan，通过 mjrfContextConfig 中的 mjrGraphicsApi 选择，可带可选的窗口句柄或使用无头软件渲染），并且独立于任何单个 mjModel。mjrfScene 是光源、可渲染对象和可选天空盒纹理的容器；场景级渲染选项和模型中自定义的 filament.* 标志通过 mjrf_configureSceneFromModel 应用。

mjrfContext is the entry point to the Filament renderer. Unlike the classic mjrContext, it manages its own graphics context (OpenGL or Vulkan, selected via mjrGraphicsApi in mjrfContextConfig, with optional window handle or headless software rendering) and is independent of any single mjModel. A mjrfScene is a container of lights, renderables, and an optional skybox texture; scene-level rendering options and custom filament.* flags from a model are applied via mjrf_configureSceneFromModel.
网格与纹理 (mjrfMesh, mjrfTexture)
Meshes and textures (mjrfMesh, mjrfTexture)

GPU 几何体和图像资源只创建一次，并在各帧之间保留。mjrfMesh 存储通过 mjrf_uploadMesh 上传的顶点属性（位置、打包的切线坐标系朝向、UV）和索引，以及用于视锥剔除的包围盒。mjrfTexture 存储通过 mjrf_uploadTexture 上传的 2D、立方体贴图或 KTX 压缩图像数据。两个上传函数都接受一个可选的完成回调，用于在异步 GPU 传输完成后释放主机内存；调用 mjrf_flush 会将待处理的操作刷新到渲染后端，并在下一次 mjrf_render 调用之前调用所有已完成的回调。

GPU geometry and image assets are created once and retained across frames. mjrfMesh stores vertex attributes (positions, packed tangent-frame orientations, UVs) and indices uploaded via mjrf_uploadMesh, along with bounding boxes used for frustum culling. mjrfTexture stores 2D, cubemap, or KTX-compressed image data uploaded via mjrf_uploadTexture. Both upload functions accept an optional completion callback for freeing host memory once the asynchronous GPU transfer finishes; calling mjrf_flush flushes pending operations to the rendering backend and invokes any completed callbacks before the next mjrf_render call.
可渲染对象与材质 (mjrfRenderable, mjrfMaterial)
Renderables and materials (mjrfRenderable, mjrfMaterial)

mjrfRenderable 是场景中持久存在的可绘制实体，组合了表面几何、材质外观和 3D 变换：

An mjrfRenderable is a persistent drawable entity in a scene, combining surface geometry, material appearance, and a 3D transform:

  • 几何： 可渲染对象既可以引用自定义的 mjrfMesh (通过 mjrf_setRenderableMesh)，也可以引用内置的几何基元，如球体、胶囊体、圆柱体、长方体或椭球体 (通过 mjrf_setRenderableGeomMesh，它会在具有相同质量参数的可渲染对象之间缓存并共享底层网格缓冲区)。

    Geometry: A renderable can reference either a custom mjrfMesh (via mjrf_setRenderableMesh) or a built-in geometric primitive such as a sphere, capsule, cylinder, box, or ellipsoid (via mjrf_setRenderableGeomMesh, which caches and shares underlying mesh buffers across renderables with matching quality parameters).

  • 材质： mjrf_setRenderableMaterial 应用一个 mjrfMaterial 结构体，它可在三种着色模型之间选择：金属度-粗糙度 PBR、传统的高光-光泽度 (Phong)，或用于 UI 和装饰性叠加层的无光照渲染 (decor ，它还会将对象放在 decor 层并禁用阴影)。材质还携带纹理绑定（颜色、法线、金属度、粗糙度、遮蔽、打包的 ORM、自发光）、UV 缩放/偏移、选中高亮 (selected)，以及用于分割和求解器岛可视化的对象/岛 ID。

    Material: mjrf_setRenderableMaterial applies an mjrfMaterial struct, which selects between three shading models: metallic-roughness PBR, legacy specular-glossiness (Phong), or unlit rendering for UI and decorative overlays (decor, which also places the object on the decor layer and disables shadows). The material also carries texture bindings (color, normal, metallic, roughness, occlusion, packed ORM, emissive), UV scale/offset, selection highlighting (selected), and object/island IDs for segmentation and solver-island visualization.

  • 位姿、尺寸与阴影： 每一帧，mjrf_setRenderablePose 就地更新可渲染对象的 3D 位置和旋转矩阵，mjrf_setRenderableSize 更新其缩放（处理非均匀的基元缩放，例如保持胶囊体端帽为球形），mjrf_setRenderableCastShadow 切换其是否投射阴影。可渲染对象通过 mjrf_addSceneRenderable 和 mjrf_removeSceneRenderable 添加到场景或从场景中移除。

    Pose, size, and shadows: On each frame, mjrf_setRenderablePose updates the renderable’s 3D position and rotation matrix in place, mjrf_setRenderableSize updates its scale (handling non-uniform primitive scaling such as keeping capsule end-caps spherical), and mjrf_setRenderableCastShadow toggles whether it casts shadows. Renderables are added to or removed from a scene with mjrf_addSceneRenderable and mjrf_removeSceneRenderable.
光源 (mjrfLight)
Lights (mjrfLight)

mjrfLight 表示通过 mjrf_addSceneLight 添加到场景的平行光、聚光灯、点光源或基于图像的（IBL 环境立方体贴图）光源。它们的位姿、强度（单位为坎德拉）、颜色和阴影贴图分辨率都可以动态更新。请注意，与相机对齐的 头灯 是在 mjrfRenderRequest 上指定的（强度单位为勒克斯），而不是作为场景光源，因此从多个相机渲染同一场景时不会让各视图相互照亮。

mjrfLight represents directional, spot, point, or image-based (IBL environment cubemap) light sources added to a scene via mjrf_addSceneLight. Their poses, intensities (in candela), colors, and shadow map resolutions can be updated dynamically. Note that the camera-aligned headlight is specified on mjrfRenderRequest (with intensity in lux) rather than as a scene light, so rendering the same scene from multiple cameras does not cross-illuminate views.
渲染目标、请求与帧句柄 (mjrfRenderTarget, mjrfRenderRequest, mjrfReadRequest)
Render targets, requests, and frame handles (mjrfRenderTarget, mjrfRenderRequest, mjrfReadRequest)

渲染通过 mjrf_render 成批提交。每个 mjrfRenderRequest 将一个 mjrfScene 与相机 (mjrCamera)、视口、可选的离屏 mjrfRenderTarget (使用原生窗口时为 NULL)、绘制模式 (mjrDrawMode，取值包括默认、无纹理、线框、深度、求解器岛，或按 ID/颜色分割) 以及每视图标志（阴影、反射、后处理、头灯）配对。由于相机和绘制模式属于请求而不是场景，因此单个保留的 mjrfScene 可以在一次调用中从多个相机或以多种绘制模式渲染。离屏像素回读与渲染请求一同通过 mjrfReadRequest 请求。mjrf_render 将工作分派到专用的渲染线程，并返回一个 mjrfFrameHandle ，调用方通过 mjrf_waitForFrame 对其进行同步。尽管使用了内部渲染线程， mjrf API 并不是线程安全的，所有调用都必须来自同一个线程。

Rendering is submitted in batches via mjrf_render. Each mjrfRenderRequest pairs an mjrfScene with a camera (mjrCamera), viewport, optional offscreen mjrfRenderTarget (or NULL for the native window), draw mode (mjrDrawMode: default, no-textures, wireframe, depth, solver islands, or segmentation by ID/color), and per-view flags (shadows, reflections, post-processing, headlight). Because camera and draw mode belong to the request rather than the scene, a single retained mjrfScene can be rendered from multiple cameras or in multiple draw modes in one call. Offscreen pixel readbacks are requested alongside render requests via mjrfReadRequest. mjrf_render dispatches work to a dedicated render thread and returns an mjrfFrameHandle, which the caller synchronizes on with mjrf_waitForFrame. Despite using an internal render thread, the mjrf API is not thread-safe and all calls must be made from a single thread.

支持层#

Support layer

虽然应用程序可以直接管理底层的 mjrf 对象，但大多数 MuJoCo 应用程序使用 src/render/filament/support 中的支持层 (以及用于 RAII UniquePtr 封装器的 support/mjrf_ptr.h)，它同样在 Python 的 mujoco.mjrf 下公开：

While applications can manage low-level mjrf objects directly, most MuJoCo applications use the support layer in src/render/filament/support (and support/mjrf_ptr.h for RAII UniquePtr wrappers), which is also exposed in Python under mujoco.mjrf:

  • ModelResources ：根据 mjModel 创建并拥有所有 mjrfMesh 资源（网格、凸包和高度场）以及 mjrfTexture 资源，并支持动态重新上传修改后的资源。

    ModelRenderables: Creates persistent mjrfRenderable entities for all model geoms, sites, skins, flexes, and spatial tendons. Calling Update(data) updates their poses, sizes, and dynamic material properties in place from mjData without constructing an mjvScene, while SetOptions(opt) applies group and category visibility from mjvOption.

  • ModelDecorations ：桥接抽象可视化器，用于瞬态装饰几何。由于装饰性叠加层（接触力箭头、惯性盒、关节/执行器轴、扰动系绳、文本标签）是每帧以程序方式生成的，而不是作为持久的模型元素存储， ModelDecorations 在内部调用 mjv_updateScene，并且只将 mjCAT_DECOR geom（以及非蒙皮的 flex 调试线框）转换为临时的 decor 可渲染对象。Filament 渲染器没有 2D 文本 API；文本标签改为报告给传递给 Update() 的可选回调，由应用程序负责绘制 (参见 render.cc 中的 DrawBitmapText())。

    ModelDecorations: Bridges the abstract visualizer for transient decorative geometry. 场景编写#

Authoring scenes

经典渲染器 实现了传统的 Phong 光照模型：表面颜色是环境光、漫反射、镜面反射和自发光各项之和，光强是凭目测调节的无量纲数值。现代基于物理的渲染（PBR）引擎用可经验测量的属性描述表面，用光度学单位描述光源。由于材质和光照参数都是物理量，资源在不同场景和光照条件下能保持其外观，并且诸如 基于图像的光照 和逼真的金属等效果成为可能。有关底层理论的介绍，参见 Filament 的 PBR 文档。

The classic renderer implements a traditional Phong lighting model: surface color is a sum of ambient, diffuse, specular and emissive terms, and light intensities are dimensionless values tuned by eye. Modern physically-based rendering (PBR) engines describe surfaces with empirically measurable properties and lights with photometric units. Because material and lighting parameters are physical, assets retain their appearance across scenes and lighting conditions, and effects like image-based lighting and realistic metals become possible. For an introduction to the underlying theory, see Filament’s PBR documentation.

Filament 渲染器同时支持这两种模型。总体而言，我们建议使用现代 PBR（例如金属度-粗糙度）方法编写场景，以获得最佳效果。不过，我们假定许多现有模型是为经典渲染器编写的，因此默认使用 Filament 基于 PBR 的 Phong 着色近似。这种后备模式已经过调校，可产生合理的结果，但最终图像与经典渲染器相比可能存在显著差异。这两个决定（如何对材质着色以及如何为场景打光）是相互独立做出的，下文将分别介绍。

The Filament renderer supports both models. In general, we recommend that scenes are authored with modern PBR (e.g. metallic-roughness) methods to produce the best results. However, we assume that many existing models are authored for the classic renderer and so we default to using Filament’s PBR-based approximation of Phong shading. This fallback mode has been tuned to produce reasonable results, but the final image can vary significantly compared to the classic renderer. The two decisions, how to shade materials and how to light the scene, are made independently and are described below.

OpenGL 渲染#

OpenGL rendering

经典的 OpenGL 渲染器（mjr）接收在 可视化 阶段填充的 mjvScene 数据结构并对其进行渲染。它还提供基本的二维绘制和帧缓冲区访问，因此大多数应用程序无需直接调用 OpenGL。它处于维护模式；新的应用程序应优先使用 Filament 渲染器。

The classic OpenGL renderer (mjr) takes the mjvScene data structure populated in the Visualization stage and renders it. It also provides basic 2D drawing and framebuffer access, so that most applications do not need to call OpenGL directly. It is in maintenance mode; new applications should prefer the Filament renderer.

mjvOption opt;                      // visualization options
mjvScene scn;                       // abstract scene
mjrContext con;                     // custom GPU context

// ... load model and data

// init GLFW, create window, make OpenGL context current, request v-sync
glfwInit();
GLFWwindow* window = glfwCreateWindow(1200, 900, "Demo", NULL, NULL);
glfwMakeContextCurrent(window);
glfwSwapInterval(1);

// initialize visualization data structures
mjv_defaultCamera(&cam);
mjv_defaultPerturb(&pert);
mjv_defaultOption(&opt);
mjr_defaultContext(&con);

// create scene and context
mjv_makeScene(m, &scn, 1000);
mjr_makeContext(m, &con, mjFONTSCALE_100);

// ... install GLFW keyboard and mouse callbacks

// run main loop, target real-time simulation and 60 fps rendering
while( !glfwWindowShouldClose(window) ) {
  // advance interactive simulation for 1/60 sec
  //  Assuming MuJoCo can simulate faster than real-time, which it usually can,
  //  this loop will finish on time for the next frame to be rendered at 60 fps.
  //  Otherwise add a cpu timer and exit this loop when it is time to render.
  mjtNum simstart = d->time;
  while( d->time - simstart < 1.0/60.0 )
      mj_step(m, d);

  // get framebuffer viewport
  mjrRect viewport = {0, 0, 0, 0};
  glfwGetFramebufferSize(window, &viewport.width, &viewport.height);

  // update scene and render
  mjv_updateScene(m, d, &opt, NULL, &cam, mjCAT_ALL, &scn);
  mjr_render(viewport, &scn, &con);

  // swap OpenGL buffers (blocking call due to v-sync)
  glfwSwapBuffers(window);

  // process pending GUI events, call GLFW callbacks
  glfwPollEvents();
}

// close GLFW, free visualization storage
glfwTerminate();
mjv_freeScene(&scn);
mjr_freeContext(&con);

// ... free MuJoCo model and data

使用 OpenGL#

Using OpenGL

MuJoCo 使用兼容性配置文件（compatibility profile）下的 OpenGL 1.5，并带有 ARB_framebuffer_object 和 ARB_vertex_buffer_object 扩展。OpenGL 符号在首次调用 mjr_makeContext 函数时通过 GLAD 加载。这意味着 MuJoCo 库本身并不显式依赖 OpenGL，只要不调用 mjr_ 函数，就可以在没有 OpenGL 支持的系统上使用。

MuJoCo uses OpenGL 1.5 in the compatibility profile with the ARB_framebuffer_object and ARB_vertex_buffer_object extensions. OpenGL symbols are loaded via GLAD the first time the mjr_makeContext function is called. This means that the MuJoCo library itself does not have an explicit dependency on OpenGL and can be used on systems without OpenGL support, as long as mjr_ functions are not called.

使用 MuJoCo 内置渲染功能的应用程序，需要自行负责链接合适的 OpenGL 上下文创建库，并确保在运行的线程上存在一个已设为当前的 OpenGL 上下文。在 Windows 和 macOS 上，操作系统提供了标准的 OpenGL 库。在 Linux 上，MuJoCo 目前支持用于渲染到 X11 窗口的 GLX、用于无头软件渲染的 OSMesa，以及用于硬件加速无头渲染的 EGL。

Applications that use MuJoCo’s built-in rendering functionalities are responsible for linking against an appropriate OpenGL context creation library and for ensuring that there is an OpenGL context that is made current on the running thread. On Windows and macOS, there is a canonical OpenGL library provided by the operating system. On Linux, MuJoCo currently supports GLX for rendering to an X11 window, OSMesa for headless software rendering, and EGL for hardware accelerated headless rendering.

Context and GPU resources

渲染过程的第一步是创建特定于模型的 GPU 上下文 mjrContext。具体做法是先用函数 mjr_defaultContext 清空该数据结构，然后调用函数 mjr_makeContext。前面已经演示过这一点；相关代码如下：

The first step in the rendering process is to create the model-specific GPU context mjrContext. This is done by first clearing the data structure with the function mjr_defaultContext, and then calling the function mjr_makeContext. This was already illustrated earlier; the relevant code is:
mjModel* m;
mjrContext con;

// clear mjrContext only once before first use
mjr_defaultContext(&con);

// create window with OpenGL context, make it current
GLFWwindow* window = glfwCreateWindow(1200, 900, "Demo", NULL, NULL);
glfwMakeContextCurrent(window);

// ... load MuJoCo model

// make model-specific mjrContext
mjr_makeContext(m, &con, mjFONTSCALE_100);

// ... load another MuJoCo model

// make mjrContext for new model (old context freed automatically)
mjr_makeContext(m, &con, mjFONTSCALE_100);

// free context when done
mjr_freeContext(&con);

mjrContext 与 OpenGL 上下文是什么关系？OpenGL 上下文使应用程序能够与显卡驱动通信并发送渲染命令。在调用 mjr_makeContext 之前，它必须已经存在，并且已在调用线程中设为当前。GLFW 及相关库提供了如上所示的必要函数。

How is mjrContext related to an OpenGL context? An OpenGL context is what enables the application to talk to the video driver and send rendering commands. It must exist and must be current in the calling thread before mjr_makeContext is called. GLFW and related libraries provide the necessary functions as shown above.

mjrContext 是 MuJoCo 特有的。创建之后，它包含对 mjr_makeContext 上传到 GPU 的所有资源的引用（在 OpenGL 中称为“名称”）。这些资源包括网格和纹理等特定于模型的资源，也包括通用资源，例如指定字体缩放比例下的字体位图、用于阴影映射和离屏渲染的帧缓冲对象，以及相关的渲染缓冲区。它还包含从 mjModel.vis 复制而来的与 OpenGL 相关的选项、自动发现的默认窗口帧缓冲区的能力，以及当前用于渲染的活动缓冲区；参见下面的 缓冲区。请注意，尽管 MuJoCo 使用固定功能的 OpenGL，但它避免了立即模式渲染，而是预先把所有资源上传到 GPU。这使它与现代着色器一样高效，甚至可能更高效，因为固定功能的 OpenGL 如今是通过由显卡驱动开发者编写并经过大量调优的内部着色器来实现的。

mjrContext is specific to MuJoCo. After creation, it contains references (called “names” in OpenGL) to all the resources that were uploaded to the GPU by mjr_makeContext. These include model-specific resources such as meshes and textures, as well as generic resources such as font bitmaps for the specified font scale, framebuffer objects for shadow mapping and offscreen rendering, and associated renderbuffers. It also contains OpenGL-related options copied from mjModel.vis, capabilities of the default window framebuffer that are discovered automatically, and the currently active buffer for rendering; see buffers below. Note that even though MuJoCo uses fixed-function OpenGL, it avoids immediate mode rendering and instead uploads all resources to the GPU upfront. This makes it as efficient as a modern shader, and possibly more efficient, because fixed-function OpenGL is now implemented via internal shaders that have been written by the video driver developers and tuned extensively.

mjrContext 的大多数字段在调用 mjr_makeContext 之后保持不变。唯一的例外是 mjrContext.currentBuffer，它在活动缓冲区改变时随之改变。部分 GPU 资源也可能发生变化，因为用户可以通过函数 mjr_uploadTexture、mjr_uploadMesh、mjr_uploadHField 上传修改后的资源。这可用于实现动态效果，例如把视频画面插入渲染，或者调制地形图。此类修改会影响驻留在 GPU 上的资源，但它们的 OpenGL 名称会被复用；因此，这种变化实际上在 mjrContext 中是不可见的。

Most of the fields of mjrContext remain constant after the call to mjr_makeContext. The only exception is mjrContext.currentBuffer which changes whenever the active buffer changes. Some of the GPU resources may also change because the user can upload modified resources with the functions mjr_uploadTexture, mjr_uploadMesh, mjr_uploadHField. This can be used to achieve dynamic effects such as inserting a video feed into the rendering, or modulating a terrain map. Such modifications affect the resources residing on the GPU, but their OpenGL names are reused; thus, the change is not actually visible in mjrContext.

用户 绝不 应直接修改 mjrContext。MuJoCo 的渲染器假定只有它自己可以管理 mjrContext。事实上，这类对象通常是不透明的，其内部结构不会暴露给用户。我们之所以将其暴露，是因为 MuJoCo 采用开放式设计，同时也因为用户可能希望把自己的 OpenGL 代码与 MuJoCo 的渲染器交错使用，在这种情况下他们可能需要对 mjrContext 的某些字段具有读取权限。例如在 VR 应用中，用户需要把 MuJoCo 的离屏缓冲区位块传输（blit）到 VR SDK 提供的纹理上。

The user should never make changes to mjrContext directly. MuJoCo’s renderer assumes that only it can manage mjrContext. In fact this kind of object would normally be opaque and its internal structure would not be exposed to the user. We are exposing it because MuJoCo has an open design and also because users may want to interleave their own OpenGL code with MuJoCo’s renderer, in which case they may need read access to some fields of mjrContext. For example in VR applications the user needs to blit from MuJoCo’s offscreen buffer to a texture provided by a VR SDK.

当加载另一个 MuJoCo 模型时，必须再次调用 mjr_makeContext。另外还有函数 mjr_freeContext，它释放 GPU 资源，同时保留初始化标志和能力标志。应用程序即将退出时应调用该函数。mjr_makeContext 内部会自动调用它，因此在加载另一个模型时无需直接调用，尽管直接调用也不算错误。函数 mjr_defaultContext 必须在渲染开始前调用一次，用于清空为数据结构 mjrContext 分配的内存。如果在调用 mjr_makeContext 之后再调用它，它会抹去所有已分配 GPU 资源的记录，而不会释放这些资源，因此不要那样做。

When a different MuJoCo model is loaded, mjr_makeContext must be called again. There is also the function mjr_freeContext which frees the GPU resources while preserving the initialization and capabilities flags. This function should be called when the application is about to exit. It is called automatically from within mjr_makeContext, so you do not need to call it directly when a different model is loaded, although it is not an error to do so. The function mjr_defaultContext must be called once before rendering starts, to clear the memory allocated for the data structure mjrContext. If you call it after calling mjr_makeContext, it will wipe out any record that GPU resources were allocated without freeing those resources, so don’t do that.

渲染缓冲区#

Buffers for rendering

除默认的窗口帧缓冲区之外，OpenGL 还可以支持数量不限的帧缓冲对象（FBO）用于自定义渲染。在 MuJoCo 中，我们系统地支持两个帧缓冲区：默认的窗口帧缓冲区和一个离屏帧缓冲区。它们由枚举类型 mjtFramebuffer 中的常量引用，即 mjFB_WINDOW 和 mjFB_OFFSCREEN。在任一时刻，这两个缓冲区之一对 MuJoCo 渲染而言处于活动状态，也就是说所有后续命令都会被导向该缓冲区。mjrContext 中还引用了另外两个帧缓冲对象，用于阴影映射和解析多重采样缓冲区，但它们仅供内部使用，用户不应尝试直接访问。

In addition to the default window framebuffer, OpenGL can support unlimited framebuffer objects (FBOs) for custom rendering. In MuJoCo we provide systematic support for two framebuffers: the default window framebuffer, and one offscreen framebuffer. They are referred to by the constants in the enum type mjtFramebuffer, namely mjFB_WINDOW and mjFB_OFFSCREEN. At any time, one of these two buffers is active for the purposes of MuJoCo rendering, meaning that all subsequent commands are directed to it. There are two additional framebuffer objects referenced in mjrContext, needed for shadow mapping and resolving multi-sample buffers, but these are used internally and the user should not attempt to access them directly.

活动缓冲区通过函数 mjr_setBuffer 设置。它会设置 mjrContext.activeBuffer 的值，并相应地配置 OpenGL 状态。调用 mjr_makeContext 时，其内部会以参数 mjFB_WINDOW 调用 mjr_setBuffer，因此渲染默认从窗口缓冲区开始。如果指定的缓冲区不存在，mjr_setBuffer 会自动默认使用另一个缓冲区（请注意，在 Linux 上使用无头渲染时，可能没有窗口帧缓冲区）。

The active buffer is set with the function mjr_setBuffer. This sets the value of mjrContext.activeBuffer and configures the OpenGL state accordingly. When mjr_makeContext is called, internally it calls mjr_setBuffer with argument mjFB_WINDOW, so that rendering starts in the window buffer by default. If the specified buffer does not exist, mjr_setBuffer automatically defaults to the other buffer (note that when using headless rendering on Linux, there may be no window framebuffer).

从 OpenGL 的角度来看，窗口帧缓冲区与离屏帧缓冲区之间存在重要差异，这些差异会影响 MuJoCo 用户与渲染器的交互方式。窗口帧缓冲区由操作系统而非 OpenGL 创建和管理。因此，分辨率、双缓冲、四缓冲立体、多重采样、垂直同步等属性是在 OpenGL 之外设置的；在我们的代码示例中，这是通过 GLFW 调用完成的。OpenGL 所能做的只是检测这些属性；我们在 mjr_makeContext 中做这件事，并将结果记录在 mjrContext 的各个窗口能力字段中。这就是此类属性不属于 MuJoCo 模型的原因；它们特定于会话/软件，而不是特定于模型。相比之下，离屏帧缓冲区完全由 OpenGL 管理，因此我们可以按任意所需的属性创建该缓冲区，即采用 mjModel.vis 中指定的分辨率和多重采样属性。

From the perspective of OpenGL, there are important differences between the window framebuffer and offscreen framebuffer, and these differences affect how the MuJoCo user interacts with the renderer. The window framebuffer is created and managed by the operating system and not by OpenGL. As a result, properties such as resolution, double-buffering, quad-buffered stereo, multi-samples, v-sync are set outside OpenGL; this is done by GLFW calls in our code samples. All OpenGL can do is detect these properties; we do this in mjr_makeContext and record the results in the various window capabilities fields of mjrContext. This is why such properties are not part of the MuJoCo model; they are session/software-specific and not model-specific. In contrast, the offscreen framebuffer is managed entirely by OpenGL, and so we can create that buffer with whatever properties we want, namely with the resolution and multi-sample properties specified in mjModel.vis.

用户可以直接访问这两个缓冲区中的像素。这通过函数 mjr_readPixels、mjr_drawPixels 和 mjr_blitBuffer 完成。读取/绘制是在活动缓冲区与 CPU 之间传输像素。位块传输（blit）则在 GPU 上的两个缓冲区之间传输像素，因此要快得多。传输方向是从活动缓冲区到非活动缓冲区。请注意，mjr_blitBuffer 的源视口和目标视口可以具有不同的大小，从而允许在此过程中缩放图像。

The user can directly access the pixels in the two buffers. This is done with the functions mjr_readPixels, mjr_drawPixels and mjr_blitBuffer. Read/draw transfer pixels from/to the active buffer to/from the CPU. Blit transfers pixels between the two buffers on the GPU and is therefore much faster. The direction is from the active buffer to the buffer that is not active. Note that mjr_blitBuffer has source and destination viewports that can have different size, allowing the image to be scaled in the process.

绘制像素#

Drawing pixels

主要的渲染函数是 mjr_render。它的参数是用于渲染的矩形视口、由抽象可视化器填充的 mjvScene，以及由 mjr_makeContext 创建的 mjrContext。视口可以是整个活动缓冲区，也可以是其一部分，以实现自定义效果。对应整个缓冲区的视口可以通过函数 mjr_maxViewport 获得。请注意，离屏缓冲区的大小不变，而窗口缓冲区的大小会在用户调整窗口大小或将其最大化时改变。因此用户代码不应假定视口大小固定。在代码示例 simulate.cc 中，我们使用了一个在窗口大小改变时触发的回调，而在 basic.cc 中，我们只是在每次渲染时检查窗口大小。在某些缩放显示器上（尤其是 MacOS），窗口大小与帧缓冲区大小可能不同。因此，如果您使用 GLFW 函数获取大小，请使用 glfwGetFramebufferSize 而不是 glfwGetWindowSize。另一方面，鼠标坐标由操作系统以窗口单位而非帧缓冲区单位返回；因此 鼠标交互函数 应使用 glfwGetWindowSize 来获取对鼠标位移数据做归一化所需的窗口高度。

The main rendering function is mjr_render. Its arguments are a rectangular viewport for rendering, the mjvScene which was populated by the abstract visualizer, and the mjrContext which was created by mjr_makeContext. The viewport can be the entire active buffer, or part of it for custom effects. A viewport corresponding to the entire buffer can be obtained with the function mjr_maxViewport. Note that while the offscreen buffer size does not change, the window buffer size changes whenever the user resizes or maximizes the window. Therefore user code should not assume fixed viewport size. In the code sample simulate.cc we use a callback which is triggered whenever the window size changes, while in basic.cc we simply check the window size every time we render. On certain scaled displays (notably on MacOS) the window size and framebuffer size can be different. So if you are getting the size with GLFW functions, use glfwGetFramebufferSize rather than glfwGetWindowSize. On the other hand, mouse coordinates are returned by the operating system in window rather than framebuffer units; thus the mouse interaction functions should use glfwGetWindowSize to obtain the window height needed to normalize the mouse displacement data.

mjr_render 渲染列表 mjvScene.geom 中的所有 mjvGeom。抽象可视化选项 mjvOption 在这里已不再相关；它们被 mjv_updateScene 用来确定要添加哪些 geom，对 mjr_render 而言，这些选项已经固化。不过，mjvScene 中还嵌入了另一组渲染选项，它们会影响 OpenGL 渲染过程。数组 mjvScene.flags 包含以枚举类型 mjtRndFlag 为索引的标志，其中的选项用于启用和禁用线框模式、阴影、反射、天空盒和雾。阴影和反射需要额外的渲染通道。MuJoCo 的渲染器非常高效，但根据模型复杂度和可用 GPU 的不同，在某些情况下可能需要禁用其中一种或两种效果。

mjr_render renders all mjvGeoms from the list mjvScene.geom. The abstract visualization options mjvOption are no longer relevant here; they are used by mjv_updateScene to determine which geoms to add, and as far as mjr_render is concerned these options are already baked-in. There is however another set of rendering options that are embedded in mjvScene, and these affect the OpenGL rendering process. The array mjvScene.flags contains flags indexed by the enum type mjtRndFlag and include options for enabling and disabling wireframe mode, shadows, reflections, skyboxes and fog. Shadows and reflections involve additional rendering passes. MuJoCo’s renderer is very efficient, but depending on the model complexity and available GPU, it may be necessary to disable one or both of these effects in some cases.

参数 mjvScene.stereo 决定立体模式。其可能取值由枚举类型 mjtStereo 给出，如下所示：

The parameter mjvScene.stereo determines the stereo mode. The possible values are given by the enum type mjtStereo and are as follows:
mjSTEREO_NONE

禁用立体渲染。使用 mjvScene 中两个 OpenGL 相机的平均值。请注意，即使不使用立体渲染，渲染器也始终要求两个相机都被正确定义。

Stereo rendering is disabled. The average of the two OpenGL cameras in mjvScene is used. Note that the renderer always expects both cameras to be properly defined, even if stereo is not used.
mjSTEREO_QUADBUFFERED

该模式仅在活动缓冲区是窗口、且窗口支持四缓冲 OpenGL 时才有效。这需要专业显卡。代码示例 simulate.cc 会尝试打开这样的窗口。在此模式下，当窗口为双缓冲时，MuJoCo 的渲染器使用 GL_BACK_LEFT 和 GL_BACK_RIGHT 缓冲区渲染两个视图（由 mjvScene 中的两个 OpenGL 相机确定），否则使用 GL_FRONT_LEFT 和 GL_FRONT_RIGHT。如果窗口不支持四缓冲 OpenGL，或者活动缓冲区是离屏缓冲区，渲染器会退回到下面描述的并排模式。

This mode works only when the active buffer is the window, and the window supports quad-buffered OpenGL. This requires a professional video card. The code sample simulate.cc attempts to open such a window. In this mode MuJoCo’s renderer uses the GL_BACK_LEFT and GL_BACK_RIGHT buffers to render the two views (as determined by the two OpenGL cameras in mjvScene) when the window is double-buffered, and GL_FRONT_LEFT and GL_FRONT_RIGHT otherwise. If the window does not support quad-buffered OpenGL or the active buffer is the offscreen buffer, the renderer reverts to the side-by-side mode described next.
mjSTEREO_SIDEBYSIDE

这种立体模式不需要特殊硬件，始终可用。传给 mjr_render 的视口会被并排分成两个相等的矩形。左视图渲染在左侧，右视图渲染在右侧。原则上，用户可以通过斗鸡眼在普通显示器上看到立体效果，但这里的目标是在立体显示设备中呈现。大多数头戴式显示器都支持这种立体模式。

This stereo mode does not require special hardware and is always available. The viewport given to mjr_render is split in two equal rectangles side-by-side. The left view is rendered on the left side and the right view on the right side. In principle users can cross their eyes and see stereo on a regular monitor, but the goal here is to show it in a stereoscopic device. Most head-mounted displays support this stereo mode.

除了主要的 mjr_render 函数之外，我们还提供了若干用于“装饰”图像的函数。这些是二维渲染函数，包括 mjr_overlay、mjr_text、mjr_rectangle 和 mjr_figure。用户可以用自己的 OpenGL 代码绘制额外的装饰。这应当在 mjr_render 之后进行，因为 mjr_render 会清空视口。

In addition to the main mjr_render function, we provide several functions for “decorating” the image. These are 2D rendering functions and include mjr_overlay, mjr_text, mjr_rectangle, and mjr_figure. The user can draw additional decorations with their own OpenGL code. This should be done after mjr_render, because mjr_render clears the viewport.

我们还提供函数 mjr_finish 和 mjr_getError，分别用于与 GPU 的显式同步和 OpenGL 错误检查。它们在内部只是简单地调用 glFinish 和 glGetError。这些函数连同上面的基本二维绘制函数，旨在提供足够的功能，使大多数用户无需编写 OpenGL 代码。当然，除非为 OpenGL 的全部功能都提供封装，否则我们无法在所有情况下都做到这一点。

We also provide the functions mjr_finish and mjr_getError for explicit synchronization with the GPU and for OpenGL error checking. They simply call glFinish and glGetError internally. This together with the basic 2d drawing functions above is meant to provide enough functionality so that most users will not need to write OpenGL code. Of course we cannot achieve this in all cases, short of providing wrappers for all of OpenGL.
