简介#

Introduction

本章是 MuJoCo 编程指南。独立的一章包含 API 参考 文档。MuJoCo 是兼容 Windows、Linux 和 macOS 的动态库，需要支持 AVX 指令的处理器。该库通过与编译器无关的共享内存 C API 公开模拟器的全部功能，也可以在 C++ 程序中使用。

This chapter is the MuJoCo programming guide. A separate chapter contains the API Reference documentation. MuJoCo is a dynamic library compatible with Windows, Linux and macOS, which requires a processor with AVX instructions. The library exposes the full functionality of the simulator through a compiler-independent shared-memory C API. It can also be used in C++ programs.

MuJoCo 代码库按照不同的主要功能领域组织为若干子目录：

The MuJoCo codebase is organized into subdirectories corresponding to different major areas of functionality:
引擎（Engine）
Engine

模拟器（或物理引擎）用 C 语言编写，负责所有运行时计算。

The simulator (or physics engine) is written in C. It is responsible for all runtime computations.
解析器（Parser）
Parser

XML 解析器用 C++ 编写，可以解析 MJCF 模型和 URDF 模型，并将其转换为内部的 mjCModel C++ 对象，该对象通过 mjSpec 向用户公开。

The XML parser is written in C++. It can parse MJCF models and URDF models, converting them into an internal mjCModel C++ object which is exposed to the user via mjSpec.
编译器（Compiler）
Compiler

编译器用 C++ 编写，它接收由解析器构建的 mjCModel C++ 对象，并将其转换为运行时使用的 mjModel C 结构体。

The compiler is written in C++. It takes an mjCModel C++ object constructed by the parser, and converts it into an mjModel C structure used at runtime.
线程（Thread）
Thread

线程框架用 C++ 编写并以 C 接口公开，提供用于异步处理任务的线程池接口。要在 MuJoCo 中启用，请调用 mju_threadpool。

The threading framework is written in C++ and exposed in C. It provides a thread pool interface to process tasks asynchronously. To enable use in MuJoCo, call mju_threadpool.
抽象可视化器（Abstract visualizer）
Abstract visualizer

抽象可视化器用 C 编写，与任何图形库无关。它提供用于相机和扰动控制、对象选择以及可视化（visualization）选项的抽象鼠标钩子，并生成一个抽象几何实体列表，用于表示仿真状态及其装饰。两个渲染器都会共用它。

The abstract visualizer is written in C and is independent of any graphics library. It provides abstract mouse hooks for camera and perturbation control, object selection, visualization options, and generates a list of abstract geometric entities representing the simulation state and its decorations. It is shared by both renderers.
渲染（Rendering）
Rendering

MuJoCo 提供了两个渲染（rendering）库。经典渲染 库用 C 编写，使用 OpenGL 1.5，提供了一种简单高效的方式来可视化 MuJoCo 模型。filament 渲染 库用 C++ 编写，使用外部开发的 Filament 渲染引擎，提供更现代、功能更丰富的实时渲染能力。

There are two rendering libraries provided by MuJoCo. The classic rendering library is written in C and uses OpenGL 1.5. It provides a simple and efficient way to visualize MuJoCo models. The filament rendering library is written in C++ and uses the externally-developed Filament rendering engine. It provides more modern and feature-rich real-time rendering capabilities.
UI 框架（UI framework）
UI framework

UI 框架用 C 编写，设计用于配合 经典 OpenGL 渲染器 工作。UI 元素通过 OpenGL 渲染。它有自己的事件机制，以及用于键盘和鼠标输入的抽象钩子。代码示例将其与 GLFW 一起使用，但它也可以与其他窗口库配合使用。

The UI framework is written in C and is designed to work with the classic OpenGL renderer. UI elements are rendered in OpenGL. It has its own event mechanism and abstract hooks for keyboard and mouse input. The code samples use it with GLFW, but it can also be used with other window libraries.

快速入门#

Getting started

无需安装任何东西即可在浏览器中试用 MuJoCo，请访问 mujoco.org，或在 live.mujoco.org 打开并拖放你自己的模型，该网站运行的是 MuJoCo Studio 应用的 WebAssembly 版本。

To try MuJoCo in your browser with nothing to install, visit mujoco.org, or open and drag and drop your own models at live.mujoco.org, which runs the WebAssembly version of the MuJoCo Studio app.

MuJoCo 是一个开源项目。适用于运行 Windows、Linux 和 macOS 的 x86_64 和 arm64 机器的预编译动态库均已提供。这些库可以从 GitHub Releases 页面 下载。不打算开发或修改 MuJoCo 核心代码的用户，建议使用我们的预编译库，因为它们捆绑了我们定期测试所用的相同版本的依赖项，并受益于为性能而调优的构建标志。我们的预编译库几乎完全自包含，除标准 C 运行时之外，不需要存在任何其他库。我们还隐藏了构成 MuJoCo 公共 API 的符号之外的所有符号，从而确保它能与进程中可能加载的任何其他库（包括 MuJoCo 所依赖的库的其他版本）共存。

MuJoCo is an open-source project. Pre-built dynamic libraries are available for x86_64 and arm64 machines running Windows, Linux, and macOS. These can be downloaded from the GitHub Releases page. Users who do not intend to develop or modify core MuJoCo code are encouraged to use our pre-built libraries, as these come bundled with the same versions of dependencies that we regularly test against, and benefit from build flags that have been tuned for performance. Our pre-built libraries are almost entirely self-contained and do not require any other library to be present, outside the standard C runtime. We also hide all symbols apart from those that form MuJoCo’s public API, thus ensuring that it can coexist with any other libraries that may be loaded into the process (including other versions of libraries that MuJoCo depends on).

预编译发行版在 macOS 上是单个 .dmg，在 Windows 上是 .zip，在 Linux 上是 .tar.gz；没有安装程序。在 macOS 和 Windows 上，MuJoCo Studio 和 simulate 都被打包为独立的桌面应用程序 (macOS .dmg 中的 MuJoCoStudio.app 和 MuJoCo.app；Windows .zip 中的 bin\mujoco_studio.exe 和 bin\simulate.exe)，可以双击启动，并将模型文件拖放到其上。

The pre-built distribution is a single .dmg on macOS, .zip on Windows, and .tar.gz on Linux; there is no installer. On macOS and Windows, both MuJoCo Studio and simulate are packaged as standalone desktop applications (MuJoCoStudio.app and MuJoCo.app in the macOS .dmg; bin\mujoco_studio.exe and bin\simulate.exe in the Windows .zip) that you can double-click to launch and drop model files onto.

在 Windows 和 Linux 上，将压缩包解压到你选择的目录。在 bin 子目录的终端中，也可以运行 MuJoCo Studio 或 simulate 等预编译的代码示例：

On Windows and Linux, extract the archive in a directory of your choice. From a terminal in the bin subdirectory, you can also run MuJoCo Studio or the precompiled code samples such as simulate:
Windows:   mujoco_studio ..\model\humanoid\humanoid.xml
Linux:     ./mujoco_studio ../model/humanoid/humanoid.xml

Windows 和 Linux 压缩包的目录结构如下所示。用户可以根据需要重新组织，也可以将动态库安装到其他目录并相应地设置路径。唯一自动创建的文件是可执行文件目录中的 MUJOCO_LOG.TXT；它包含错误和警告消息，可以随时删除。

The directory structure of the Windows and Linux archives is shown below. Users can re-organize it if needed, as well as install the dynamic libraries in other directories and set the path accordingly. The only file created automatically is MUJOCO_LOG.TXT in the executable directory; it contains error and warning messages, and can be deleted at any time.
bin     - dynamic libraries, executables, MUJOCO_LOG.TXT
doc     - README.txt and REFERENCE.txt
include - header files needed to develop with MuJoCo
model   - model collection
sample  - code samples and CMakeLists.txt needed to build them

确认模拟器可以运行之后，你可能还想重新编译代码示例，以确保拥有可用的开发环境。我们提供了跨平台的 CMake 配置，可用于独立于 MuJoCo 库本身构建示例应用程序。

After verifying that the simulator works, you may also want to re-compile the code samples to ensure that you have a working development environment. We provide a cross-platform CMake setup that can be used to build sample applications independently of the MuJoCo library itself.

在 macOS 上，可以将 MuJoCoStudio.app 和 MuJoCo.app 从 .dmg 拖入 /Applications 进行安装，与任何其他 应用程序包 一样 (其 Contents/MacOS/ 中的可执行文件也可以从终端运行)。除应用程序包之外，DMG 还包含 mujoco.framework 子目录，其中有 MuJoCo 动态库及其所有公共头文件。如果你使用 Xcode，可以将其作为框架依赖项导入到你的项目中 (这对 Swift 项目同样适用，无需任何修改)。如果手动构建，可以分别使用 -F 和 -framework mujoco 来指定头文件搜索路径和库搜索路径。

On macOS, you can drag MuJoCoStudio.app and MuJoCo.app from the .dmg into /Applications to install them like any other application bundle (their executables inside Contents/MacOS/ can also be run from a terminal). Alongside the app bundles, the DMG includes the mujoco.framework subdirectory containing the MuJoCo dynamic library and all of its public headers. If you are using Xcode, you can import it as a framework dependency on your project. (This also works for Swift projects without any modification). If you are building manually, you can use -F and -framework mujoco to specify the header search path and the library search path respectively.

从源码构建#

Building from source

从源码构建 MuJoCo 需要安装 CMake 和可用的 C++17 编译器。步骤如下：

To build MuJoCo from source, you will need CMake and a working C++17 compiler installed. The steps are:

  1. 克隆 mujoco 仓库：git clone https://github.com/google-deepmind/mujoco.git

    Clone the mujoco repository: git clone https://github.com/google-deepmind/mujoco.git

  2. 创建一个新的构建目录并 cd 进入该目录。

    Create a new build directory and cd into it.

  3. 运行 cmake $PATH_TO_CLONED_REPO 来配置构建。

    Run cmake $PATH_TO_CLONED_REPO to configure the build.

  4. 运行 cmake --build . 进行构建。

    Run cmake --build . to build.

MuJoCo 的构建系统使用 CMake 的 FetchContent 模块，通过互联网自动从上游仓库获取依赖项。

MuJoCo’s build system automatically fetches dependencies from upstream repositories over the Internet using CMake’s FetchContent module.

主 CMake 配置会构建 MuJoCo 库本身以及所有示例应用程序，但不会构建 Python 绑定。Python 绑定有自己的构建说明，可在文档的 Python 一节中找到。

The main CMake setup will build the MuJoCo library itself along with all sample applications, but the Python bindings are not built. Those come with their own build instructions, which can be found in the Python section of the documentation.

此外，CMake 配置还实现了一个安装阶段，会将输出文件复制并整理到目标目录。

Additionally, the CMake setup also implements an installation phase which will copy and organize the output files to a target directory.

  1. 选择目录：cmake $PATH_TO_CLONED_REPO -DCMAKE_INSTALL_PREFIX=<my_install_dir>

    Select the directory: cmake $PATH_TO_CLONED_REPO -DCMAKE_INSTALL_PREFIX=<my_install_dir>

  2. 构建完成后，使用 cmake --install . 进行安装

    After building, install with cmake --install .

  3. 如有需要，可继续构建 Python 绑定，参见 从源码构建。

    If desired, proceed to building the Python bindings - see Building from source.

注意：

Notes:

  • 若要优化运行时性能，请使用 -DCMAKE_BUILD_TYPE=Release 构建。

    To optimize runtime performance build with -DCMAKE_BUILD_TYPE=Release.

  • 在 Windows 上使用 MSVC 构建时，请使用 Visual Studio 2019 或更高版本，并确保已安装 Windows SDK 10.0.22000 或更高版本 (详见 issue #862)。

    When building on Windows with MSVC, use Visual Studio 2019 or later and make sure Windows SDK version 10.0.22000 or later is installed (see issue #862 for more details).

  • 我们发现，在 Windows 上使用 Clang 而非 MSVC 构建时性能最佳。

    We’ve found that performance on Windows is best when building with Clang, rather than MSVC.

使用 Bazel 构建#

Building with Bazel

MuJoCo 也可以使用 Bazel 8.0 或更高版本构建。其所测试的 Bazel 版本固定在 .bazelversion 中，Bazelisk 会自动使用该版本。要在克隆仓库的根目录构建并测试 MuJoCo：

MuJoCo can also be built with Bazel 8.0 or later. The Bazel version it is tested with is pinned in .bazelversion, which Bazelisk uses automatically. To build and test MuJoCo from the root of the cloned repository:
bazel build //...
bazel test //...

要在你自己的 Bazel 模块中使用 MuJoCo，请将其添加到你的 MODULE.bazel 中。MuJoCo 尚未收录在 Bazel Central Registry 中，因此请使用 override，例如：

To use MuJoCo from your own Bazel module, add it to your MODULE.bazel. MuJoCo isn’t in the Bazel Central Registry yet, so use an override, for example:
bazel_dep(name = "mujoco")
git_override(
    module_name = "mujoco",
    remote = "https://github.com/google-deepmind/mujoco.git",
    commit = "<commit>",
)

主要目标有：

The main targets are:

  • @mujoco：MuJoCo 库。其头文件以 #include <mujoco/mujoco.h> 的方式包含。

    @mujoco: the MuJoCo library. Its headers are included as #include <mujoco/mujoco.h>.

  • @mujoco//:mujoco_shared：作为共享库的 MuJoCo (libmujoco.so，在 macOS 上为 libmujoco.dylib)，与用 CMake 构建的共享库一样，它只导出 MuJoCo API。将其添加到依赖 @mujoco 的 cc_binary 或 cc_shared_library 的 dynamic_deps 中，即可动态链接 MuJoCo，例如与 Python 绑定共享同一份 MuJoCo 副本。

    @mujoco//:mujoco_shared: MuJoCo as a shared library (libmujoco.so, or libmujoco.dylib on macOS) which, like the one built with CMake, exports only the MuJoCo API. Add it to the dynamic_deps of a cc_binary or cc_shared_library that depends on @mujoco to link MuJoCo dynamically, for example to share one copy of MuJoCo with the Python bindings.

  • @mujoco//plugin/<name>:register，其中 <name> 为 actuator、elasticity、sdf 或 sensor：随库提供的插件（plugin），在链接时会自动注册自身。

    @mujoco//plugin/<name>:register, where <name> is actuator, elasticity, sdf or sensor: the bundled plugins, which register themselves when linked in.

  • @mujoco//python/mujoco：Python 绑定，参见 使用 Bazel 构建。

    @mujoco//python/mujoco: the Python bindings, see Building with Bazel.

要像随库提供的插件那样，将你自己的 插件 构建为共享库，请使用 mujoco_plugin 宏。该库链接到 @mujoco//:mujoco_shared 且不导出任何符号；在运行时用 mj_loadPluginLibrary 加载它，该函数会运行其 注册 代码：

To build your own plugin as a shared library, like the bundled ones, use the mujoco_plugin macro. The library links against @mujoco//:mujoco_shared and exports no symbols; load it at run time with mj_loadPluginLibrary, which runs its registration code:
load("@mujoco//plugin:mujoco_plugin.bzl", "mujoco_plugin")

cc_library(
    name = "my_plugin_lib",
    srcs = ["my_plugin.cc"],
    deps = ["@mujoco"],
    alwayslink = True,
)

# Builds libmy_plugin.so (libmy_plugin.dylib on macOS).
mujoco_plugin(
    name = "my_plugin",
    deps = [":my_plugin_lib"],
)

若要使用单精度浮点数 (mjUSESINGLE)，请使用 --@mujoco//:single_precision 构建。

To use single-precision floating point (mjUSESINGLE), build with --@mujoco//:single_precision.

Bazel 构建在 Linux 和 macOS 上经过测试，涵盖 MuJoCo 库、simulate、插件、示例以及核心 Python 绑定。

The Bazel build is tested on Linux and macOS, and covers the MuJoCo library, simulate, the plugins, the samples and the core Python bindings.

版本与兼容性#

Versions and compatibility

MuJoCo 自 2010 年起被广泛使用，已相当成熟（尽管我们的版本编号方案相当保守）。尽管如此，它仍在积极开发中，我们有许多令人兴奋的新功能构想，也会根据用户反馈进行修改。这导致建模语言和 API 都不可避免地发生变化。虽然我们鼓励用户升级到最新版本，但我们也认识到这并不总是可行，尤其是当其他开发者发布依赖于 MuJoCo 的软件时。因此，我们引入了一些简单的机制来帮助避免版本冲突，如下所述。

MuJoCo has been used extensively since 2010 and is quite mature (even though our version numbering scheme is quite conservative). Nevertheless it remains under active development, and we have many exciting ideas for new features and are also making changes based on user feedback. This leads to unavoidable changes in both the modeling language and the API. While we encourage users to upgrade to the latest version, we recognize that this is not always feasible, especially when other developers release software that relies on MuJoCo. Therefore we have introduced simple mechanisms to help avoid version conflicts, as follows.

如果现有代码是用某个版本的 MuJoCo 开发的，现在却要与另一个版本一起编译和链接，情况就更为微妙。如果该代码所用 API 函数的定义已经改变，编译器或链接器会产生错误。但即使函数定义没有改变，断言软件版本相同仍然是个好主意。为此，主头文件 (mujoco.h) 定义了符号 mjVERSION_HEADER，库则提供了函数 mj_version。因此，可以这样比较头文件和库的版本：

The situation is more subtle if existing code was developed with a certain version of MuJoCo, and is now being compiled and linked with a different version. If the definitions of the API functions used in that code have changed, either the compiler or the linker will generate errors. But even if the function definitions have not changed, it may still be a good idea to assert that the software version is the same. To this end, the main header (mujoco.h) defines the symbol mjVERSION_HEADER and the library provides the function mj_version. Thus the header and library versions can be compared with:
// recommended version check
if (mjVERSION_HEADER != mj_version())
  complain();

请注意，只有主头文件定义了该符号。我们假定每个软件版本发布的头文件集合会保持在一起，不会在不同版本之间混用。为避免浮点数比较带来的复杂性，上述符号和函数使用整数而非浮点数。编码公式和版本语义请参见 VERSIONING.md。

Note that only the main header defines this symbol. We assume that the collection of headers released with each software version will stay together and will not be mixed between versions. To avoid complications with floating-point comparisons, the above symbol and function use integers rather than floating-point numbers. See VERSIONING.md for the encoding formula and version semantics.

命名约定#

Naming convention

API 中定义的所有符号都以前缀“mj”开头。前缀中“mj”之后的字符决定该符号所属的族。首先列出与类型定义对应的前缀。

All symbols defined in the API start with the prefix “mj”. The character after “mj” in the prefix determines the family to which the symbol belongs. First we list the prefixes corresponding to type definitions.
mj

核心仿真数据结构（C 结构体），例如 mjModel。如果前缀之后的所有字符都是大写，例如 mjMIN，则这是一个宏或符号（#define）。

Core simulation data structure (C struct), for example mjModel. If all characters after the prefix are capital, for example mjMIN, this is a macro or a symbol (#define).
mjt

基本类型，例如 mjtNum 和 mjtGeom。此族中的大多数类型是枚举。

Primitive type, for example mjtNum and mjtGeom. Most types in this family are enums.
mjf

回调函数类型，例如 mjfGeneric。

Callback function type, for example mjfGeneric.
mjs

与 程序化模型编辑 相关的数据结构，例如 mjsJoint。

Data structure related to procedural model editing, for example mjsJoint.
mjv

与抽象可视化相关的数据结构，例如 mjvCamera。

Data structure related to abstract visualization, for example mjvCamera.
mjrf

与 filament 渲染相关的数据结构，例如 mjrfContext。

Data structure related to filament rendering, for example mjrfContext.
mjr

与 OpenGL 渲染相关的数据结构，例如 mjrContext。

Data structure related to OpenGL rendering, for example mjrContext.
mjui

与 UI 框架相关的数据结构，例如 mjuiSection。

Data structure related to UI framework, for example mjuiSection.

接下来列出与函数定义对应的前缀。请注意，函数前缀总是以下划线结尾。

Next we list the prefixes corresponding to function definitions. Note that function prefixes always end with underscore.
mj_

核心仿真函数，例如 mj_step。几乎所有此类函数的前两个参数都是指向 mjModel 和 mjData 的指针，其后可能还有其他参数。它们通常将输出写入 mjData。

Core simulation function, for example mj_step. Almost all such functions have pointers to mjModel and mjData as their first two arguments, possibly followed by other arguments. They usually write their outputs to mjData.
mju_

实用函数，例如 mju_mulMatVec。这些函数是自包含的，即它们的参数中没有 mjModel 和 mjData 指针。

Utility function, for example mju_mulMatVec. These functions are self-contained in the sense that they do not have mjModel and mjData pointers as their arguments.
mjv_

与抽象可视化相关的函数，例如 mjv_updateScene。

Function related to abstract visualization, for example mjv_updateScene.
mjrf_

与 filament 渲染相关的函数，例如 mjrf_render。

Function related to filament rendering, for example mjrf_render.
mjr_

与 OpenGL 渲染相关的函数，例如 mjr_render。

Function related to OpenGL rendering, for example mjr_render.
mjui_

与 UI 框架相关的函数，例如 mjui_update。

Function related to UI framework, for example mjui_update.
mjcb_

全局回调函数指针，例如 mjcb_control。用户可以通过将这些全局指针设置为用户定义的函数来安装自定义回调。

Global callback function pointer, for example mjcb_control. The user can install custom callbacks by setting these global pointers to user-defined functions.
mjd_

用于计算导数的函数，例如 mjd_transitionFD。

Functions for computing derivatives, for example mjd_transitionFD.
mjs_

用于 程序化模型编辑 的函数，例如 mjs_addJoint。

Functions for procedural model editing, for example mjs_addJoint.
mjb_

用于 批量仿真 的函数，声明于 mujoco/mjbatch.h 中，例如 mjb_step。

Functions for batched simulation, declared in mujoco/mjbatch.h, for example mjb_step.
