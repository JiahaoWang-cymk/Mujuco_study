## 9.2 换了一台“新” G1：12 自由度模型

### 先猜一猜

1. 宇树训练行走策略用的模型只有 12 个关节（两条腿各 6 个）。那腰和手臂去哪了？机器人总质量会变吗？
2. 第 2 课里 Menagerie 版用的是 `position` 执行器。行走策略输出的也是“目标关节角”，你猜 12 自由度模型用的是什么执行器？

### 运行 `code/09_compare_models.py`

```bash
python code/09_compare_models.py
```

脚本把两个模型都加载进来，按同样的项目各打一行。实际输出：

```text

```

逐条看：

- **腰和手臂被“焊死”了。** 打开 `g1_12dof.xml`，躯干、头、两条手臂的 geom 全都直接挂在 `pelvis` 下面，没有关节。所以 `nq = 7 + 12 = 19`，`nv = 6 + 12 = 18`。手臂没被删掉，它们的质量并进了骨盆：12 自由度模型的 `pelvis` 一个 body 就有 17.73 kg。两个模型的腿完全一样重（两条腿合计都是 14.37 kg），总质量差的 1.2 kg 全在上半身：Menagerie 版骨盆、腰、躯干、手臂加起来是 18.97 kg。
- **执行器是 `motor`。** `motor` 的 `ctrl` 就是力矩本身（gear 默认为 1），MuJoCo 不替你做任何反馈。PD 公式要在 Python 里自己算，见 9.3 ③。
- **力矩上限写在关节上。** Menagerie 写在执行器的 `forcerange` 里；这里写成关节属性 `actuatorfrcrange="-139 139"`，意思是“所有作用到这个关节上的执行器力，合起来截断到 ±139”。效果一样，写法不同。
- **积分器是默认的 Euler。** Menagerie 用 `implicitfast`，是为了把 `position` 执行器里的 `kv·q̇` 这一项隐式处理，大增益时更稳。这里的 PD 是在 Python 里算好再写进 `ctrl` 的，MuJoCo 只看到一个常数力矩，根本不知道它和速度有关，换成 `implicitfast` 也帮不上这一项。好在这组 kd 很小（2～4），显式积分没问题。
- **脚还是 4 个小球**，位置、半径都和 Menagerie 一样，只是摩擦用默认的 1，而不是 0.6。
- **没有传感器。** 策略需要的角速度和重力方向，部署脚本直接从 `qpos`、`qvel` 里取。仿真里这样做没问题；真机上这两个量来自 IMU，会带噪声和偏差。
- **默认站姿不同。** Menagerie 的 `stand` 关键帧是直腿；行走策略的默认姿势是屈髋 0.1、屈膝 0.3、踝 −0.2（单位 rad），重心更低，更像随时准备迈步。

> 腿部 12 个关节的名字和范围两边完全一致，所以第 1 课那张 `qpos` 排布表在这里依然适用，只是腿后面没有腰和手臂了：`qpos[7:13]` 是左腿，`qpos[13:19]` 是右腿。

## 9.3 逐行拆解 deploy_mujoco.py

先把官方脚本的骨架抽出来（省掉了读文件和查看器的部分）：

```python
action = np.zeros(num_actions)            # 上一次策略输出
target_dof_pos = default_angles.copy()    # 当前的目标关节角
counter = 0
while ...:
    tau = pd_control(target_dof_pos, d.qpos[7:], kps, np.zeros_like(kds), d.qvel[6:], kds)
    d.ctrl[:] = tau                       # ① 每个仿真步：PD 算力矩
    mujoco.mj_step(m, d)
    counter += 1
    if counter % control_decimation == 0: # ② 每 10 步：组观测 → 策略 → 新目标
        obs = ...（47 维）
        action = policy(obs)
        target_dof_pos = action * action_scale + default_angles
```

下面分块讲。

### ① 配置：g1.yaml 里有什么

| 字段 | 值 | 含义 |
|---|---|---|
| `simulation_dt` | 0.002 | 仿真步长，500 Hz |
| `control_decimation` | 10 | 每 10 个仿真步跑一次策略，50 Hz |
| `kps` | 髋 100、膝 150、踝 40 | PD 的比例增益（N·m/rad） |
| `kds` | 髋 2、膝 4、踝 2 | PD 的微分增益（N·m·s/rad） |
| `default_angles` | `[-0.1, 0, 0, 0.3, -0.2, 0] × 2` | 默认关节角，动作和观测都以它为零点 |
| `ang_vel_scale` / `dof_pos_scale` / `dof_vel_scale` | 0.25 / 1.0 / 0.05 | 观测缩放 |
| `action_scale` | 0.25 | 动作缩放 |
| `cmd_scale` | `[2.0, 2.0, 0.25]` | 速度指令缩放 |
| `num_actions` / `num_obs` | 12 / 47 | 动作、观测的维数 |
| `cmd_init` | `[0.5, 0, 0]` | 初始指令：向前 0.5 m/s |

这些数字**都是训练时定下的**，部署时一个都不能改。策略只认识训练时见过的那种输入：缩放系数改了，在它眼里就像换了一个世界。

### ② 控制分频：策略 50 Hz，仿真 500 Hz

```text
仿真步  1   2   3  …  10  11  12  …  20  21 …
PD     ●   ●   ●  …   ●   ●   ●  …   ●   ●       每步都按最新的 q、dq 重算力矩
策略                  ▲                  ▲         每 10 步更新一次 target_dof_pos
```

真机也是这样分层的：电机驱动器里的 PD 环跑得很快（kHz 级），上层的策略网络慢一些。入门教程 7.4 节说过，**控制周期要和真实系统一致**；这个策略是按 0.02 s 一拍训练的，部署也必须 0.02 s 一拍。

几个细节：

- 第一次调用策略是在 `counter = 10`，也就是 t = 0.02 s。在此之前目标角就是 `default_angles`。
- 官方脚本**没有**把初始姿势设成默认角：机器人从 `qpos0`（直腿、骨盆高 0.793 m）开始，一落地就被 PD 拉向屈膝的默认姿势。
- 相位用 `counter * simulation_dt` 计算，也就是仿真时间，与墙钟无关。

### ③ PD 力矩：motor 执行器 + 自己算

```python
def pd_control(target_q, q, kp, target_dq, dq, kd):
    return (target_q - q) * kp + (target_dq - dq) * kd
```

调用时 `target_dq` 传的是全零，所以就是

$$\tau = k_p\,(q^* - q) - k_d\,\dot q$$

和第 2 课 `position` 执行器的公式是同一个东西，只是这回由 Python 每步算一次再写进 `ctrl`。为什么不直接用 `position` 执行器？一来真机的接口就是“发目标角 + kp/kd 给电机驱动器”，部署脚本照着真机写更直接；二来增益是训练时定的，每个关节不同，写在 yaml 里比改 XML 方便。练习 3 会让你验证两种写法是等价的。

算出来的力矩不需要自己截断：关节上的 `actuatorfrcrange` 会把它限制在 ±88 / ±139 / ±50 N·m 以内。`09_walk.py` 会统计 PD 力矩超出上限、被截断的次数。

### ④ 观测向量：47 个数，各是什么

```python
qj = (d.qpos[7:] - default_angles) * dof_pos_scale
dqj = d.qvel[6:] * dof_vel_scale
gravity_orientation = get_gravity_orientation(d.qpos[3:7])
omega = d.qvel[3:6] * ang_vel_scale
phase = counter * simulation_dt % 0.8 / 0.8
obs[:3]   = omega
obs[3:6]  = gravity_orientation
obs[6:9]  = cmd * cmd_scale
obs[9:21] = qj
obs[21:33] = dqj
obs[33:45] = action
obs[45:47] = [sin(2π·phase), cos(2π·phase)]
```

| 下标 | 维数 | 内容 | 从哪来 | 缩放 |
|---|---|---|---|---|
| 0–2 | 3 | 骨盆角速度 | `qvel[3:6]` | × 0.25 |
| 3–5 | 3 | 重力方向在骨盆坐标系里的投影 | 由四元数 `qpos[3:7]` 算 | 不缩放（本身是单位向量） |
| 6–8 | 3 | 速度指令 vx、vy、wz | 用户给定 | × 2, 2, 0.25 |
| 9–20 | 12 | 关节角 − 默认角 | `qpos[7:19]` | × 1 |
| 21–32 | 12 | 关节角速度 | `qvel[6:18]` | × 0.05 |
| 33–44 | 12 | 上一步的动作 | 上次策略输出 | 不缩放 |
| 45–46 | 2 | 步态相位 sin、cos | 仿真时间，周期 0.8 s | 不缩放 |

3 + 3 + 3 + 12 × 3 + 2 = 47，正好等于 `num_obs`。

逐项说几句：

- **角速度 `qvel[3:6]` 是在骨盆自己的坐标系里表示的。** 这是 freejoint 的约定：线速度 `qvel[0:3]` 用世界坐标，角速度 `qvel[3:6]` 用局部坐标。真机的 IMU 测的也是机身坐标系下的角速度，两边对得上。
- **重力投影**告诉策略“哪边是下”，相当于人的前庭感觉。站直时是 (0, 0, −1)；身体前倾时 x 分量变正，向左歪时 y 分量变正。`get_gravity_orientation` 那三行公式，其实就是 $R^\top (0,0,-1)^\top$，$R$ 是骨盆的旋转矩阵。脚本运行时会用 `mju_quat2Mat` 现算一遍来核对。注意四元数顺序是 **w x y z**（第 1 课）。
- **为什么要缩放？** 让每一项的数值大致落在 ±1 附近。关节速度动不动就十几 rad/s，乘 0.05 才和其他量差不多大。神经网络对输入的量级很敏感。
- **上一步动作**让策略知道自己刚才“想干什么”，输出更平滑。
- **相位**是一个周期 0.8 s 的“节拍器”。sin、cos 一起给，是为了让 0 和 1 这两个相位在输入上连续。策略据此安排左右脚交替：前半个周期一只脚着地，后半个周期换另一只。
- **注意观测里没有骨盆位置和线速度。** 真机上这两个量很难测准，所以训练时就不给。机器人得“凭感觉”走出指令要的速度。

### ⑤ 动作 → 目标角

```python
target_dof_pos = action * action_scale + default_angles
```

策略输出 12 个数，乘 0.25 再加上默认角，就是新的目标关节角。动作为 0，就意味着“回到默认姿势”。

### ⑥ 策略本身：motion.pt 里是什么

`.pt` 文件其实是个 zip 包。用 Python 自带的 `zipfile` 打开就能看到里面有网络结构的源码（`code/` 目录）和权重（`data/` 目录）。读源码可知它的结构是：

```text
47 维观测 ──► LSTM（隐状态 64 维）──► Linear 64→32 ──► ELU ──► Linear 32→12 ──► 12 维动作
                  ▲      │
                  └──────┘  隐状态 h、c 每次调用后保留
```

一共约 3.1 万个参数，非常小。关键在 **LSTM**：它带“记忆”，每次调用都会更新内部的隐状态。所以同一个观测，在不同时刻喂进去，输出可能不同；换一次实验就要重新加载策略，让记忆清零。

官方脚本用 `torch.jit.load` 加载它，需要安装 PyTorch。没有 PyTorch 也不要紧：`09_walk.py` 里的 `NumpyPolicy` 从 zip 包里把权重读出来，用 numpy 按同样的结构手写了前向计算（LSTM 的四个门、ELU、两个全连接层），一共二十来行。`--policy` 参数选择后端：

| `--policy` | 做法 | 需要 |
|---|---|---|
| `auto`（默认） | 有 PyTorch 就用 torch，否则用 numpy | — |
| `torch` | 和官方一样，`torch.jit.load` | PyTorch |
| `numpy` | 手写前向计算 | 只要 numpy |

另外还有一个 `--dummy-policy`：不用网络，动作恒为 0。它是下一节的主角。

## 9.4 先用零动作把管线跑通

部署一个策略，最常见的毛病不在网络里，而在网络外面：观测顺序拼错、缩放写错、四元数顺序弄反、分频不对……这些错误不会报错，只会让机器人莫名其妙地摔倒。所以先把策略换成“零动作”，把网络以外的部分逐项核对一遍。

### 先猜一猜

1. 动作恒为 0，意味着 PD 一直把关节拉向默认姿势，机器人像一尊屈膝的“雕像”。它能站住吗？如果会倒，往哪边倒？
2. 跑 10 s 仿真，策略应该被调用几次？

### 运行

```bash
python code/09_walk.py --dummy-policy
```

| 相位 | 0.02 / 0.8 = 0.025 个周期，sin(2π×0.025) = 0.156 | ✓ |
| PD 力矩 | 最大 45 N·m（膝），远小于上限，没有截断 | ✓ |

**它为什么会倒？** 粗算一下：默认姿势下整机质心离地约 0.69 m，在踝关节上方约 0.64 m。把整个人看成绕脚踝转动的倒立摆，前倾 1 rad 时重力产生的力矩约为 $mgh ≈ 32.1 × 9.81 × 0.64 ≈ 201$ N·m；而两个踝 pitch 的 PD 刚度加起来只有 2 × 40 = 80 N·m/rad。弹簧比重力“软”，一旦有点前倾就扶不回来。真策略的工作，就是不停地调整目标角把重心“接住”。

这次摔倒正好用来检验摔倒判定。脚本用了三条判据，满足任一条就记为摔倒：骨盆高度 < 0.5 m、躯干倾角 > 45°、脚以外的部位碰到地面。倒向由骨盆坐标系里的重力方向判断。

编写时用 numpy 后端实测：motor + 手算 PD 与 position 执行器跑 10 s，骨盆终点都是 (4.586, −0.390, 0.768) m，三位小数完全相同。编译后左髋 pitch 执行器的 `biasprm` 前三项是 `[0, -100, -2]`、左膝是 `[0, -150, -4]`，`gainprm[0]` 等于 kp，合起来正是 $k_p\,\mathrm{ctrl} - k_p q - k_v \dot q$。两种写法在 Euler 积分器下每步算出的力矩相同：Euler 只对关节自身的 `damping` 做隐式处理，执行器的 `kv` 项和 Python 里的 D 项一样是显式算的。如果顺手把积分器换成 `implicitfast`，`kv` 项会被隐式处理，两种写法就不再一致了：编写时实测 position 版的终点变成 (4.595, −0.390, 0.768) m。

**练习 4**（以实际运行为准）：编写时实测 t = 0.62 s 就向前倒了，比零动作（1.16 s）还快。策略以为自己倒过来了，拼命做“纠正”动作，反而把自己掀翻。

**练习 5**：策略只能从关节角、关节速度、角速度这些“本体感觉”推断自己的速度，就像人闭着眼走路也大致知道自己走多快。单个时刻的观测信息不够，LSTM 把过去若干拍的观测“记”在隐状态里，相当于积累了一段历史，这样才能估计出速度、地面软硬这类看不见的量。这也是 9.5 节里机器人会慢慢偏离直线的原因：它估计的是速度，不是位置，误差会累积。
