扩展#

Extensions

备注

本页由 AI（Claude Sonnet）根据 MuJoCo 官方英文文档（2026-11-16 版）翻译，仅供学习参考；如有出入，以英文原版为准。术语对照见资料包中的 术语表.md 。

本节介绍 MuJoCo 为用户自行编写的扩展所提供的机制。目前，扩展性通过 引擎插件、解码器 和 资源提供者 来提供。

This section describes MuJoCo’s mechanisms for user-authored extensions. At present, extensibility is provided by via engine plugins, decoders, and resource providers.

引擎插件#

Engine plugins

引擎插件（engine plugin）允许将用户自定义的逻辑插入 MuJoCo 计算流水线的各个部分。例如，自定义的传感器和执行器类型都可以实现为插件。插件功能在 MJCF 模型的 XML 内容中被引用，因此即使仿真需求超出了 MuJoCo 内置的能力，MJCF 仍可保持为对系统的抽象物理描述。

Engine plugins allow user-defined logic to be inserted into various parts of MuJoCo’s computational pipeline. For example, custom sensor and actuator types can be implemented as plugins. Plugin features are referenced in the XML content of an MJCF model, allowing MJCF to remain an abstract physical description of a system even if the simulation requirements extend beyond MuJoCo’s built-in capabilities.

插件机制的设计目的是克服 MuJoCo 的 物理回调 的缺点。这些全局回调（用法示例）仍然可用，并且适用于快速原型开发，或在用户希望用 Python 实现功能时使用，但作为扩展功能的稳定机制，它们通常已不推荐使用。插件机制的核心特性是：

The plugin mechanism was designed to overcome the disadvantages of MuJoCo’s physics callbacks. These global callbacks (usage example) are still available and useful for fast prototyping or when the user wishes to implement functionality in Python, but are generally deprecated as a stable mechanism for extended functionality. The central features of the plugin mechanism are:

  • 线程安全： 插件实例（见下文）是线程局部的，从而避免冲突。

    Thread safety: Plugin instances (see below) are thread-local, avoiding collisions.

  • 有状态性： 插件可以是有状态的，其状态会被正确地（反）序列化。

    Statefulness: Plugins can be stateful, and their state will be (de)serialized correctly.

  • 互操作性： 不同的插件可以共存而互不干扰。

    Interoperability: Different plugins can coexist without interference.

插件的使用者和开发者都应当熟悉两个关键概念：

Both users and developers of plugins should familiarize themselves with two key concepts:
插件（Plugin）
Plugin

插件 是一组实现其功能的函数和静态属性的集合，被打包在一个 mjpPlugin 结构体中。插件函数是 无状态 的：它们只依赖于传递给它们的参数。当插件需要内部状态时，它会声明该状态，并允许 MuJoCo 对其进行管理并传入。这使得完整仿真状态的（反）序列化成为可能。因此，插件可以被视为功能中的“纯逻辑”部分，并且通常被打包为 C 库。插件既不是模型元素，也不与特定的模型元素相关联。

A plugin is a collection of functions and static attributes that implement its capabilities, bundled into an mjpPlugin struct. Plugin functions are stateless: they depend only on the arguments passed to them. When a plugin requires an internal state, it declares this state and allows MuJoCo to manage it and pass it in. This enables (de)serialization of the full simulation state. A plugin can therefore be regarded as the “pure logic” part of the functionality and is often bundled as a C library. A plugin is neither a model element nor is it associated with specific model elements.
插件实例（Plugin instance）
Plugin instance

插件 实例 表示由插件所操作的、自包含的运行时状态：当执行插件逻辑时，实例状态由引擎传入。插件实例本身是类型为 mjOBJ_PLUGIN 的模型元素。共有 mjModel.nplugin 个实例，其 id 位于 [0 nplugin-1] 范围内。与其他元素一样，实例可以有名称，mj_name2id 和 mj_id2name 在 id 与名称之间进行映射。与只被加载一次并放入全局表中的插件代码不同，同一个插件可以定义多个实例，并且这些实例与其他模型元素之间存在一对多的关系。

A plugin instance represents the self-contained runtime state that is operated on by the plugin: when the plugin logic is executed, the instance state is passed in by the engine. A plugin instance is itself a model element of type mjOBJ_PLUGIN. There are mjModel.nplugin instances with id’s in [0 nplugin-1]. Like other elements, instances can have names, with mj_name2id and mj_id2name mapping between id’s and names. Unlike the plugin code which is loaded once into a global table, multiple instances of the same plugin can be defined and have a one-to-many relationship with other model elements.
一对一：
one-to-one:

在这种最简单的情形下，每个实例在模型中只被引用一次。例如，两个传感器（sensor）可以声明它们的值由同一个插件的两个插件实例计算得出。在这种情况下，每次计算传感器输出时，插件逻辑都会被单独执行。

In this simplest case, each instance is referenced once in the model. For example, two sensors may declare that their values are computed by two plugin instances of the same plugin. In this case, every time the sensor output is computed, the plugin logic will be executed separately.
一对多：
one-to-many:

或者，多个元素的行为也可以由单个插件实例来支撑。有两种主要场景适合这样做：

Alternatively, the behavior of multiple elements can be backed by a single plugin instance. There are two main scenarios where this is useful:

  • 不同元素类型的值与同一个物理实体和同一次计算相关联。例如，考虑一个带有内部温度计的电机。这会表现为一个执行器（actuator）和一个传感器，二者都与同一个插件实例相关联，该实例同时计算力矩输出和温度读数。

    The values of different element types are linked to the same physical entity and computation. For example consider a motor with an internal thermometer. This would manifest as an actuator and sensor, both associated with the same plugin instance which computes both torque outputs and temperature readings.

  • 将多个相关元素的计算批量合并在一起是有利的，例如计算值是神经网络的输出时。这里的典型例子是一个配备了 N 个电机的机器人，其电机动力学（dynamics）由神经网络建模。在这种情况下，在一次前向传播中产生全部 N 个执行器的力矩输出，可以比分别为每个电机计算快得多。

    It is advantageous to batch the computation of multiple related elements together, for example where the computed value is the output of a neural network. The canonical example here is a robot that is equipped with N motors, where motor dynamics are modeled as a neural network. In this case, it can be substantially faster to produce the torque output of all N actuators in a single forward pass than for each motor separately.

插件能力#

Plugin capabilities

插件由其关联的 mjpPlugin 结构体的内容来描述。capabilityflags 成员是一个整数位域，用于描述插件的能力，其位的语义定义在枚举 mjtPluginCapabilityBit 中。使用位域使得插件可以支持多种类型的计算。目前支持的插件能力有：

A plugin is described by the contents of its associated mjpPlugin struct. The capabilityflags member is an integer bitfield describing the plugin’s capabilities, where bit semantics are defined in the enum mjtPluginCapabilityBit. Using a bitfield allows plugins to support multiple types of computation. The currently supported plugin capabilities are:

  • 执行器插件

    Actuator plugin

  • 传感器插件

    Sensor plugin

  • 被动力（passive force）插件

    Passive force plugin

  • 有符号距离场插件

    Signed distance field plugin

未来将根据需要添加更多能力。

Additional capabilities will be added in the future as required.

在 MJCF 中声明#

Declaration in MJCF

首先，必须通过 <extension><plugin> 声明插件依赖。解析模型时，如果声明了任何插件但该插件未被注册（见下文），则会引发模型编译错误。如果只有单个 MJCF 元素由插件支撑，则可以就地隐式创建实例。如果多个元素由同一个插件支撑，则必须显式声明实例：

First, a plugin dependency must be declared through <extension><plugin>. When the model is parsed, if any plugin is declared but not registered (see below), a model compilation error is raised. If only a single MJCF element is backed by a plugin, instances can be implicitly created in-place. If multiple elements are backed by the same plugin, instance declaration must be explicit:
<mujoco>
  <extension>
    <plugin plugin="mujoco.test.simple_sensor_plugin"/>
    <plugin plugin="mujoco.test.actuator_sensor_plugin">
      <instance name="explicit_instance"/>
    </plugin>
  </extension>
  ...
  <sensor>
    <plugin name="sensor0" plugin="mujoco.test.simple_sensor_plugin"/>
    <plugin name="sensor1" plugin="mujoco.test.simple_sensor_plugin"/>
    <plugin name="sensor2" instance="explicit_instance"/>
  </sensor>
  ...
  <actuator>
    <plugin name="actuator2" instance="explicit_instance"/>
  </actuator>
</mujoco>

在上面的示例中，sensor0 和 sensor1 各自由一个简单的插件支撑，该插件不在元素之间共享计算，因此通过直接引用插件标识符，为每个传感器隐式创建了一个实例。相反，sensor2 和 actuator2 由一个共享计算的插件支撑，因此它们必须引用一个显式声明的共享实例。

In the example above, sensor0 and sensor1 are each backed by a simple plugin that does not share computation among elements, so an instance is implicitly created for each sensor by directly referencing the plugin identifier. In contrast, sensor2 and actuator2 are backed by a plugin that shares computation, so they must reference a shared instance that was explicitly declared.

在 MJCF 中配置#

Configuration in MJCF

插件可以声明自定义属性，用来表示专门的可配置参数。例如，直流电机模型可以将电阻、电感和电容作为配置属性公开。在 MJCF 中，这些属性的值可以通过 <config> 元素来指定，其中每个 <config> 都有一个键和一个值。有效的键和值由插件开发者指定，但会在插件注册时向 MuJoCo 声明，以便 MuJoCo 模型编译器（model compiler）可以对无效值报错。

Plugins can declare custom attributes that represent specialized configurable parameters. For example, a DC motor model may expose the resistance, inductance, and capacitance as configuration attributes. In MJCF, the values of these attributes can be specified via <config> elements, where each <config> has a key and a value. Valid keys and values are specified by the plugin developers, but are declared to MuJoCo during plugin registration time so that the MuJoCo model compiler can raise errors for invalid values.
<mujoco>
  <extension>
    <plugin plugin="mujoco.test.simple_actuator_plugin">
      <instance name="explicit_instance">
        <config key="resistance" value="1.0"/>
        <config key="inductance" value="2.0"/>
      </instance>
    </plugin>
  </extension>
  ...
  <actuator>
    <plugin name="actuator0" instance="explicit_instance"/>
    <plugin name="actuator1" plugin="mujoco.test.simple_actuator_plugin">
        <config key="resistance" value="3.0"/>
        <config key="inductance" value="4.0"/>
    </plugin>
  </actuator>
</mujoco>

在上面的示例中，actuator0 引用的是一个预先存在的插件实例，该实例通过 <instance> 元素创建并配置；而 actuator1 则是在原地隐式创建并配置一个新的插件实例。请注意，直接向 actuator0 添加 <config> 子元素将会出错，因为那里并没有创建新的插件实例。

In the example above, actuator0 refers to a pre-existing plugin instance that was created and configured via the <instance> element, while actuator1 is implicitly creating and configuring a new plugin instance in-place. Note that it would be an error to add <config> child elements directly to actuator0 because a new plugin instance is not being created there.

插件状态#

Plugin state

虽然插件代码应当是无状态的，但各个插件实例可以持有与时间相关的状态，这些状态旨在随 MuJoCo 物理一同演化，例如热力学耦合的执行器模型中的温度变量。另外，插件实例也可能希望对其运行过程中可能开销很大的部分进行记忆化（memoize）。例如，由预训练神经网络支撑的传感器或执行器插件，会希望在模型编译时预加载其权重。区分这两种每实例的插件载荷非常重要。术语 插件状态（plugin state）指插件实例中由 浮点 值构成的、与时间相关的状态，而术语 插件数据（plugin data）则指由记忆化载荷构成的 任意数据结构，它们应被视为插件计算的实现细节。

While plugin code should be stateless, individual plugin instances are permitted to hold time-dependent state that is intended to evolve alongside MuJoCo physics, for example temperature variables in thermodynamically coupled actuator models. Separately, it may also be desirable for plugin instances to memoize potentially expensive parts of their operation. For example, sensor or actuator plugins that are backed by pretrained neural networks will want to preload their weights at model compilation time. It is important for us to distinguish between these two types of per-instance plugin payload. The term plugin state refers to the time-dependent state of the plugin instance that consists of floating point values, while the term plugin data refers to arbitrary data structures consisting of memoized payload that should be considered implementation detail for the plugin’s computation.

关键在于，插件数据必须仅能通过插件配置属性、插件状态以及 MuJoCo 状态变量 重新构建。这意味着插件数据不要求可序列化，并且 MuJoCo 在复制或存储数据时不会对其进行序列化。另一方面，插件状态被视为物理的组成部分，必须与 MuJoCo 的其他状态变量一起序列化，才能忠实地恢复物理。

Crucially, plugin data must be reconstructible only from plugin configuration attributes, the plugin state, and MuJoCo state variables. This means that the plugin data is not expected to be serializable, and will not be serialized by MuJoCo when it copies or stores data. On the other hand, plugin state is considered an integral part of the physics and must be serialized alongside MuJoCo’s other state variables in order for the physics to be faithfully restored.

插件必须通过其 mjpPlugin 结构体的 nstate 回调，声明每个实例所需的浮点数个数。请注意，这个数目可能取决于实例的具体配置。在 mj_makeData 期间，MuJoCo 会在 mjData 的 plugin_state 字段中为每个插件实例分配所需数量的槽位。mjModel 中的 plugin_stateadr 字段指明了每个插件实例可在整个 plugin_state 数组中的哪个位置找到其状态值。

Plugins must declare the number of floating point values required for each instance via the nstate callback of its mjpPlugin struct. Note that this number can depend on the exact configuration of the instance. During mj_makeData, MuJoCo allocates the requisite number of slots in the plugin_state field of mjData for each plugin instance. The plugin_stateadr field in mjModel indicates the position within the overall plugin_state array at which each plugin instance can find its state values.

然而，从 MuJoCo 的角度来看，插件数据是完全不透明的。在 mj_makeData 期间，MuJoCo 会调用相应 mjpPlugin 的 init 回调。在该回调中，插件被允许分配或以其他方式创建其运行所需的任意数据结构，并将其指针存储在正在创建的 mjData 的 plugin_data 字段中。在 mj_deleteData 期间，MuJoCo 会调用同一个 mjpPlugin 的 destroy 回调，插件负责释放与该实例相关联的内部资源。

Plugin data, however, is entirely opaque from MuJoCo’s point of view. During mj_makeData, MuJoCo calls the init callback from the relevant mjpPlugin. In this callback, the plugin is permitted to allocate or otherwise create an arbitrary data structure that it requires to function and stores its pointer in the plugin_data field of mjData that is being created. During mj_deleteData, MuJoCo calls the destroy callback from the same mjpPlugin, and the plugin is responsible for deallocating its internal resources associated with the instance.

init 回调应通过发出 mju_warning 并返回 -1 来报告无效配置，此时 mj_makeData（以及模型编译）会失败。插件回调不应调用 mju_error：不返回的错误处理程序（如 Python 绑定和模型编译器的错误处理程序）会跳过位于栈上的、插件中以及 MuJoCo 自身中的 C++ 对象的析构函数。

The init callback should report an invalid configuration by issuing a mju_warning and returning -1, upon which mj_makeData (and model compilation) fails. Plugin callbacks should not call mju_error: error handlers which do not return, like those of the Python bindings and the model compiler, skip the destructors of C++ objects on the stack, in the plugin and in MuJoCo itself.

当通过 mj_copyData 复制 mjData 时，MuJoCo 会复制插件状态。然而，插件代码负责为新复制的 mjData 设置插件数据。为此，MuJoCo 会对每个存在的插件实例调用 mjpPlugin 中的 copy 回调。

When mjData is being copied via mj_copyData, MuJoCo will copy over the plugin state. However, the plugin code is responsible for setting up the plugin data for the newly copied mjData. To facilitate this, MuJoCo calls the copy callback from mjpPlugin for each plugin instance present.

执行器状态#

Actuator states

在编写有状态的执行器插件时，对于执行器状态保存在何处有两种选择。一种是如上所述使用 plugin_state，另一种是通过在 mjpPlugin 上实现相应的回调来使用 mjData.act。

When writing stateful actuator plugins, there are two choices for where to save the actuator state. One option is using plugin_state as described above, and the other is to use mjData.act by implementing the callback on mjpPlugin.

使用后一种选项时，执行器插件的状态会被添加到 mjData.act 中，并且 MuJoCo 会在各时间步之间自动对 mjData.act_dot 的值进行积分。这种方法的一个优点是，像 mjd_transitionFD 这样的有限差分函数的工作方式与对原生执行器相同。mjpPlugin.advance 回调将在 act_dot 被积分之后调用，如果内置积分器（integrator）不合适，执行器插件可以在此时覆盖 act 的值。

When using the latter option, the actuator plugin’s state will be added to mjData.act, and MuJoCo will automatically integrate mjData.act_dot values between timesteps. One advantage of this approach is that finite-differencing functions like mjd_transitionFD will work as they do for native actuators. The mjpPlugin.advance callback will be called after act_dot is integrated, and actuator plugins may overwrite the act values at that point, if the built-in integrator is not appropriate.

用户可以在执行器插件上指定 dyntype 属性，以便在用户输入与执行器状态之间引入滤波器或积分器。这样做时，由 dyntype 引入的状态变量将被放置在 act 数组中插件状态变量的 之后。

Users may specify the dyntype attribute on actuator plugins, to introduce a filter or an integrator between user inputs and actuator states. When they do, the state variable introduced by dyntype will be placed after the plugin’s state variables in the act array.

注册#

Registration

插件必须先在 MuJoCo 中注册，才能在 MJCF 模型中被引用。

Plugins must be registered with MuJoCo before they can be referenced in MJCF models.

旨在支持特定应用程序的一次性插件（或为帮助排查模型问题而实现的临时插件）可以被静态链接到应用程序中。这可以简单到只需在 main 函数中准备一个 mjpPlugin 结构体，然后将其传递给 mjp_registerPlugin，以便向 MuJoCo 注册。

One-off plugins that are intended to support a specific application (or throwaway plugins that are implemented to help troubleshoot issues with a model) can be statically linked into the application. This can be as simple as preparing an mjpPlugin struct in the main function, then passing it to mjp_registerPlugin to be registered with MuJoCo.

一般来说，可复用的插件预期会被打包为库，并应在库加载时注册。在兼容 GCC 的编译器中，这可以通过在用 __attribute__((constructor)) 声明的函数中调用 mjp_registerPlugin 来实现，而在 MSVC 中，则可以通过向 C 运行时初始化中注入代码来实现。MuJoCo 提供了一个便利宏 mjPLUGIN_LIB_INIT，它会根据所用的编译器展开为上述两种构造之一。

Generally, reusable plugins are expected to be packaged as libraries and should be registered when the library is loaded. In GCC-compatible compilers, this can be achieved by calling mjp_registerPlugin in a function that is declared with __attribute__((constructor)), while in MSVC this can be done by injecting code into the C runtime initialization. MuJoCo provides a convenience macro mjPLUGIN_LIB_INIT that expands to either of these constructs depending on the compiler used.

对于以上述动态库形式交付的插件，其使用者可以使用函数 mj_loadPluginLibrary 加载该库。这是加载包含 MuJoCo 插件的动态库的首选方式（而不是比如直接调用 dlopen 或 LoadLibraryA），因为 MuJoCo 期望动态库自动注册插件的确切方式可能会随时间变化，而 mj_loadPluginLibrary 预期也会随之演进，以反映最佳实践。

Users of plugins that are delivered as dynamic libraries as described above can load the library using the function mj_loadPluginLibrary. This is the preferred way to load dynamic libraries containing MuJoCo plugins (rather than, say, calling dlopen or LoadLibraryA directly) since the exact way in which MuJoCo expects dynamic libraries to auto-register plugins may change over time, but mj_loadPluginLibrary is expected to also evolve to reflect the best practices.

对于需要能够加载任意用户提供的 MJCF 模型的应用程序，可能希望自动扫描并加载在特定目录中找到的所有动态库。这样，带来了需要插件的 MJCF 的用户，就可以被告知将所需的插件库放置在相应的目录中。例如，simulate 交互式查看器应用程序就是这样做的。mj_loadAllPluginLibraries 函数正是为这种扫描并加载的用例而提供的。目录中某个加载失败的库（例如因为缺少其某个依赖项）会被跳过并给出警告，而不会中止应用程序。

For applications that need to be able to load arbitrary user-provided MJCF models, it may be desirable to automatically scan and load all dynamic libraries found without a specific directory. Users who bring along an MJCF that requires a plugin can then be instructed to place the requisite plugin libraries in the relevant directory. For example, this is what is done in the simulate interactive viewer application. The mj_loadAllPluginLibraries function is provided for this scan-and-load use case. A library in the directory that fails to load, for example because one of its dependencies is missing, is skipped with a warning rather than aborting the application.

sdf#

sdf/ 目录中的插件以无网格的方式指定自定义形状，其做法是定义在查询点处计算有符号距离场及其梯度的方法。该形状随后在 engine_collision_driver.c 顶部的碰撞表中充当一种新的 geom 类型。有关可用的 SDF 以及如何编写自己的隐式几何的更多信息，请参见 README。本节其余部分将更详细地介绍碰撞算法和插件引擎接口。

The plugins in the sdf/ directory specify custom shapes in a mesh-free manner, by defining methods computing a signed distance field and its gradient at query points. This shape then acts as a new geom type in the collision table at the top of engine_collision_driver.c. For more information concerning the available SDFs and how to write your own implicit geometry, please see the README. The rest of this section will give more detail concerning the collision algorithm and the plugin engine interface.

碰撞点是通过梯度下降最小化函数 A + B + abs(max(A, B)) 找到的，其中 A 和 B 是两个相碰撞的 SDF。由于 SDF 是非凸的，需要多个起始点才能收敛到多个局部极小值。起始点的数量通过 sdf_initpoints 设置，并使用 Halton 序列在轴对齐包围盒的交集内部初始化。梯度下降的迭代次数通过 sdf_iterations 设置。

Collision points are found by minimizing the function A + B + abs(max(A, B)), where A and B are the two colliding SDFs, via gradient descent. Because SDFs are non-convex, multiple starting points are required in order to converge to multiple local minima. The number of starting points is set using sdf_initpoints, and are initialized using the Halton sequence inside the intersection of the axis-aligned bounding boxes. The number of gradient descent iterations is set using sdf_iterations.

虽然 精确 的 SDF——即编码到表面的精确有符号距离——是首选，但任何在表面处值为零、远离表面时单调增长、且在内部为负的函数都可以进行碰撞。对于这类函数，仍然可以找到碰撞，只是可能需要增加起始点的数量。请注意，如果在零水平集附近 \(\|\nabla f\| \neq 1\)，则接触穿透深度会相应缩放，梯度下降的投影步骤也会发生畸变，因此建议在表面附近使 \(\|\nabla f\| \approx 1\)。

While exact SDFs—encoding the precise signed distance to the surface—are preferred, collisions are possible with any function whose value vanishes at the surface and grows monotonically away from it, with a negative sign in the interior. For such functions, it is still possible to find collisions, albeit with a possibly increased number of starting points. Note that if \(\|\nabla f\| \neq 1\) near the zero level set, contact penetration depth is scaled accordingly and gradient-descent projection steps are distorted, so \(\|\nabla f\| \approx 1\) near the surface is recommended.

编译器会调用 sdf_distance 方法，使用 MarchingCubeCpp 所实现的 marching cubes 算法生成用于渲染的可视化网格。

The sdf_distance method is called by the compiler to produce a visual mesh for rendering using the marching cubes algorithm implemented by MarchingCubeCpp.

对梯度下降算法的未来改进，例如利用 SDF 性质的线搜索，可能会减少迭代次数和／或起始点数量。

Future improvement to the gradient descent algorithm, such as a line search which takes advantage of the properties of SDFs, might reduce the number of iterations and/or starting points.

解码器接口#

Decoder interface

解码器由 mjpDecoder 结构体描述，该结构体具有以下字段：

A decoder is described by the mjpDecoder struct, which has the following fields:
content_type

标识格式的、类似 MIME 的内容类型字符串。例如 "model/obj" 或 "model/stl"。当 MJCF 中的某个网格资产指定了 content-type 属性时，该字符串会被用来查找合适的解码器。

A MIME-like content type string identifying the format. For example, "model/obj", or "model/stl". When a mesh asset specifies a content-type attribute in MJCF, this string is used to find the appropriate decoder.
extension

文件扩展名字符串（包含点号），在未指定内容类型时用于匹配。对于具有多个扩展名的格式，多个扩展名可以用竖线（|）分隔，例如 .usd|.usda|.usdc|.usdz。

A file extension string (including the dot) used for matching when no content type is specified. Multiple extensions can be separated by pipes (|) for formats with multiple extensions such as .usd|.usda|.usdc|.usdz.
can_decode

类型为 mjfCanDecode 的回调，用于判断解码器是否能处理给定的资源。它通常通过检查文件扩展名来实现，但也可以检查文件内容以区分不同格式。例如，URDF 和 MJCF 文件的扩展名都是 .xml。如果解码器能够处理该资源，则返回非零值。

A callback of type mjfCanDecode that determines whether the decoder can handle a given resource. This is typically implemented by checking the file extension but may also check the file contents to differentiate between formats. For example, URDF and MJCF files both have a .xml extension. Returns nonzero if the decoder can handle the resource.
decode

类型为 mjfDecode 的回调，用于执行实际的解码。它接收一个 mjResource，并返回一个新分配的、包含已解码资产数据的 mjSpec。调用方获得所返回 spec 的所有权，并负责使用 mj_deleteSpec 将其释放。失败时返回 NULL，此时解码器应将人类可读的原因写入大小为 error_sz 的 error 缓冲区（如果 error 不为 NULL）。该消息会被传播给用户，例如通过 mj_parse 的 error 参数，或作为网格资产的编译器错误。非致命问题可以通过 mju_warning 报告。解码器不应调用 mju_error，参见 插件状态。

A callback of type mjfDecode that performs the actual decoding. It receives an mjResource and returns a newly allocated mjSpec containing the decoded asset data. The caller takes ownership of the returned spec and is responsible for freeing it with mj_deleteSpec. Returns NULL on failure, in which case the decoder should write a human-readable reason into the error buffer of size error_sz, if error is not NULL. This message is propagated to the user, e.g. via the error argument of mj_parse or as a compiler error for mesh assets. Non-fatal issues can be reported with mju_warning. Decoders should not call mju_error, see plugin state.

当为网格资产调用解码器时，编译器会引用由 decode 回调所返回的 spec 中的第一个网格元素。

When a decoder is invoked for a mesh asset, the compiler will reference the first mesh element in the spec returned by the decode callback.

当为模型资产调用解码器时，由 decode 回调所返回的 spec 可以包含任意数量的任意类型的元素。

When a decoder is invoked for a model asset, the spec returned by the decode callback may contain any number of elements of any type.

注册#

Registration

解码器必须先注册才能使用。注册通过 mjp_registerDecoder 执行。mjp_defaultDecoder 函数用默认值初始化一个 mjpDecoder 结构体。mjPLUGIN_LIB_INIT 宏用于定义初始化函数，该函数会在库加载时注册解码器。

Decoders must be registered before they can be used. Registration is performed via mjp_registerDecoder. The mjp_defaultDecoder function initializes an mjpDecoder struct with default values. The mjPLUGIN_LIB_INIT macro is used to define the initialization function that registers the decoder when the library is loaded.
mjPLUGIN_LIB_INIT(my_format_decoder) {
  mjpDecoder decoder;
  mjp_defaultDecoder(&decoder);
  decoder.content_type = "model/my-format";
  decoder.extension = ".myf|.myfa|.myfc";
  decoder.decode = MyDecode;
  decoder.can_decode = MyCanDecode;
  mjp_registerDecoder(&decoder);
}

Below is a minimal decoder that reads a hypothetical binary mesh format:
#include <stdio.h>
#include <mujoco.h>

static mjSpec* MyDecode(mjResource* resource, const mjVFS* vfs, char* error, int error_sz) {
  const void* bytes = NULL;
  int nbytes = mju_readResource(resource, &bytes);
  if (nbytes < 0) {
    if (error) snprintf(error, error_sz, "failed to read resource '%s'", resource->name);
    return NULL;
  }

  /* ... parse bytes into vertex/face arrays ... */

  mjSpec* spec = mj_makeSpec();
  mjsMesh* mesh = mjs_addMesh(spec, NULL);
  mjs_setString(mesh->file, resource->name);
  mjs_setFloat(mesh->uservert, vertices, nvert * 3);
  mjs_setInt(mesh->userface, faces, nface * 3);
  return spec;
}

static int MyCanDecode(const mjResource* resource) {
  /* check file extension */
  const char* name = resource->name;
  int len = strlen(name);
  return len > 4 && strcmp(name + len - 4, ".myf") == 0;
}

资源提供者#

Resource providers

资源提供者（mjpResourceProvider）用于扩展 MuJoCo，使其能够加载并不一定来自操作系统文件系统或虚拟文件系统（mjVFS）的资源文件（XML 文件、网格、纹理等）。例如，从 Internet 下载资源文件就可以通过资源提供者来实现。MuJoCo 通过 mjResource 结构体来对这些扩展进行抽象处理。

Resource providers (mjpResourceProvider) extend MuJoCo to load assets (XML files, meshes, textures, and etc.) that don’t necessarily come from the OS filesystem or the Virtual File System (mjVFS). For example, downloading assets from the Internet could be implemented as a resource provider. These extensions are handled abstractly in MuJoCo via the mjResource struct.

概述#

Overview

创建新的资源提供者的方法是：通过 mjp_registerProvider 把一个 mjpResourceProvider 结构体注册到全局表中。资源提供者一经注册，所有加载函数都可以使用它。mjpResourceProvider 结构体存储三类字段：

Creating a new resource provider works by registering a mjpResourceProvider struct via mjp_registerProvider in a global table. Once a resource provider is registered it can be used by all loading functions. The mjpResourceProvider struct stores three types of fields:
资源前缀
Resource prefix

资源通过其名称中的前缀来标识。所选前缀应符合有效的 Uniform Resource Identifier（URI）方案语法。资源名称也应具有有效的 URI 语法，但这一点并不强制要求。语法为 {prefix}:{filename} 的资源名称将匹配使用方案 prefix 的提供者。例如，通过 Internet 访问资源文件的资源提供者可能会使用 http 作为其方案，这时名为 http://www.example.com/myasset.obj 的资源就会与该资源提供者匹配。方案不区分大小写，因此 HTTP://www.example.com/myasset.obj 同样可以匹配。请注意冒号的重要性：URI 语法要求资源名称中的前缀后面必须紧跟一个冒号，才能与某个方案匹配。例如，https://www.example.com/myasset.obj 就不会匹配，因为其方案是 https。

Resources are identified by prefixes in their name. The chosen prefix should have a valid Uniform Resource Identifier (URI) scheme syntax. Resource names should also have a valid URI syntax, however this isn’t enforced. A resource name with the syntax {prefix}:{filename} will match a provider using the scheme prefix. For instance, a resource provider accessing assets via the Internet might use http as its scheme. In this case a resource with the name http://www.example.com/myasset.obj would match against this resource provider. Schemes are case-insensitive so that HTTP://www.example.com/myasset.obj will also match. Note the importance of the colon. URI syntax requires that a colon follows the prefix in a resource name in order to match against a scheme. For example https://www.example.com/myasset.obj would NOT be a match since the scheme is designated as https.
回调函数
Callbacks

资源提供者必须实现三个回调函数：open、read 和 close。另外两个回调函数 getdir 和 modified 是可选的。下文会给出这些回调函数的更多细节。

There are three callbacks that a resource provider is required to implement: open, read, and close. The other two callback getdir and modified are optional. More details on these callbacks are given below.
数据指针
Data Pointer

最后，还有一个不透明的数据指针，供提供者向回调函数传递数据。在同一个模型内，该数据指针保持不变。

Lastly, there’s an opaque data pointer for the provider to pass data into the callbacks. This data pointer is constant within a given model.

资源提供者通过回调函数工作：

Resource providers work via callbacks:

  • mjfOpenResource：打开回调函数接受一个类型为 mjResource 的参数。应使用资源的 name 字段来验证该资源是否存在，并用资源所需的任何额外信息填充资源的 data 字段。失败时该回调函数应返回 0（false），否则返回 1（true）。

    mjfOpenResource: The open callback takes a single parameter of type mjResource. The name field of the resource should be used to verify that the resource exists and populate the resource data field with any extra information needed for the resource. On failure this callback should return 0 (false) or else 1 (true).

  • mjfReadResource：读取回调函数的参数为一个 mjResource 和一个指向 void 指针的指针，称为 buffer。读取回调函数应让 buffer 指针指向可以读取该资源字节数据的位置，并返回 buffer 所指向的字节数。失败时该回调函数应返回 -1。

    mjfReadResource: The read callback takes as arguments a mjResource and a pointer to a void pointer called the buffer. The read callback should point the buffer pointer to the location of where the bytes of the resource can be read and return the number of bytes pointed to in the buffer. On failure, this callback should return -1.

  • mjfCloseResource：该回调函数接受一个类型为 mjResource 的参数，应用于释放在所提供资源的 data 字段中分配的所有内存。

    mjfCloseResource: This callback takes a single parameter of type mjResource, and should be used to free any memory allocated in the data field in the supplied resource.

  • mjfGetResourceDir：该回调函数是可选的，用于从资源名称中提取目录。例如，资源名称 http://www.example.com/myasset.obj 的目录为 http://www.example.com/。

    mjfGetResourceDir: This callback is optional and is used to extract the directory from a resource name. For example, the resource name http://www.example.com/myasset.obj would have http://www.example.com/ as its directory.

  • mjfResourceModified：该回调函数是可选的，用于检查已打开的现有资源相对于其原始来源是否已被修改。

    mjfResourceModified: This callback is optional and is used to check if an existing opened resource has been modified from its original source.

用法#

Usage

资源提供者一经注册，就可以立即用于打开资源文件。如果资源文件名的前缀与某个已注册提供者的前缀匹配，则会使用该提供者来加载该资源。

When a resource provider is registered, it can be used immediately to open assets. If the asset filename has a prefix that matches with the prefix of a registered provider, then that provider will be used to load the asset.

示例#

Example

本节给出一个基本示例：一个从 data URI scheme 读取数据的资源提供者。首先我们实现这些回调函数：

This section provides a basic example of a resource provider that reads from a data URI scheme. First we implement the callbacks:
int str_open_callback(mjResource* resource) {
  // call some util function to validate
  if (!is_valid_data_uri(resource->name)) {
    return 0; // return failure
  }

  // some upper bound for the data
  resource->data = mju_malloc(get_data_uri_size(resource->name));
  if (resource->data == NULL) {
    return 0; // return failure
  }

  // fill data from string (some util function)
  get_data_uri(resource->name, &data);
}

int str_read_callback(mjResource* resource, const void** buffer) {
  *buffer = resource->data;
  return get_data_uri_size(resource->name);
}

void str_close_callback(mjResource* resource) {
  mju_free(resource->data);
}

接下来，我们创建资源提供者并将其注册到 MuJoCo：

Next we create the resource provider and register it with MuJoCo:
mjpResourceProvider provider = {
  .prefix = "data",
  .open = str_open_callback,
  .read = str_read_callback,
  .close = str_close_callback,
};

// return positive number on success
if (!mjp_registerProvider(&provider)) {
  // ...
  // return failure
}
