初始化#

Initialization

用户永远不应直接分配 mjModel 和 mjData，它们应由相应的 API 函数分配并初始化。这两个数据结构相当复杂，包含（由其他结构组成的）数组、为所有中间结果预先分配的数据数组，以及一个 内部栈。我们的策略是在仿真开始时分配全部所需的堆内存，并在仿真结束后释放，这样在仿真过程中就无需调用 C 的内存分配与释放函数。这样做是为了提高速度、避免内存碎片、便于移植到 GPU，并且便于在重置时管理整个仿真器的状态。但这也意味着，由 MJCF 元素 size 中的 memory 属性给出的最大可变内存分配量（它影响 mjData 的分配）必须设置为足够大的值。如果仿真过程中超出了这一最大值，它不会被动态增大，而是会产生一个错误。另见下文的 诊断。

mjModel and mjData should never be allocated directly by the user. Instead they are allocated and initialized by the corresponding API functions. These are very elaborate data structures, containing (arrays of) other structures, preallocated data arrays for all intermediate results, as well as an internal stack. Our strategy is to allocate all necessary heap memory at the beginning of the simulation, and free it after the simulation is done, so that we never have to call the C memory allocation and deallocation functions during the simulation. This is done for speed, avoidance of memory fragmentation, GPU portability, and ease of managing the state of the entire simulator during a reset. It also means however that the maximal variable-memory allocation given by the memory attribute in the size MJCF element, which affects the allocation of mjData, must be set to a sufficiently large value. If this maximal size is exceeded during simulation, it is not increased dynamically, but instead an error is generated. See also diagnostics below.

仿真循环#

Simulation loop

在 MuJoCo 中有多种方式运行仿真循环。最简单的方式是在循环中调用顶层仿真函数 mj_step，例如

There are multiple ways to run a simulation loop in MuJoCo. The simplest way is to call the top-level simulation function mj_step in a loop such as
// simulate until t = 10 seconds
while (d->time < 10)
  mj_step(m, d);

由于我们没有提供任何控制信号或施加力，这样做本身只会仿真被动动力学（dynamics）。控制系统的默认方式是实现一个控制回调函数，例如

This by itself will simulate the passive dynamics, because we have not provided any control signals or applied forces. The default way to control the system is to implement a control callback, for example
// simple controller applying damping to each DOF
void mycontroller(const mjModel* m, mjData* d) {
  if (m->nu == m->nv)
    mju_scl(d->ctrl, d->qvel, -0.1, m->nv);
}

这里体现了两个概念。第一，我们检查控制数量 mjModel.nu 是否等于自由度（DoF）数量 mjModel.nv 。一般而言，取决于用户代码的组织方式，同一个回调函数可能被用于多个模型，因此在回调中检查模型维度是个好主意。第二，MuJoCo 有一个类似 BLAS 的函数库，非常有用；事实上，代码库的很大一部分就是在内部调用这类函数。上面的 mju_scl 函数把速度向量 mjData.qvel 乘以一个常数反馈增益（gain），并把结果复制到控制向量 mjData.ctrl 中。要安装这个回调函数，只需把它赋给全局控制回调指针 mjcb_control：

This illustrates two concepts. First, we are checking if the number of controls mjModel.nu equals the number of DoFs mjModel.nv. In general, the same callback may be used with multiple models depending on how the user code is structured, and so it is a good idea to check the model dimensions in the callback. Second, MuJoCo has a library of BLAS-like functions that are very useful; indeed a large part of the code base consists of calling such functions internally. The mju_scl function above scales the velocity vector mjData.qvel by a constant feedback gain and copies the result into the control vector mjData.ctrl. To install this callback, we simply assign it to the global control callback pointer mjcb_control:
// install control callback
mjcb_control = mycontroller;

现在如果我们调用 mj_step，那么每当仿真流水线需要控制信号时，就会执行我们的控制回调函数，最终我们就仿真了受控的动力学。

Now if we call mj_step, our control callback will be executed whenever the control signal is needed by the simulation pipeline, and as a result we will end up simulating the controlled dynamics.

除了依赖控制回调函数，我们也可以直接设置控制向量 mjData.ctrl 。或者也可以设置施加力，如 状态与控制 中所述。如果我们能在调用 mj_step 之前计算出这些与控制相关的量，那么受控动力学的仿真循环（不使用控制回调）就变成

Instead of relying on a control callback, we could set the control vector mjData.ctrl directly. Alternatively we could set applied forces as explained in state and control. If we could compute these control- related quantities before mj_step is called, then the simulation loop for the controlled dynamics (without using a control callback) would become
while (d->time < 10) {
  // set d->ctrl or d->qfrc_applied or d->xfrc_applied
  mj_step(m, d);
}

为什么我们不能在调用 mj_step 之前计算控制量呢？毕竟，因果性不就是这个意思吗？答案微妙但重要，它与我们是在离散时间中进行仿真这一事实有关。顶层仿真函数 mj_step 做两件事：在连续时间中计算 正动力学，然后在 mjModel.opt.timestep 指定的时间段上积分。正动力学根据时刻 mjData.time 的 状态与控制，计算该时刻的加速度 mjData.qacc 。随后数值积分器把状态和时间推进到 mjData.time + mjModel.opt.timestep 。现在，控制被要求是时刻 mjData.time 状态的函数。然而，一般的反馈控制器可能是非常复杂的函数，依赖于状态的各种特征——尤其是 MuJoCo 作为仿真中间结果计算出的所有特征，其中可能包括接触、雅可比矩阵、被动力。在调用 mj_step 之前，这些量都不可用（更准确地说，它们是可用的，但是 滞后了一个时间步长）。相比之下，当 mj_step 调用我们的控制回调函数时，它是在计算过程中尽可能晚的时刻调用的——也就是在所有依赖于状态但不依赖于控制的中间结果都已算出之后。

Why would we not be able to compute the controls before mj_step is called? After all, isn’t this what causality means? The answer is subtle but important, and has to do with the fact that we are simulating in discrete time. The top- level simulation function mj_step does two things: compute the forward dynamics in continuous time, and then integrate over a time period specified by mjModel.opt.timestep. Forward dynamics computes the acceleration mjData.qacc at time mjData.time, given the state and control at time mjData.time. The numerical integrator then advances the state and time to mjData.time + mjModel.opt.timestep. Now, the control is required to be a function of the state at time mjData.time. However a general feedback controller can be a very complex function, depending on various features of the state – in particular all the features computed by MuJoCo as intermediate results of the simulation. These may include contacts, Jacobians, passive forces. None of these quantities are available before mj_step is called (or rather, they are available but outdated by one time step). In contrast, when mj_step calls our control callback, it does so as late in the computation as possible – namely after all the intermediate results dependent on the state but not on the control have been computed.

不使用控制回调函数也可以达到同样的效果。做法是把 mj_step 拆成两部分：需要控制之前的部分，和需要控制之后的部分。这时仿真循环变为

The same effect can be achieved without using a control callback. This is done by breaking mj_step in two parts: before the control is needed, and after the control is needed. The simulation loop now becomes
while (d->time < 10) {
  mj_step1(m, d);
  // set d->ctrl or d->qfrc_applied or d->xfrc_applied
  mj_step2(m, d);
}

不过有一个复杂之处：这种方式只适用于单步 积分器 （Euler、implicit、implicitfast）。Runge-Kutta 积分器每一步需要多次计算包括反馈控制律在内的完整动力学，这只能通过控制回调函数来实现。对于单步积分器，上述把 mj_step 拆分为 mj_step1 和 mj_step2 的做法，足以把计算的中间结果提供给控制律。

There is one complication however: this only works with the single-step integrators (Euler, implicit, implicitfast). The Runge-Kutta integrator needs to evaluate the entire dynamics including the feedback control law multiple times per step, which can only be done using a control callback. With the single-step integrators, the above separation of mj_step into mj_step1 and mj_step2 is sufficient to provide the control law with the intermediate results of the computation.

为了使上面的讨论更清晰，我们给出 mj_step、mj_step1 和 mj_step2 的内部实现，省略了一些计算计时诊断信息的代码。主仿真函数为

To make the above discussion clearer, we provide the internal implementation of mj_step, mj_step1 and mj_step2, omitting some code that computes timing diagnostics. The main simulation function is
void mj_step(const mjModel* m, mjData* d) {
  // common to all integrators
  mj_checkPos(m, d);
  mj_checkVel(m, d);
  mj_forward(m, d);
  mj_checkAcc(m, d);

  // use selected integrator
  switch ((mjtIntegrator) m->opt.integrator) {
  case mjINT_EULER:
    mj_Euler(m, d);
    break;

  case mjINT_RK4:
    mj_RungeKutta(m, d, 4);
    break;

  case mjINT_IMPLICIT:
  case mjINT_IMPLICITFAST:
    mj_implicit(m, d);
    break;

  default:
    mjERROR("invalid integrator");
  }
}

如果任何数值变得无效或过大，检查函数会自动重置仿真。控制回调函数（如果有的话）是在正动力学函数内部被调用的。

The checking functions reset the simulation automatically if any numerical values have become invalid or too large. The control callback (if any) is called from within the forward dynamics function.

接下来我们展示两段式步进方式的实现，不过其中的细节要等到后文解释 正动力学 之后才能理解。注意，由于我们实质上把正动力学函数展开了，控制回调函数现在是被直接调用的。还要注意，在 mj_step2 中我们总是调用单步积分器；如果选择了 RK4，积分器会默认使用 Euler。

Next we show the implementation of the two-part stepping approach, although the specifics will make sense only after we explain the forward dynamics later. Note that the control callback is now called directly, since we have essentially unpacked the forward dynamics function. Note also that we always call a single-step integrator in mj_step2; if RK4 is selected, the integrator will default to Euler.
void mj_step1(const mjModel* m, mjData* d) {
  mj_checkPos(m, d);
  mj_checkVel(m, d);
  mj_fwdPosition(m, d);
  mj_sensorPos(m, d);
  mj_energyPos(m, d);
  mj_fwdVelocity(m, d);
  mj_sensorVel(m, d);
  mj_energyVel(m, d);

  // if we had a callback we would be using mj_step, but call it anyway
  if (mjcb_control)
    mjcb_control(m, d);
}

void mj_step2(const mjModel* m, mjData* d) {
  mj_fwdActuation(m, d);
  mj_fwdAcceleration(m, d);
  mj_fwdConstraint(m, d);
  mj_sensorAcc(m, d);
  mj_checkAcc(m, d);

  // integrate with Euler or implicit; RK4 defaults to Euler
  if (m->opt.integrator == mjINT_IMPLICIT || m->opt.integrator == mjINT_IMPLICITFAST)
    mj_implicit(m, d);
  else
    mj_Euler(m, d);
}

状态与控制#

State and control

MuJoCo 有一个定义明确的状态，易于设置、重置并随时间推进。这与动力系统状态的概念密切相关。动力系统通常用如下一般形式描述

MuJoCo has a well-defined state that is easy to set, reset and advance through time. This is closely related to the notion of state of a dynamical system. Dynamical systems are usually described in the general form
dx/dt = f(t, x, u)

其中 t 是时间， x 是状态向量， u 是控制向量， f 是计算状态时间导数的函数。这是一种连续时间的表述，MuJoCo 所仿真的物理模型确实是在连续时间中定义的。尽管数值积分器是在离散时间中运行的，计算的主要部分——即函数 mj_forward——对应于上面的连续时间动力学函数 f(t,x,u) 。下面我们解释这种对应关系。

where t is the time, x is the state vector, u is the control vector, and f is the function that computes the time-derivative of the state. This is a continuous-time formulation, and indeed the physics model simulated by MuJoCo is defined in continuous time. Even though the numerical integrator operates in discrete time, the main part of the computation—namely the function mj_forward—corresponds to the continuous-time dynamics function f(t,x,u) above. Below we explain this correspondence.

用户输入#

User inputs

这些输入字段 (mjSTATE_USER) 由用户设置并影响物理仿真，但不会被仿真器改动。除 MoCap 位姿外，所有输入字段默认为 0。所有 用户输入 数组的一个普遍性质是它们不会被库改动。因此，从写入该内存的值是持久的这个意义上讲，它们也可以被视为有状态的。

These input fields (mjSTATE_USER) are set by the user and affect the physics simulation, but are untouched by the simulator. All input fields except for MoCap poses default to 0. 热启动#

Warmstarts
热启动加速度： qacc_warmstart
Warmstart accelerations: qacc_warmstart

mjData.qacc_warmstart 是上一步的加速度，用于对约束求解器进行热启动。假设当前解与上一个解相差不大，这可以减少收敛所需的迭代次数，从而加快仿真。当使用像 PGS 这样收敛缓慢的 约束求解器 时，热启动可以减少收敛所需的迭代次数，从而加速仿真。不过请注意，默认的 Newton 求解器收敛得非常快（通常 2-3 次迭代），因此热启动对速度的影响往往可以忽略，可以将其 禁用。

mjData.qacc_warmstart are the previous step’s accelerations used to warmstart the constraint solver. Assuming that the current solution is not very different from the previous one, this can speed up simulation by reducing the number of iterations required for convergence. When using a slowly-converging constraint solver like PGS, these can speed up simulation by reducing the number of iterations required for convergence. Note however that the default Newton solver converges so quickly (usually 2-3 iterations), that warmstarts often have a negligible effect on speed and can be disabled.

由于我们的优化问题是 严格凸的，只有一个全局极小值，只要达到了收敛，不同的求解器初始化对解没有可察觉的影响。如果没有达到数值收敛，无论是由于收敛缓慢，还是由于 iterations 或 tolerance 被限制（如 MJX 中有时的做法），影响就会变得显著。

Because our optimization problem is strictly convex with a single global minimum, different solver initialization have no perceptible effect on the solution, assuming that convergence was achieved. The effect becomes significant if numerical convergence is not achieved, either due to slow convergence or if iterations or tolerance are capped, as is sometimes done in MJX.

热启动至关重要的另一种情形是需要完美的数值可复现性，即加载非初始状态时（因为初始状态总是冷启动的）。请注意，尽管热启动对物理的影响可以忽略，许多物理系统在时间步进时会 指数级 累积微小差异，使得不同热启动下的轨迹很快发散。更多细节参见 可复现性。

The other case where warmstarts are critical is if perfect numerical reproducibility is required, when loading a non-initial state (since the initial state is always cold-started). Note that even though their effect on physics is negligible, many physical systems will accumulate small differences exponentially when time-stepping, quickly leading to divergent trajectories for different warmstarts. See Reproducibility for more details.

积分状态#

Integration state

积分状态 (mjSTATE_INTEGRATION) 是上述所有 mjData 字段的并集，构成了 正动力学 的全部输入。具有相同积分状态的两个 mjData 实例，其流水线输出是完全相同的。对于 逆动力学， mjData.qacc 也被视为输入变量。所有其他 mjData 字段都是积分状态的函数。

The integration state (mjSTATE_INTEGRATION) is the union of all the above mjData fields and constitutes the entire set of inputs to the forward dynamics. The pipeline output of two mjData instances with the same integration state will be identical. In the case of inverse dynamics, mjData.qacc is also treated as an input variable. All other mjData fields are functions of the integration state.

注意，mjSTATE_INTEGRATION 给出的完整积分状态是最大化的，包含了通常用不到的字段。如果希望状态尺寸较小，避免保存未使用的字段可能是合理的。特别是 xfrc_applied 可能相当大（ nbody x 6 ），却经常用不到。

Note that the full integration state as given by mjSTATE_INTEGRATION is maximalist and includes fields which are often unused. If a small state size is desired, it might be sensible to avoid saving unused fields. In particular xfrc_applied can be quite large (nbody x 6) yet is often unused.

仿真状态#

Simulation state

仿真状态 是整个 mjData 结构体及其关联的内存缓冲区。该状态包含在动力学计算过程中得到的所有派生量。由于 mjData 缓冲区是按最坏情况预先分配的，从 积分状态 重新计算派生量，往往比使用 mj_copyData 快得多。关于启用休眠时仿真状态的注意事项，参见 休眠说明。

The simulation state is the entirety of the mjData struct and associated memory buffer. This state includes all derived quantities computed during dynamics computation. Because the mjData buffers are preallocated for the worst case, it is often significantly faster to recompute derived quantities from the integration state rather than using mj_copyData. See Notes on sleeping for caveats regarding the simulation state when sleeping is enabled.

正动力学#

Forward dynamics

正动力学（forward dynamics）的目标是计算状态的时间导数，即加速度向量 mjData.qacc 和激活的时间导数 mjData.act_dot 。在此过程中，它还会计算仿真动力学所需的其他一切，包括活动的接触和其他约束、关节空间惯性及其 \(L^TDL\) 分解、约束力、传感器数据等。所有这些中间结果都可以在 mjData 中获得，并可用于自定义计算。如上文 仿真循环 一节所示，主步进函数 mj_step 调用 mj_forward 完成大部分工作，然后调用数值积分器把仿真状态推进到下一个离散时间点。

The goal of forward dynamics is to compute the time-derivative of the state, namely the acceleration vector mjData.qacc and the activation time-derivative mjData.act_dot. Along the way it computes everything else needed to simulate the dynamics, including active contacts and other constraints, joint-space inertia and its \(L^TDL\) decomposition, constraint forces, sensor data and so on. All these intermediate results are available in mjData and can be used in custom computations. As illustrated in the simulation loop section above, the main stepper function mj_step calls mj_forward to do most of the work, and then calls the numerical integrator to advance the simulation state to the next discrete point in time.

正动力学函数 mj_forward 在内部以跳过参数 (mjSTAGE_NONE, 0) 调用 mj_forwardSkip，后者的实现如下

The forward dynamics function mj_forward internally calls mj_forwardSkip with skip arguments (mjSTAGE_NONE, 0), where the latter function is implemented as
void mj_forwardSkip(const mjModel* m, mjData* d, int skipstage, int skipsensor) {
  // position-dependent
  if (skipstage < mjSTAGE_POS) {
    mj_fwdPosition(m, d);
    if (!skipsensor)
      mj_sensorPos(m, d);
    if (mjENABLED(mjENBL_ENERGY))
      mj_energyPos(m, d);
  }

  // velocity-dependent
  if (skipstage < mjSTAGE_VEL) {
    mj_fwdVelocity(m, d);
    if (!skipsensor)
      mj_sensorVel(m, d);
    if (mjENABLED(mjENBL_ENERGY))
      mj_energyVel(m, d);
  }

  // acceleration-dependent
  if (mjcb_control)
    mjcb_control(m, d);
  mj_fwdActuation(m, d);
  mj_fwdAcceleration(m, d);
  mj_fwdConstraint(m, d);
  if (!skipsensor)
    mj_sensorAcc(m, d);
}

注意，这与上文 mj_step1 和 mj_step2 中的调用序列相同，只是省略了实数值的检查以及传感器和能量等特征的计算。被调用的函数是仿真流水线的组成部分，它们又会调用各自的子组件。

Note that this is the same sequence of calls as in mj_step1 and mj_step2 above, except that checking of real values and computing features such as sensor and energy are omitted. The functions being called are components of the simulation pipeline. In turn they call sub-components.

整数参数 skipstage 决定哪些部分的计算会被跳过。可选的跳过级别有

The integer argument skipstage determines which parts of the computation will be skipped. The possible skip levels are
mjSTAGE_NONE

不跳过任何内容，运行所有计算。

Skip nothing. Run all computations.
mjSTAGE_POS

跳过依赖于位置、但不依赖于速度、控制或施加力的计算。这类计算的例子包括正运动学、碰撞检测（collision detection）、惯性矩阵的计算与分解。这些计算通常占用最多的 CPU 时间，应尽可能跳过（见下文）。

Skip computations that depend on position but not on velocity or control or applied force. Examples of such computations include forward kinematics, collision detection, inertia matrix computation and decomposition. These computations typically take the most CPU time and should be skipped when possible (see below).
mjSTAGE_VEL

跳过依赖于位置和速度、但不依赖于控制或施加力的计算。例子包括科里奥利力和离心力的计算、被动阻尼力、约束稳定的参考加速度。

Skip computations that depend on position and velocity but not on control or applied force. Examples include the computation of Coriolis and centrifugal forces, passive damping forces, reference accelerations for constraint stabilization.

mjData 的中间结果字段按照计算它们所需的状态部分分成若干区段。以 mjSTAGE_POS 调用 mj_forwardSkip 时，假定第一区段（依赖于位置）的字段已经算好，不会重新计算。类似地，mjSTAGE_VEL 假定第一和第二区段（依赖于位置和速度）的字段已经算好。

The intermediate result fields of mjData are organized into sections according to which part of the state is needed in order to compute them. Calling mj_forwardSkip with mjSTAGE_POS assumes that the fields in the first section (position dependent) have already been computed and does not recompute them. Similarly, mjSTAGE_VEL assumes that the fields in the first and second sections (position and velocity dependent) have already been computed.

什么时候可以使用上述机制并跳过部分计算呢？在常规仿真中这是不可能的。然而，MuJoCo 的设计不仅用于仿真，还用于更高级的应用，如基于模型的优化、机器学习等。在这类场景中，常常需要在一簇邻近状态处对动力学采样，或者通过有限差分来近似导数——这是另一种形式的采样。如果采样点按网格排列，其中只有位置、或只有速度、或只有控制与中心点不同，那么上述机制可以使性能提升约 2 倍。

When can we use the above machinery and skip some of the computations? In a regular simulation this is not possible. However, MuJoCo is designed not only for simulation but also for more advanced applications such as model-based optimization, machine learning etc. In such settings one often needs to sample the dynamics at a cloud of nearby states, or approximate derivatives via finite differences – which is another form of sampling. If the samples are arranged on a grid, where only the position or only the velocity or only the control is different from the center point, then the above mechanism can improve performance by about a factor of 2.

逆动力学#

Inverse dynamics

逆动力学（inverse dynamics）的计算是 MuJoCo 的一项独有特性，在其他任何能够仿真接触的现代引擎中都找不到。得益于概述章节中介绍的 软约束模型，逆动力学定义明确且计算非常高效。事实上，一旦完成了与正动力学共享的、依赖于位置和速度的计算，在给定加速度的情况下恢复约束力和施加力就归结为一个解析公式。这个过程非常快，以至于我们实际上用逆动力学（使用上一个时间步长计算出的加速度）来对正动力学中的迭代约束求解器进行热启动。

The computation of inverse dynamics is a unique feature of MuJoCo, and is not found in any other modern engine capable of simulating contacts. Inverse dynamics are well-defined and very efficient to compute, thanks to our soft-constraint model described in the Overview chapter. In fact once the position and velocity-dependent computations that are shared with forward dynamics have been performed, the recovery of constraint and applied forces given the acceleration comes down to an analytical formula. This is so fast that we actually use inverse dynamics (with the acceleration computed at the previous time step) to warm-start the iterative constraint solver in forward dynamics.

逆动力学的输入与正动力学中的状态向量相同，如 状态与控制 中所示，但不包括 mjData.act 和 mjData.time 。假设没有依赖于用户自定义状态变量的回调函数，逆动力学的输入是 mjData 的以下字段：

The inputs to inverse dynamics are the same as the state vector in forward dynamics as illustrated in state and control, but without mjData.act and mjData.time. Assuming no callbacks that depend on user- defined state variables, the inputs to inverse dynamics are the following fields of mjData:
(mjData.qpos, mjData.qvel, mjData.qacc, mjData.mocap_pos, mjData.mocap_quat)

主要输出是 mjData.qfrc_inverse 。这是为了实现观测到的加速度 mjData.qacc ，必须作用在系统上的力。如果正动力学通过让迭代求解器运行到完全收敛而被精确计算，我们将有

The main output is mjData.qfrc_inverse. This is the force that must have acted on the system in order to achieve the observed acceleration mjData.qacc. If forward dynamics were to be computed exactly, by running the iterative solver to full convergence, we would have
mjData.qfrc_inverse = mjData.qfrc_applied + Jacobian'*mjData.xfrc_applied + mjData.qfrc_actuator

其中 mjData.qfrc_actuator 是执行器产生的关节空间力，雅可比矩阵是从关节空间到笛卡尔空间的映射。当 mjModel.opt.enableflags 中的 fwdinv 标志被设置时，上述恒等式被用来监测正动力学解的质量。具体而言， mjData.solver_fwdinv 的两个分量被设置为正动力学解与逆动力学解之差的 L2 范数，分别针对关节力和约束力。

where mjData.qfrc_actuator is the joint-space force produced by the actuators and the Jacobian is the mapping from joint to Cartesian space. When the fwdinv flag in mjModel.opt.enableflags is set, the above identity is used to monitor the quality of the forward dynamics solution. In particular, the two components of mjData.solver_fwdinv are set to the L2 norm of the difference between the forward and inverse solutions, in terms of joint forces and constraint forces respectively.

与正动力学类似，mj_inverse 在内部以跳过参数 (mjSTAGE_NONE, 0) 调用 mj_inverseSkip。跳过机制与正动力学中相同，可用于加速结构化采样。结果 mjData.qfrc_inverse 是这样得到的：先用递归牛顿-欧拉算法（Recursive Newton-Euler）计算作用在系统上的净力，再从中减去所有内力。

Similar to forward dynamics, mj_inverse internally calls mj_inverseSkip with skip arguments (mjSTAGE_NONE, 0). The skip mechanism is the same as in forward dynamics, and can be used to speed up structured sampling. The result mjData.qfrc_inverse is obtained by using the Recursive Newton-Euler algorithm to compute the net force acting on the system, and then subtracting from it all internal forces.

当有实验数据可用时，逆动力学可以作为一种分析工具。这在机器人学和生物力学中很常见。它也可用于计算驱动系统沿给定参考轨迹运动所需的关节力矩，这称为计算力矩控制。在状态估计、系统辨识和最优控制的情境中，它可用于优化循环内部，寻找在最小化其他代价的同时使物理违背最小的状态序列。物理违背可以量化为逆动力学计算出的任何无法解释的外力的范数。

Inverse dynamics can be used as an analytical tool when experimental data are available. This is common in robotics as well as biomechanics. It can also be used to compute the joint torques needed to drive the system along a given reference trajectory; this is known as computed torque control. In the context of state estimation, system identification and optimal control, it can be used within an optimization loop to find sequences of states that minimize physics violation along with other costs. Physics violation can be quantified as the norm of any unexplained external force computed by inverse dynamics.

多线程#

Multi-threading

MuJoCo 支持步内多线程。当通过 mju_threadpool 初始化线程池后，仿真流水线的若干部分——例如碰撞检测和跨 岛 的约束求解——可以分布到工作线程上。

MuJoCo has support for within-step multi-threading. When a thread pool is initialized via mju_threadpool, parts of the simulation pipeline — such as collision detection and constraint solving across islands — can be distributed across worker threads.

更常见且支持更完善的多线程用法，是加速更高级应用中常见的采样操作。仿真在时间上本质上是串行的（一次 mj_step 的输出是下一次的输入），而在采样中，对正动力学或逆动力学的许多调用可以并行执行，因为它们之间没有依赖关系，至多共用一个初始状态。

The more common and well-supported use of multi-threading is to speed up sampling operations that are common in more advanced applications. Simulation is inherently serial over time (the output of one mj_step is the input to the next), while in sampling many calls to either forward or inverse dynamics can be executed in parallel since there are no dependencies among them, except perhaps for a common initial state.

MuJoCo 从一开始就是为多线程设计的。在大多数现有仿真器中，动力系统状态的概念很难映射到软件状态，往往分散在多个对象中；而在 MuJoCo 中，我们有统一的数据结构 mjData，其中包含了所有随时间变化的内容。请回顾关于 状态与控制 的讨论。关键思想是为每个线程创建一个 mjData，然后用它完成该线程的所有计算。下面是一般模板，使用 OpenMP 来简化线程管理。

MuJoCo was designed for multi-threading from its beginning. Unlike most existing simulators where the notion of dynamical system state is difficult to map to the software state and is often distributed among multiple objects, in MuJoCo we have the unified data structure mjData which contains everything that changes over time. Recall the discussion of state and control. The key idea is to create one mjData for each thread, and then use it for all per-thread computations. Below is the general template, using OpenMP to simplify thread management.
// prepare OpenMP
int nthread = omp_get_num_procs();      // get number of logical cores
omp_set_dynamic(0);                     // disable dynamic scheduling
omp_set_num_threads(nthread);           // number of threads = number of logical cores

// allocate per-thread mjData
mjData* d[64];
for (int n=0; n < nthread; n++)
  d[n] = mj_makeData(m);

// ... serial code, perhaps using its own mjData* dmain

// parallel section
#pragma omp parallel
{
  int n = omp_get_thread_num();       // thread-private variable with thread id (0 to nthread-1)

  // ... initialize d[n] from results in serial code

  // thread function
  worker(m, d[n]);                    // shared mjModel (read-only), per-thread mjData (read-write)
}

// delete per-thread mjData
for (int n=0; n < nthread; n++)
  mj_deleteData(d[n]);

由于所有顶层 API 函数都把 mjModel 视为 const ，这种多线程方案是安全的。每个线程只写入它自己的 mjData，因此线程之间不需要进一步同步。

Since all top-level API functions treat mjModel as const, this multi-threading scheme is safe. Each thread only writes to its own mjData. Therefore no further synchronization among threads is needed.

上述模板体现了一种特定的并行处理风格。我们并不是创建大量线程（每个工作项一个）再让 OpenMP 把它们分配给处理器，而是依靠手动调度。更准确地说，我们创建与处理器数量相同的线程，然后在 worker 函数内部把工作显式分配给各线程。这种方法更高效，因为与处理器缓存相比，线程专用的 mjData 很大。

The above template reflects a particular style of parallel processing. Instead of creating a large number of threads, one for each work item, and letting OpenMP distribute them among processors, we rely on manual scheduling. More precisely, we create as many threads as there are processors, and then within the worker function we distribute the work explicitly among threads. This approach is more efficient because the thread-specific mjData is large compared to the processor cache.

出于缓存效率，我们还使用共享的 mjModel。在某些情况下，可能无法让所有线程使用同一个 mjModel。一个显而易见的原因是，mjModel 可能需要在线程函数中被修改。另一个原因是，包含在 mjModel 中的 mjOption 结构可能需要调整（例如为了控制求解器迭代次数），不过这对所有并行线程很可能是相同的，因此可以在并行段之前对共享模型进行调整。

We also use a shared mjModel for cache-efficiency. In some situations it may not be possible to use the same mjModel for all threads. One obvious reason is that mjModel may need to be modified within the thread function. Another reason is that the mjOption structure which is contained within mjModel may need to be adjusted (so as to control the number of solver iterations for example), although this is likely to be the same for all parallel threads and so the adjustment can be made in the shared model before the parallel section.

线程专用的 mjData 如何初始化、线程函数做什么，当然取决于具体应用。不过，前面章节中的一般效率准则在这里同样适用。把状态复制到线程专用的 mjData 中，再运行 MuJoCo 来填充其余部分，可能比使用 mj_copyData 更快。此外，正动力学和逆动力学中都有的跳过机制在并行采样应用中特别有用，因为样本通常具有某种结构，使得某些计算可以复用。最后请记住，正动力学求解器是迭代的，良好的热启动可以大幅减少所需的迭代次数。当样本在状态和控制空间中彼此接近时，可以用其中一个样本（理想情况下是位于中心的样本）的解来热启动所有其他样本。在这种设置下，重要的是确保邻近样本之间不同的结果反映的是样本间真实的差异，而不是迭代求解器的热启动或终止条件不同所致。

How the thread-specific mjData is initialized and what the thread function does is of course application-dependent. Nevertheless, the general efficiency guidelines from the earlier sections apply here. Copying the state into the thread-specific mjData and running MuJoCo to fill in the rest may be faster than using mj_copyData. Furthermore, the skip mechanism available in both forward and inverse dynamics is particularly useful in parallel sampling applications, because the samples usually have structure allowing some computations to be re-used. Finally, keep in mind that the forward solver is iterative and good warm-start can substantially reduce the number of necessary iterations. When samples are close to each other in state and control space, the solution for one sample (ideally in the center) can be used to warm-start all the other samples. In this setting it is important to make sure that the different results between nearby samples reflect genuine differences between the samples, and not different warm-start or termination of the iterative solver.

批量仿真#

Batched simulation

mujoco/mjbatch.h 中的 批量 API 封装了这种多线程方案。一个 mjBatch 持有同一个模型的 nsim 个仿真，并在它自己的线程池上运行它们。无论线程数是多少，结果都与对每个仿真使用一个 mjData 的串行循环逐位一致。下面各段介绍该 API 所基于的概念；细节见 函数参考。

The batch API in mujoco/mjbatch.h packages this multi-threading scheme. An mjBatch holds nsim simulations of one model and runs them on a thread pool of its own. Results are bit-identical to a serial loop over one mjData per simulation, at any thread count. The paragraphs below introduce the concepts the API is built on; the function reference has the details.

状态行。 一个仿真就是它的 积分状态：即正动力学的输入，其他所有 mjData 字段都是它的函数。批量对象把这些状态保存在由 mjb_state 返回的表中，这是一个 nsim x nstate 的数组，其第 i 行是仿真 i 的状态，其中 nstate 为 mjb_nstate。这些行是唯一的输入存储。写入 ctrl 、 qpos 、 mocap_pos 或施加力，就是写入行中相应的部分，其地址由 mjb_stateComponent 给出，该写入会成为该仿真在下一次调用时的状态。每个仿真还有警告计数器，由 mjb_warning 返回，它们随其所在的行一同保存和恢复。

State rows. A simulation is its integration state: the inputs to the forward dynamics, of which every other mjData field is a function. The batch keeps these states in a table returned by mjb_state, an nsim x nstate array whose row i is simulation i’s state, where nstate is mjb_nstate. The rows are the only input storage. Writing to ctrl, qpos, mocap_pos or the applied forces means writing to the corresponding part of a row, whose address mjb_stateComponent gives, and the write becomes that simulation’s state at its next call. Each simulation also has warning counters, returned by mjb_warning, which are saved and restored with its row.

调用。 诸如 mjb_step 的调用在由 ids 选定的仿真上运行，或在全部仿真上运行。对每个仿真，它会把该行加载到一个 mjData 中，运行所请求的计算，然后把该行保存回去。如果 MuJoCo 在某个仿真中引发错误，该仿真保持其先前的状态，其他仿真则运行至完成；mjb_status 和 mjb_error 会报告发生了什么。

Calls. A call such as mjb_step runs on the simulations selected by ids, or on all of them. For each simulation, it loads the row into an mjData, runs the requested computation, and saves the row back. If MuJoCo raises an error in a simulation, that simulation keeps its previous state and the others run to completion; mjb_status and mjb_error report what happened.

输出。 诸如 xpos 或 sensordata 的派生量不属于状态，因此当 mjData 转去处理下一个仿真时，它们会丢失。mjb_output 把某个 mjData 字段注册为一个 输出：每次调用之后，批量对象都会把它从每个仿真的 mjData 中复制到由批量对象拥有的 nsim x size 数组中。

Outputs. Derived quantities such as xpos or sensordata are not part of the state, so they would be lost when the mjData moves on to the next simulation. mjb_output registers an mjData field as an output: after every call, the batch copies it out of each simulation’s mjData into an nsim x size array that the batch owns.

共享与持久的 mjData。 默认情况下，批量对象为每个线程保留一个 mjData，各线程对它所运行的仿真重复使用该 mjData，因此内存随线程数而不是仿真数增长。此时状态之外的一切都是共享的。调用中未计算的字段，例如 mj_step 之后的 qfrc_inverse ，保存的是另一个仿真的值；而把状态保存在 plugin_state 之外的 引擎插件，会在一个线程所运行的各个仿真之间共享这些状态。配置 为 持久 的批量对象则改为每个仿真保留一个 mjData，代价是需要 nsim 个 mjData 的内存。此时每个字段和插件实例都是该仿真自己的，而 mjb_getData 会复制整个 mjData。启用了 休眠 或 IPC 的模型需要持久批量对象，因为它们的记录信息保存在 mjData 中而不是状态里。

Shared and persistent mjData. By default, a batch keeps one mjData per thread, which each thread reuses for the simulations it runs, so memory scales with threads rather than simulations. Anything outside the state is then shared. A field the call does not compute, such as qfrc_inverse after mj_step, holds another simulation’s value, and engine plugins that keep state outside plugin_state share it among the simulations a thread runs. A batch configured to be persistent keeps one mjData per simulation instead, at the cost of nsim mjData of memory. Every field and plugin instance is then the simulation’s own, and mjb_getData copies the whole mjData. Models with sleep or IPC enabled require a persistent batch, because their bookkeeping lives in the mjData rather than in the state.

阶段。 在 mj_step 之后，派生字段描述的是最后一个子步 之前 的状态，因为一步先计算它们、然后再积分；参见 mjData 中的一致性。要观察新状态，执行步进或重置的调用接受一个 stage 参数（一个 mjtStage）：调用完成后，批量对象会在新状态下运行 mj_forward 中直到 stage 的各个阶段。 mjSTAGE_VEL 计算位置、速度以及依赖于它们的传感器，就像 mj_step1 所做的那样，这通常正是策略所观察的内容。 mjSTAGE_ACC 则运行 mj_forward 的全部阶段。详见 mjb_step。

Stages. After mj_step, derived fields describe the state before the last substep, because a step computes them first and then integrates; see Consistency in mjData. To observe the new state, the calls that step or reset take a stage argument (an mjtStage): when the call is done, the batch runs the stages of mj_forward up to stage at the new state. mjSTAGE_VEL computes positions, velocities and the sensors that depend on them, as mj_step1 does, which is what a policy typically observes. mjSTAGE_ACC runs all of mj_forward. See mjb_step for the details.

延续。 mj_step 就是 mj_step1 后接 mj_step2：前者计算位置和速度阶段，后者完成这一步。因此，以 mjSTAGE_VEL 观察新状态所做的工作，与下一步的前半部分相同。在持久批量对象中，仿真的 mjData 在下一次调用时仍保存着这些阶段的结果，因此下一步会跳过它们，并以 mj_step2 延续，这样获取新的观测不需要额外开销。只有当结果与完整步进的结果相同时，批量对象才会延续一步：即自这些阶段被计算以来，除 ctrl 、 qfrc_applied 和 xfrc_applied （只有 mj_step2 会读取它们）之外，它们所依赖的内容没有任何改变。非持久的批量对象无法延续，因为其间它的 mjData 已经为其他仿真服务过了。确切条件见 mjb_step。

Continuation. mj_step is mj_step1 followed by mj_step2: the first computes the position and velocity stages, and the second completes the step. Observing the new state with mjSTAGE_VEL is therefore the same work as the first half of the next step. In a persistent batch, the simulation’s mjData still holds those stages at the next call, so the next step skips them and continues with mj_step2, and fresh observations cost nothing extra. The batch continues a step only when the result is the same as that of a full step: when nothing the stages depend on has changed since they were computed, other than ctrl, qfrc_applied and xfrc_applied, which only mj_step2 reads. A batch that is not persistent cannot continue, since its mjData have served other simulations in between. See mjb_step for the exact conditions.

每个仿真独立的模型。 所有仿真共享由 mjb_makeBatch 制作的批量对象自己的模型副本。若要让各仿真拥有不同的模型或选项值，例如随机化质量、摩擦或重力，可由 mjb_expand 来 展开 一个字段。它返回一个由批量对象拥有、以模型的值初始化的 nsim x size 数组，在对仿真 i 的每次调用之前，其第 i 行会被复制到模型中。选项 字段命名为 "opt.<name>" ，网格和纹理等资源字段无法被展开。对展开字段的写入不会更新 mj_setConst 由它们导出的常量，例如各刚体的逆质量权重；mjb_setConst 会为每个仿真运行 mj_setConst，并展开它改变的每一个字段。另一种做法是，mjb_setModels 让每个仿真在调用者编译的模型上运行，例如由同一个 spec 以不同参数编译而来，只要这些模型给出的 mjData 布局与批量对象的模型相同即可。无论哪种方式，mjb_getModel 都会把某个仿真的完整模型写入调用者分配的 mjModel 中，用于渲染或传给任何函数。

Per-simulation models. All simulations share the batch’s copy of the model, made by mjb_makeBatch. To give simulations different model or option values, for example to randomize masses, friction or gravity, mjb_expand expands a field. It returns an nsim x size array, owned by the batch and initialized with the model’s values, whose row i is copied into the model before each call on simulation i. Option fields are named "opt.<name>", and asset fields such as meshes and textures cannot be expanded. Writes to expanded fields do not update the constants that mj_setConst derives from them, such as the bodies’ inverse weights; mjb_setConst runs mj_setConst for each simulation and expands every field it changes. Alternatively, mjb_setModels runs each simulation on a model the caller compiled, for example from one spec with different parameters, as long as it gives mjData the same layout as the batch’s model. Either way, mjb_getModel writes one simulation’s complete model into an mjModel the caller allocates, for rendering or to pass to any function.

轨迹与查询。 mjb_rollout 记录开环轨迹：它施加给定的控制序列，并在每个子步之后记录选定的状态或字段。mjb_apply 在每个仿真的模型和数据上运行任意函数，用于雅可比或导数等查询；示例见其参考文档。

Trajectories and queries. mjb_rollout records open-loop trajectories: it applies a given control sequence and records chosen states or fields after every substep. mjb_apply runs any function on each simulation’s model and data, for queries such as Jacobians or derivatives; see its reference for examples.
const int nsim = 1024;  // number of simulations
const int nstep = 500;  // number of control steps

// allocate batch
char error[1000];
mjBatchConfig config;
mjb_defaultConfig(&config);
config.nthread = 8;  // default 0: all logical CPUs, at most nsim
mjBatch* b = mjb_makeBatch(m, nsim, &config, error, sizeof(error));
if (!b) {
  mju_error("could not make batch: %s", error);
}

// pointers into storage that the batch owns, valid until mjb_deleteBatch
int nstate = mjb_nstate(b);                                // length of a state row
mjtNum* ctrl = mjb_stateComponent(b, mjSTATE_CTRL, NULL);  // ctrl in row 0; row i is nstate*i further
mjtNum* xpos = mjb_output(b, "xpos", NULL, NULL);          // nsim x 3*nbody, copied after every call

// reset all simulations to the model's defaults, then compute every stage so that xpos is current
mjb_reset(b, /*ids=*/NULL, 0, /*key=*/NULL, mjSTAGE_ACC);

for (int k=0; k < nstep; k++) {
  // write each simulation's controls into its row, from observations of its current state
  for (int i=0; i < nsim; i++) {
    policy(xpos + 3*m->nbody*i, ctrl + nstate*i);
  }

  // step every simulation once, then compute positions at the new state for the next observations
  if (mjb_step(b, /*ids=*/NULL, 0, 1, mjSTAGE_VEL)) {
    // simulations that raised an error kept their previous state; see mjb_status and mjb_error
  }
}

// delete memory and threadpool
mjb_deleteBatch(b);

线程与回调。 批量对象的线程跨仿真运行，而 mju_threadpool 的线程则在单个仿真内部运行。两者不会结合使用，批量对象从不安装引擎线程池。诸如 mjcb_control 的全局回调函数在批量对象的线程上并发运行，并且不会被告知它们服务于哪个仿真；针对各个仿真的工作应放在 mjb_apply 中。

Threads and callbacks. The batch’s threads run across simulations, while those of mju_threadpool run within one simulation. The two are not combined, and the batch never installs an engine thread pool. Global callbacks such as mjcb_control run on the batch’s threads, concurrently, and are not told which simulation they serve; per-simulation work belongs in mjb_apply.

数据布局#

Data layout

MuJoCo 中的所有矩阵都采用 行主序（row-major） 格式。例如，线性内存数组 (a0, a1, ... a5) 表示如下的 2 行 3 列矩阵

All matrices in MuJoCo are in row-major format. For example, the linear memory array (a0, a1, … a5) represents the 2-by-3 matrix
a0 a1 a2
a3 a4 a5

这种约定传统上与 C 语言相关联，而相反的列主序（column-major）约定则与 Fortran 相关联。选择哪一种并没有特别的理由，但无论选择哪一种，都必须时刻牢记。MuJoCo 中所有对矩阵进行运算的工具函数，例如 mju_mulMatMat、mju_mulMatVec 等，都假定采用这种矩阵布局。对于向量而言，行主序和列主序格式当然没有区别。

This convention has traditionally been associated with C, while the opposite column-major convention has been associated with Fortran. There is no particular reason to choose one over the other, but whatever the choice is, it is essential to keep it in mind at all times. All MuJoCo utility functions that operate on matrices, such as mju_mulMatMat, mju_mulMatVec etc. assume this matrix layout. For vectors there is of course no difference between row-major and column-major formats.

只要可能，MuJoCo 就会利用稀疏性。这可能决定了计算量是按 O(N) 还是按 O(N^3) 增长。惯性矩阵（inertia matrix） mjData.qM 及其 LTDL 分解 mjData.qLD 始终以稀疏形式表示。qM 使用为对应于树形拓扑的矩阵设计的自定义索引格式，而 qLD 使用标准的 CSR 格式。qM 将在后续的更新中迁移到 CSR。函数 mj_factorM、mj_solveM、mj_solveM2 和 mj_mulM 用于稀疏分解、代入以及矩阵-向量乘法。用户也可以使用函数 mj_fullM 将这些矩阵转换为稠密格式，不过 MuJoCo 内部从不这样做。

When possible, MuJoCo exploits sparsity. This can make all the difference between O(N) and O(N^3) scaling. The inertia matrix mjData.qM and its LTDL factorization mjData.qLD are always represented as sparse. qM uses a custom indexing format designed for matrices that correspond to tree topology, while qLD uses the standard CSR format. qM will be migrated to CSR in an upcoming change. The functions mj_factorM, mj_solveM, mj_solveM2 and mj_mulM are used for sparse factorization, substitution and matrix-vector multiplication. The user can also convert these matrices to dense format with the function mj_fullM although MuJoCo never does that internally.

只要启用了稀疏雅可比选项，约束雅可比矩阵（Jacobian） mjData.efc_J 就以稀疏形式表示。函数 mj_isSparse 可用于判断当前是否正在使用稀疏格式。在这种情况下，转置雅可比矩阵 mjData.efc_JT 也会被计算，并且约束逆惯性 mjData.efc_AR 也变为稀疏。稀疏矩阵以压缩稀疏行（CSR）格式存储。对于维度为 m 行 n 列的一般矩阵 A，该格式如下：

In that case the transposed Jacobian mjData.efc_JT is also computed, and the inverse constraint inertia mjData.efc_AR becomes sparse. We call this sparse layout “uncompressed”. It is still a valid layout, but instead of A_rowadr[r] = A_rowadr[r-1] + A_rownnz[r] which is the standard convention, we set A_rowadr[r] = r*n. 为了表示三维朝向和旋转，MuJoCo 使用单位四元数（quaternion），即排列为 q = (w, x, y, z) 的四维单位向量。其中 (x, y, z) 是旋转轴单位向量乘以 sin(a/2)，a 为以弧度计的旋转角，而 w = cos(a/2)。因此，零旋转对应的四元数为 (1, 0, 0, 0)。这是 MJCF 中所有四元数的默认设置。

To represent 3D orientations and rotations, MuJoCo uses unit quaternions – namely 4D unit vectors arranged as q = (w, x, y, z). Here (x, y, z) is the rotation axis unit vector scaled by sin(a/2), where a is the rotation angle in radians, and w = cos(a/2). Thus the quaternion corresponding to a null rotation is (1, 0, 0, 0). This is the default setting of all quaternions in MJCF.

MuJoCo 内部还使用 6 维空间向量（spatial vector）。它们是 mjData 中以 'c' 为前缀的量，即 cvel、cacc、cdot 等。它们是空间运动向量和空间力向量，由 3 维旋转分量后接 3 维平移分量组合而成。我们不提供处理它们的工具函数，对其进行详细说明也超出了本文的范围。请参阅 Roy Featherstone 的网页 空间代数（Spatial Algebra）。这种不寻常的顺序（旋转在前，平移在后）源自该资料，并且过去显然是标准约定。

MuJoCo also uses 6D spatial vectors internally. These are quantities in mjData prefixed with ‘c’, namely cvel, cacc, cdot, etc. They are spatial motion and force vectors that combine a 3D rotational component followed by a 3D translational component. We do not provide utility functions for working with them, and documenting them is beyond our scope here. See Roy Featherstone’s webpage on Spatial Algebra. The unusual order (rotation before translation) is based on this material, and was apparently standard convention in the past.

数据结构 mjModel 和 mjData 包含许多指向预分配缓冲区的指针。这些数据结构的构造函数（mj_makeModel 和 mj_makeData）会分配一个大缓冲区，即 mjModel.buffer 和 mjData.buffer，然后对其进行划分并设置其中所有其他指针。如下文所述，mjData 在这个主缓冲区之外还包含一个栈。即使两个指针前后相邻，例如 mjData.qpos 和 mjData.qvel，也不要假定这些数据数组是连续的、彼此之间没有间隙。构造函数会对每个数据数组实施字节对齐，并在必要时跳过若干字节。因此，如果要复制 mjData.qpos 和 mjData.qvel，正确的做法是老老实实地分开处理：

The data structures mjModel and mjData contain many pointers to preallocated buffers. The constructors of these data structures (mj_makeModel and mj_makeData) allocate one large buffer, namely mjModel.buffer and mjData.buffer, and then partition it and set all the other pointers in it. mjData also contains a stack outside this main buffer, as discussed below. Even if two pointers appear one after the other, say mjData.qpos and mjData.qvel, do not assume that the data arrays are contiguous and there is no gap between them. The constructors implement byte-alignment for each data array, and skip bytes when necessary. So if you want to copy mjData.qpos and mjData.qvel, the correct way to do it is the hard way:
// do this
mju_copy(myqpos, d->qpos, m->nq);
mju_copy(myqvel, d->qvel, m->nv);

// DO NOT do this, there may be padding at the end of d->qpos
mju_copy(myqposqvel, d->qpos, m->nq + m->nv);

可选头文件 mjxmacro.h 中定义的 X 宏 可用于自动分配与 mjModel 和 mjData 相匹配的数据结构，例如在为脚本语言编写 MuJoCo 封装时。

The X Macros defined in the optional header file mjxmacro.h can be used to automate allocation of data structure that match mjModel and mjData, for example when writing a MuJoCo wrapper for a scripting language.

内部栈#

Internal stack

MuJoCo 在 mjData.arena 中的“竞技场”（arena）空间里分配和管理动态内存。arena 内存空间包含两类动态分配的内存：

MuJoCo allocates and manages dynamic memory in an “arena” space in mjData.arena. The arena memory space contains two types of dynamically allocated memory:

  • 与约束相关的内存，因为在一个时间步开始时接触的数量是未知的。

    Memory related to constraints, since the number of contacts is unknown at the beginning of a step.

  • 临时变量的内存，由内部栈机制管理。

    Memory for temporary variables, managed by an internal stack mechanism.

关于 arena 和内部栈布局的详细信息，请参阅 内存分配。

See Memory allocation for details regarding the layout of the arena and internal stack.

大多数顶层的 MuJoCo 函数会在 mjData 的栈上分配空间，将其用于内部计算，然后再释放。它们无法使用常规的 C 栈来完成这些工作，因为分配大小是在运行时动态确定的。调用堆内存管理函数则效率低下，并且会导致内存碎片，因此才有了自定义栈。调用任何 MuJoCo 函数后，返回时 mjData.pstack 的值都与调用前相同。唯一的例外是函数 mj_resetData 及其变体：它们会设置 mjData.pstack = 0。请注意，当 mj_step、mj_step1 和 mj_step2 检测到不稳定时，会在内部调用该函数。因此，如果用户函数要利用自定义栈，就需要在两次可能重置仿真的 MuJoCo 调用之间进行。

Most top-level MuJoCo functions allocate space on the mjData stack, use it for internal computations, and then deallocate it. They cannot do this with the regular C stack because the allocation size is determined dynamically at runtime. Calling the heap memory management functions would be inefficient and result in fragmentation – thus a custom stack. When any MuJoCo function is called, upon return the value of mjData.pstack is the same. The only exception is the function mj_resetData and its variants: they set mjData.pstack = 0. Note that this function is called internally when an instability is detected in mj_step, mj_step1 and mj_step2. So if user functions take advantage of the custom stack, this needs to be done in-between MuJoCo calls that have the potential to reset the simulation.

下面是在用户代码中使用自定义栈的一般模板。

Below is the general template for using the custom stack in user code.
// mark an mjData stack frame
mj_markStack(d);

// allocate space
mjtNum* myqpos = mj_stackAllocNum(d, m->nq);
mjtNum* myqvel = mj_stackAllocNum(d, m->nv);

// restore the mjData stack frame
mj_freeStack(d);

函数 mj_stackAllocNum 会检查是否有足够的空间，如果有，就推进栈指针，否则触发错误。它还会记录栈分配的最大值；参见下文的 诊断。请注意，mj_stackAllocNum 仅用于分配 mjtNum 数组，这是最常见的数组类型。mj_stackAllocInt 用于分配整数数组，mj_stackAllocByte 则用于分配任意字节数及对齐方式的内存。

The function mj_stackAllocNum checks if there is enough space, and if so it advances the stack pointer, otherwise it triggers an error. It also keeps track of the maximum stack allocation; see diagnostics below. Note that mj_stackAllocNum is only used for allocating mjtNum arrays, the most common type of array. mj_stackAllocInt is provided for integer array allocation, and mj_stackAllocByte is provided for allocation of arbitrary number of bytes and alignment.

错误、警告与日志#

Errors, warnings, logging

MuJoCo 拥有一个统一的日志系统，用于处理错误、警告和信息类消息。所有日志输出都经由类型为 mjfLogHandler 的单个回调函数进行路由，该回调接收一个结构化的 mjLogMessage，其中包含严重级别、消息文本以及可选的源码位置。错误是致命的，默认情况下会终止程序。警告表示存在问题但并非致命的情况。信息类消息提供可选的诊断输出。

MuJoCo has a unified logging system for errors, warnings and informational messages. All log output is routed through a single callback of type mjfLogHandler, which receives a structured mjLogMessage containing the severity level, message text, and optional source location. Errors are fatal and terminate the program by default. Warnings indicate problematic but non-fatal conditions. Informational messages provide optional diagnostic output.

安装处理器#

Installing a handler

若用户希望拦截并处理 MuJoCo 的日志输出，应使用 mju_setLogHandler 安装日志处理器。该处理器通过单个结构化回调接收所有错误、警告和信息类消息：

Users who want to intercept and process MuJoCo’s log output should install a log handler using mju_setLogHandler. The handler receives all errors, warnings and info messages as a single structured callback:
void my_handler(const mjLogMessage* msg) {
  // do something with msg, for example:
  printf("%s\n", msg->subject);
}

// install handler, save previous
mjfLogHandler prev = mju_setLogHandler(my_handler);

// ... do work ...

// restore previous handler
mju_setLogHandler(prev);

mju_setLogHandler 返回先前安装的处理器（该返回值绝不会是 NULL；传入 NULL 会恢复默认处理器）。先前的处理器可以通过两种方式使用：

mju_setLogHandler returns the previously installed handler (which is never NULL; passing NULL restores the default handler). The previous handler can be used in two ways:

  • 保存/恢复： 库或子系统可以临时安装自己的处理器，之后再恢复先前的处理器。

    Save/restore: A library or subsystem can temporarily install its own handler and later restore the previous one.

  • 链式调用： 自定义处理器可以仅作为观察者，在其回调末尾调用先前的处理器，以保留现有行为。反之，旨在拦截并从错误中恢复的处理器（例如通过 longjmp）则不应链式调用先前的处理器。

    Chaining: A custom handler can act as a pure observer by calling the previous handler at the end of its callback to preserve existing behavior. Conversely, handlers intended to intercept and recover from errors (e.g., via longjmp) should not chain to the previous handler.

当处理器被调用且 level == mjLOG_ERROR 时，该错误始终是致命的：默认处理器 会通过 exit(EXIT_FAILURE) 终止进程（除非安装了旧版错误处理器）。希望从错误中恢复的处理器（例如抛出 C++ 异常，或转换为 Python 异常）绝不能返回，而应在返回之前通过 longjmp 跳转到先前建立的恢复点，或以其他方式转移控制权。编译器和 Python 绑定正是以这种方式处理错误的。MuJoCo 的编写基于这样的假设：错误处理器不会返回；如果它们返回了，软件的行为是未定义的。

When the handler is called with level == mjLOG_ERROR, the error is always fatal: the default handler terminates the process with exit(EXIT_FAILURE) (unless a legacy error handler is installed). Handlers that wish to recover from errors (e.g., to throw a C++ exception or convert to a Python exception) must not return — they should longjmp to a previously established recovery point or otherwise transfer control before returning. This is how the compiler and Python bindings handle errors. MuJoCo is written with the assumption that error handlers will not return; if they do, the behavior of the software is undefined.

默认处理器#

Default handler

如果没有安装自定义处理器（或者向 mju_setLogHandler 传入了 NULL），MuJoCo 会使用默认处理器，其行为如下：

If no custom handler is installed (or if NULL is passed to mju_setLogHandler), MuJoCo uses a default handler that provides the following behavior:

  1. 如果安装了旧版处理器（mju_user_error 或 mju_user_warning），则以格式化后的消息文本调用它。这为现有代码提供了向后兼容性。

    If a legacy handler (mju_user_error or mju_user_warning) is installed, it is called with the formatted message text. This provides backward compatibility with existing code.

  2. 否则，消息会被写入日志文件（默认：MUJOCO_LOG.TXT），并打印到控制台（错误和警告输出到 stderr，信息输出到 stdout）。

    Otherwise, the message is written to the log file (default: MUJOCO_LOG.TXT) and printed to the console (stderr for errors and warnings, stdout for info).

  3. 对于错误，程序会通过 exit(EXIT_FAILURE) 终止（除非安装了旧版错误处理器）。

    For errors, the program is terminated with exit(EXIT_FAILURE) (unless a legacy error handler is installed).

默认处理器的行为可以使用 mju_setLogConfig 和 mju_getLogConfig 进行配置，它们控制输出是否发送到控制台、日志文件路径（将其设为空字符串即可禁用文件日志），以及启用哪些信息主题。

The default handler’s behavior can be configured using mju_setLogConfig and mju_getLogConfig, which control whether output goes to the console, the log file path (or disabling file logging by setting it to an empty string), and which info topics are enabled.

错误恢复#

Error recovery

交互式仿真器加载模型文件失败，是一种即使出错也希望继续运行的情形。这可能是因为用户提供了错误的文件名，或者模型编译失败。这由一种避免调用 mju_error 的特殊机制来处理。模型加载函数 mj_loadXML 和 mj_loadModel 在操作失败时返回 NULL，无需退出程序。对于 mj_loadXML，有一个输出参数包含导致失败的解析器或编译器错误，而 mj_loadModel 则会生成相应的警告（见下文）。

One situation where it is desirable to continue even after an error is an interactive simulator that fails to load a model file. This could be because the user provided the wrong file name, or because model compilation failed. This is handled by a special mechanism which avoids calling mju_error. The model loading functions mj_loadXML and mj_loadModel return NULL if the operation fails, and there is no need to exit the program. In the case of mj_loadXML there is an output argument containing the parser or compiler error that caused the failure, while mj_loadModel generates corresponding warnings (see below).

在内部，mj_loadXML 实际上使用了 mju_error 机制：它临时安装一个线程局部的处理器（使用内部的 _mjPRIVATE_setTlsLogHandler），该处理器会触发一个 C++ 异常，随后该异常被拦截。这种线程局部的覆盖优先于全局处理器，并且仅影响调用线程。

Internally mj_loadXML actually uses the mju_error mechanism, by temporarily installing a thread-local handler (using the internal _mjPRIVATE_setTlsLogHandler) that triggers a C++ exception, which is then intercepted. This thread-local override takes priority over the global handler and affects only the calling thread.

信息类消息#

Informational messages

MuJoCo 提供两种 级别 的可选诊断日志：信息类消息（mjLOG_INFO）和调试跟踪（mjLOG_DEBUG）。两者都使用来自 mjtLogTopic 枚举的主题标识符，但在过滤的应用方式上存在细微的架构差异：

MuJoCo provides two levels of opt-in diagnostic logging: informational messages (mjLOG_INFO) and debug traces (mjLOG_DEBUG). Both use topic identifiers from the mjtLogTopic enum, but have a subtle architectural distinction in how filtering is applied:

  • INFO 消息： 由引擎无条件发出。过滤发生在默认处理器内部的 消费者端。通过 mju_setLogHandler 安装的自定义处理器会接收所有 INFO 消息，并可以实现自己的过滤逻辑。

    INFO messages: Emitted unconditionally by the engine. Filtering happens on the consumer side inside the default handler. Custom handlers installed via mju_setLogHandler receive all INFO messages and can implement their own filtering logic.

  • DEBUG 消息： 专为紧凑、高频的仿真循环而设计，在这类循环中构造字符串会成为性能瓶颈。因此，过滤发生在 生产者端。如果某个主题被禁用，消息就根本不会被构造或分发。因此，只有当该主题在当前生效的 mjLogConfig 中被显式启用时，自定义处理器才会收到 DEBUG 消息。

    DEBUG messages: Designed for tight, high-frequency simulation loops where constructing strings would be a performance bottleneck. Therefore, filtering happens on the producer side. If a topic is disabled, the message is never constructed or dispatched. Consequently, custom handlers will only receive DEBUG messages if the topic is explicitly enabled in the active mjLogConfig.

在默认处理器中，INFO 消息之后会附加一个空行以提高可读性，而高频的 DEBUG 跟踪则以紧凑方式打印，后面没有空行。

In the default handler, INFO messages are followed by a blank line for readability, whereas high-frequency DEBUG traces are printed compactly without trailing blank lines.

要在默认处理器的配置中启用主题：

To enable topics in the default handler configuration:
// enable sleep/wake messages
mjLogConfig config = mju_getLogConfig();
config.topics |= (1 << (mjTOPIC_SLEEP - 1));
mju_setLogConfig(config);

主题 0（mjTOPIC_NONE）无论主题配置如何，始终会通过。

Topic 0 (mjTOPIC_NONE) always passes through, regardless of the topic configuration.

请注意，主题的编号从 1 开始，因此主题 t 的位掩码为 (1 << (t - 1))。mjLogConfig 的 topics 字段也是按此方式编码的。

Note that topics are 1-indexed, so the bitmask for topic t is (1 << (t - 1)). This is also how the topics field of mjLogConfig is encoded.

主题还可以通过环境变量 MUJOCO_LOG_TOPICS 启用，该变量在启动时只读取一次。其值是以逗号分隔的主题名称列表（不区分大小写），主题名称由 mjtLogTopic 枚举去掉 mjTOPIC_ 前缀并转为小写得到（例如 mjTOPIC_SLEEP 变为 sleep）。例如：

Topics can also be enabled via the environment variable MUJOCO_LOG_TOPICS, which is read once at startup. The value is a comma-separated list of topic names (case-insensitive), derived from the mjtLogTopic enum by removing the mjTOPIC_ prefix and lowercasing (e.g., mjTOPIC_SLEEP becomes sleep). For example:

这等价于通过 mju_setLogConfig 以编程方式启用相应的主题位，对于不修改代码就启用诊断很有用。

This is equivalent to programmatically enabling the corresponding topic bits via mju_setLogConfig, and is useful for enabling diagnostics without modifying code.

Frameworks and wrappers

框架作者（例如构建 Python 绑定、MATLAB 封装或游戏引擎集成的人）应安装自定义日志处理器，将 MuJoCo 的输出路由到其所在环境的日志系统：

Framework authors (e.g., those building Python bindings, MATLAB wrappers, or game engine integrations) should install a custom log handler to route MuJoCo’s output to their environment’s logging system:

  } else {
    framework_log_info(msg->subject);
  }
}

mju_setLogHandler(framework_handler);

The mjLogMessage struct also provides source location information (func, file, line) when available, which can be useful for debugging.

旧版处理器#

Legacy handlers

全局函数指针 mju_user_error 和 mju_user_warning 为了向后兼容仍受支持，但已被弃用，推荐使用 mju_setLogHandler。当自定义日志处理器和旧版处理器同时安装时，自定义日志处理器优先。只有在未安装自定义处理器时，默认 处理器才会查询旧版处理器。

The global function pointers mju_user_error and mju_user_warning are still supported for backward compatibility, but are deprecated in favor of mju_setLogHandler. When both a custom log handler and legacy handlers are installed, the custom log handler takes precedence. The legacy handlers are only consulted by the default handler when no custom handler has been installed.

内存处理器#

Memory handlers

MuJoCo 在堆上分配和释放内存时，始终使用函数 mju_malloc 和 mju_free。这两个函数在安装了用户回调 mju_user_malloc 和 mju_user_free 时会调用它们，否则调用标准 C 函数 malloc 和 free。采用这种间接方式的原因是，用户可能希望 MuJoCo 使用由其控制的堆。例如在 MATLAB 中，用于内存分配的用户回调会使用 mxmalloc 和 mexMakeArrayPersistent。

When MuJoCo allocates and frees memory on the heap, it always uses the functions mju_malloc and mju_free. These functions call the user callbacks mju_user_malloc and mju_user_free when installed, otherwise they call the standard C functions malloc and free. The reason for this indirection is because users may want MuJoCo to use a heap under their control. In MATLAB for example, a user callback for memory allocation would use mxmalloc and mexMakeArrayPersistent.

诊断#

Diagnostics

MuJoCo 内置了若干诊断机制，可用于对模型进行精细调整。它们的输出被归入 mjData 开头的诊断部分。

MuJoCo has several built-in diagnostics mechanisms that can be used to fine-tune the model. Their outputs are grouped in the diagnostics section at the beginning of mjData.

当仿真器遇到的情况并非终止性错误，但仍然可疑并且很可能导致数值结果不准确时，它会触发一个警告。警告有多种可能的类型，由枚举类型 mjtWarning 索引。数组 mjData.warning 为每种警告类型包含一个 mjWarningStat 数据结构，指示自上次重置以来每种警告类型被触发了多少次，以及关于该警告的任何信息（通常是出问题的模型元素的索引）。计数器在重置时被清零。当给定类型的警告首次触发时，警告文本还会由 mju_warning 打印出来，如上文 错误与内存 所述。所有这些都由函数 mj_warning 完成，仿真器在遇到警告时会在内部调用该函数。用户也可以直接调用此函数来模拟一个警告。

When the simulator encounters a situation that is not a terminal error but is nevertheless suspicious and likely to result in inaccurate numerical results, it triggers a warning. There are several possible warning types, indexed by the enum type mjtWarning. The array mjData.warning contains one mjWarningStat data structure per warning type, indicating how many times each warning type has been triggered since the last reset and any information about the warning (usually the index of the problematic model element). The counters are cleared upon reset. When a warning of a given type is first triggered, the warning text is also printed by mju_warning as documented in error and memory above. All this is done by the function mj_warning which the simulator calls internally when it encounters a warning. The user can also call this function directly to emulate a warning.

当需要针对高速仿真优化模型时，了解流水线中 CPU 时间花在哪里非常重要。这反过来可以提示应当简化模型的哪些部分，或者如何设计用户应用程序。MuJoCo 提供了丰富的性能分析机制。它涉及多个计时器，由枚举类型 mjtTimer 索引。每个计时器对应一个顶层 API 函数，或此类函数的某个组成部分。与警告类似，计时器信息会不断累积，仅在重置时被清除。数组 mjData.timer 为每个计时器包含一个 mjTimerStat 数据结构。给定计时器（以下例子中对应 mj_step）每次调用的平均耗时可按如下方式计算：

When a model needs to be optimized for high-speed simulation, it is important to know where in the pipeline the CPU time is spent. This can in turn suggest which parts of the model to simplify or how to design the user application. MuJoCo provides an extensive profiling mechanism. It involves multiple timers indexed by the enum type mjtTimer. Each timer corresponds to a top-level API function, or to a component of such a function. Similar to warnings, timer information accumulates and is only cleared on reset. The array mjData.timer contains one mjTimerStat data structure per timer. The average duration per call for a given timer (corresponding to mj_step in the example below) can be computed as:
mjtNum avtm = d->timer[mjTIMER_STEP].duration / mjMAX(1, d->timer[mjTIMER_STEP].number);

这一机制内置于 MuJoCo 中，但只有在用户安装了计时器回调 mjcb_time 时才起作用。否则所有计时器的耗时都为 0。这样设计的原因是，在 C 语言中，不引入额外依赖就无法以与平台无关的方式实现高分辨率计时器。此外，大多数时候用户并不需要计时，在这种情况下就没有理由调用计时函数。

This mechanism is built into MuJoCo, but it only works when the timer callback mjcb_time is installed by the user. Otherwise all timer durations are 0. The reason for this design is because there is no platform-independent way to implement high-resolution timers in C without bringing in additional dependencies. Also, most of the time the user does not need timing, and in that case there is no reason to call timing functions.

仿真流水线中需要密切监控的一部分是迭代式约束求解器。这里最简单的诊断量是 mjData.solver_niter，它显示求解器在最近一次调用 mj_step 或 mj_forward 时执行了多少次迭代。请注意，求解器带有用于提前终止的容差参数，因此这个数字通常小于允许的最大迭代次数；当热启动（warm start）得到的解已被判定为收敛时，它可以为 0，此时不执行任何迭代，也不会写入任何统计信息。数组 mjData.solver 为约束求解器的每次迭代包含一个 mjSolverStat 数据结构，其中含有关于约束状态和线搜索的信息。

One part of the simulation pipeline that needs to be monitored closely is the iterative constraint solver. The simplest diagnostic here is mjData.solver_niter which shows how many iterations the solver took on the last call to mj_step or mj_forward. Note that the solver has tolerance parameters for early termination, so this number is usually smaller than the maximum number of iterations allowed; it can be 0 when a warmstarted solution is already certified as converged, in which case no iterations are performed and no statistics are written. The array mjData.solver contains one mjSolverStat data structure per iteration of the constraint solver, with information about the constraint state and line search.

当 mjModel.opt.enableflags 中启用了选项 fwdinv 时，字段 mjData.fwdinv 也会被填充。它包含正动力学与逆动力学之间的差异，以广义力和约束力表示。请记住，逆动力学使用解析公式，始终是精确的，因此任何差异都源于正动力学中迭代求解器收敛不佳。mjData.solver 中接近终止时的数值与 mjData.fwdinv 中的数值具有相近的数量级，但它们仍是两种不同的诊断量。

When the option fwdinv is enabled in mjModel.opt.enableflags, the field mjData.fwdinv is also populated. It contains the difference between the forward and inverse dynamics, in terms of generalized forces and constraint forces. Recall that that the inverse dynamics use analytical formulas and are always exact, thus any discrepancy is due to poor convergence of the iterative solver in the forward dynamics. The numbers in mjData.solver near termination have similar order-of-magnitude as the numbers in mjData.fwdinv, but nevertheless these are two different diagnostics.

由于 MuJoCo 的运行时处理的是已编译的模型，内存是在模型编译或加载时预先分配的。请回忆 MJCF 中 size 元素的 memory 属性。它决定了为动态数组预分配的空间。用户应该如何知道合适的取值是多少？如果有可靠的办法，我们早就在编译器中实现了，但目前没有。理论上的最坏情况，即所有 geom 与所有其他 geom 都发生接触，需要巨大的分配量，而这在实践中几乎从不需要。我们的做法是在 MJCF 中提供对大多数模型都足够的默认设置，并允许用户通过上述属性手动调整。如果仿真器在运行时耗尽动态内存，就会触发错误。触发此类错误时，用户应增大 memory。字段 mjData.maxuse_arena 正是为了帮助进行这种调整而设计的。它记录自上次重置以来 arena 的最大使用量。因此一种策略是先做一个非常大的分配，然后在典型仿真过程中监控 mjData.maxuse_arena 的统计数据，并据此缩减分配量。

Since MuJoCo’s runtime works with compiled models, memory is preallocated when a model is compiled or loaded. Recall the memory attribute of the size element in MJCF. It determines the preallocated space for dynamic arrays. How is the user supposed to know what the appropriate value is? If there were a reliable recipe we would have implemented it in the compiler, but there isn’t one. The theoretical worst-case, namely all geoms contacting all other geoms, calls for huge allocation which is almost never needed in practice. Our approach is to provide default settings in MJCF which are sufficient for most models, and allow the user to adjust them manually with the above attribute. If the simulator runs out of dynamic memory at runtime it will trigger an error. When such errors are triggered, the user should increase memory. The field mjData.maxuse_arena is designed to help with this adjustment. It keeps track of the maximum arena use since the last reset. So one strategy is to make very large allocation, then monitor mjData.maxuse_arena statistics during typical simulations, and use it to reduce the allocation.

当 mjModel.opt.enableflags 中的相应标志被设置时，动能和势能会被计算并存储在 mjData.energy 中。这可以用作另一种诊断手段。一般而言，仿真不稳定与能量增加有关。在某些特殊情况下（当所有单边约束、执行器和耗散力都被禁用时），底层物理系统是能量守恒的。此时总能量随时间的任何波动都表明数值积分存在不精确之处。对于这类系统，龙格-库塔（Runge-Kutta）积分器的性能远好于默认的半隐式欧拉积分器。

The kinetic and potential energy are computed and stored in mjData.energy when the corresponding flag in mjModel.opt.enableflags is set. This can be used as another diagnostic. In general, simulation instability is associated with increasing energy. In some special cases (when all unilateral constraints, actuators and dissipative forces are disabled) the underlying physical system is energy-conserving. In that case any temporal fluctuations in the total energy indicate inaccuracies in numerical integration. For such systems the Runge-Kutta integrator has much better performance than the default semi-implicit Euler integrator.

雅可比矩阵#

Jacobians

任何向量函数对其向量自变量的导数称为雅可比矩阵。在多关节运动学与动力学中使用这个术语时，它指的是某个空间量作为系统构型函数的导数。此时，雅可比矩阵也是一个线性映射，作用于构型流形的（余）切空间中的向量，例如速度、动量、加速度、力。这里需要注意的一点是：存储在 mjData.qpos 中的系统构型维数为 mjModel.nq，而切空间的维数为 mjModel.nv，当存在四元数关节时，后者更小。因此，雅可比矩阵的大小为 N 行 mjModel.nv 列，其中 N 是被微分的空间量的维数。

The derivative of any vector function with respect to its vector argument is called Jacobian. When this term is used in multi-joint kinematics and dynamics, it refers to the derivative of some spatial quantity as a function of the system configuration. In that case the Jacobian is also a linear map that operates on vectors in the (co)tangent space to the configuration manifold – such as velocities, momenta, accelerations, forces. One caveat here is that the system configuration encoded in mjData.qpos has dimensionality mjModel.nq, while the tangent space has dimensionality mjModel.nv, and the latter is smaller when quaternion joints are present. So the size of the Jacobian matrix is N-by-mjModel.nv where N is the dimensionality of the spatial quantity being differentiated.

MuJoCo 可以对许多空间量进行解析微分。这些量包括肌腱长度、执行器传动长度、末端执行器位姿、接触以及其他约束违反量。对于肌腱和执行器传动，对应的量分别是 mjData.ten_moment 和 mjData.actuator_moment；我们称它们为力臂，但在数学上它们就是雅可比矩阵。所有标量约束违反量的雅可比矩阵存储在 mjData.efc_J 中。请注意，我们谈论的是约束违反量，而不是约束本身。这是因为约束违反量具有长度的单位，即它们是我们可以微分的空间量。约束则是更抽象的实体，对其求导意味着什么并不清楚。

MuJoCo can differentiate analytically many spatial quantities. These include tendon lengths, actuator transmission lengths, end-effector poses, contact and other constraint violations. In the case of tendons and actuator transmissions the corresponding quantities are mjData.ten_moment and mjData.actuator_moment; we call them moment arms but mathematically they are Jacobians. The Jacobian matrix of all scalar constraint violations is stored in mjData.efc_J. Note that we are talking about constraint violations rather than the constraints themselves. This is because constraint violations have units of length, i.e., they are spatial quantities that we can differentiate. Constraints are more abstract entities and it is not clear what it means to differentiate them.

除了这些自动计算的雅可比矩阵之外，我们还提供了支持函数，允许用户按需计算额外的雅可比矩阵。完成这项工作的主要函数是 mj_jac。给定一个三维点以及该点被视为附着于其上的 MuJoCo 刚体，mj_jac 随后会计算平移雅可比和旋转雅可比，它们告诉我们：如果对运动学构型做一个微小改变，锚定在给定点上的空间坐标系将如何平移和旋转。更准确地说，雅可比矩阵将关节速度映射为末端执行器速度，而雅可比矩阵的转置则将末端执行器的力映射为关节力。此外还有若干其他的 mj_jacXXX 函数；它们是便捷函数，以不同的关注点（例如刚体质心、geom 中心等）调用主函数 mj_jac。

Beyond these automatically-computed Jacobians, we provide support functions allowing the user to compute additional Jacobians on demand. The main function for doing this is mj_jac. It is given a 3D point and a MuJoCo body to which this point is considered to be attached. mj_jac then computes both the translational and rotational Jacobians, which tell us how a spatial frame anchored at the given point will translate and rotate if we make a small change to the kinematic configuration. More precisely, the Jacobian maps joint velocities to end-effector velocities, while the transpose of the Jacobian maps end-effector forces to joint forces. There are also several other mj_jacXXX functions; these are convenience functions that call the main mj_jac function with different points of interest – such as a body center of mass, geom center etc.

能够精确而高效地计算末端执行器雅可比矩阵，是在关节坐标下工作的一大关键优势。此类雅可比矩阵是许多控制方案的基础，这些方案将末端执行器误差映射为适合抑制这些误差的执行器指令。通过 mj_jac 函数在 MuJoCo 中计算末端执行器雅可比矩阵，在 CPU 开销方面基本上是免费的；因此请放心使用该函数。

The ability to compute end-effector Jacobians exactly and efficiently is a key advantage of working in joint coordinates. Such Jacobians are the foundation of many control schemes that map end-effector errors to actuator commands suitable for suppressing those errors. The computation of end-effector Jacobians in MuJoCo via the mj_jac function is essentially free in terms of CPU cost; so do not hesitate to use this function.

接触#

Contacts

接触（contact）的碰撞检测（collision detection）与接触力求解已在 计算 一章中详细说明。这里我们从编程的角度进一步阐明接触的处理过程。

Collision detection and solving for contact forces were explained in detail in the Computation chapter. Here we further clarify contact processing from a programming perspective.

碰撞检测阶段会找出 geom 之间的接触，并将它们记录在由 mjContact 数据结构组成的数组 mjData.contact 中。它们经过排序，使得同一对刚体（body）之间的多个接触是连续排列的（请注意，一个刚体可以附有多个 geom），而刚体对本身的排序方式是：第一个刚体作为主索引，第二个刚体作为次索引。并非所有检测到的接触都会被纳入接触力的计算。当某个接触被纳入时，其 mjContact.exclude 字段为 0，并且其 mjContact.efc_address 是它在活动标量约束列表中的地址。被排除的原因可能是 geom 的 gap 属性，也可能是某些使用虚拟接触进行中间计算的内部处理。

The collision detection stage finds contacts between geoms, and records them in the array mjData.contact of mjContact data structures. They are sorted such that multiple contacts between the same pair of bodies are contiguous (note that one body can have multiple geoms attached to it), and the body pairs themselves are sorted such that the first body acts as the major index and the second body as the minor index. Not all detected contacts are included in the contact force computation. When a contact is included, its mjContact.exclude field is 0, and its mjContact.efc_address is the address in the list of active scalar constraints. Reasons for exclusion can be the gap attribute of geom, as well as certain kinds of internal processing that use virtual contacts for intermediate computations.

列表 mjData.contact 由正动力学和逆动力学的位置阶段生成。这是自动完成的。不过，用户可以覆盖内部的碰撞检测函数，例如用于实现非凸网格碰撞，或者用针对特定 geom 的基元碰撞函数来替换我们使用的某些凸碰撞函数，使其超出 MuJoCo 所提供的范围。全局二维数组 mjCOLLISIONFUNC 中为每一对 geom 类型（位于左上三角部分）存放了碰撞函数指针。要替换它们，只需将这些指针设置为你自己的函数即可。碰撞函数的类型是 mjfCollision。当用户的碰撞函数检测到接触时，应该为每个接触构造一个 mjContact 结构，然后调用函数 mj_addContact 将该接触添加到 mjData.contact 中。mj_addContact 的参考文档说明了自定义碰撞函数必须填写 mjContact 的哪些字段。请注意，这里谈到的函数对应的是近场阶段（near-phase）的碰撞，并且仅在内部粗测阶段（broad-phase）碰撞机制构造出候选 geom 对列表之后才会被调用。

The list mjData.contact is generated by the position stage of both forward and inverse dynamics. This is done automatically. However the user can override the internal collision detection functions, for example to implement non-convex mesh collisions, or to replace some of the convex collision functions we use with geom-specific primitives beyond the ones provided by MuJoCo. The global 2D array mjCOLLISIONFUNC contains the collision function pointer for each pair of geom types (in the upper-left triangle). To replace them, simply set these pointers to your functions. The collision function type is mjfCollision. When user collision functions detect contacts, they should construct an mjContact structure for each contact and then call the function mj_addContact to add that contact to mjData.contact. The reference documentation of mj_addContact explains which fields of mjContact must be filled in by custom collision functions. Note that the functions we are talking about here correspond to near-phase collisions, and are called only after the list of candidate geom pairs has been constructed by the internal broad-phase collision mechanism.

and similarly for all other efc_XXX vectors. Keep in mind that the contact friction cone can be pyramidal or elliptic, depending on which solver is selected in mjModel.opt. The function mj_isPyramidal can be used to determine which friction cone type is used. For pyramidal cones, the interpretation of the contact force (whose address we computed above) is non-trivial, because the components are forces along redundant non-orthogonal axes corresponding to the edges of the pyramid. The function mj_contactForce can be used to convert the force generated by a given contact into a more intuitive format: a 3D force followed by a 3D torque. The torque component will be zero when condim is 1 or 3, and non-zero otherwise. This force and torque are expressed in the contact frame given by mjContact.frame. Unlike all other matrices in mjData, this matrix is stored in transposed form. Normally a 3-by-3 matrix corresponding to a coordinate frame would have the frame axes along the columns. Here the axes are along the rows of the matrix. Thus, given that MuJoCo uses row-major format, the contact normal axis (which is the X axis of the contact frame by our convention) is in position mjContact.frame[0-2], the Y axis is in [3-5] and the Z axis is in [6-8]. The reason for this arrangement is because we can have frictionless contacts where only the normal axis is used, so it makes sense to have its coordinates in the first 3 positions of mjContact.frame.

休眠岛#

Sleeping islands

休眠岛（sleeping island）已在 计算章节 中作了概括性的描述。这里我们着重介绍实现细节。

Sleeping islands are described in broad strokes in the Computation chapter. Here we focus on implementation details.

树 的高层休眠状态由 mjData.tree_asleep 描述（但请参见下文的注意事项）。负值表示该树处于唤醒状态，非负值表示处于休眠状态。完全唤醒的树取值为 -⁠(1⁠+⁠mjMINAWAKE)，并且在其速度低于休眠 容差 的每个时间步，该整数都会递增，直至 -1，表示“准备休眠”。如果一个岛中的所有树都已准备好休眠，则它们会在状态推进期间进入休眠，并且它们在 tree_asleep 中的相关取值会被设置为一个（非负的）索引循环：即“休眠岛”。如果岛中有任何一棵树被唤醒，则全部被唤醒。

The high level sleep state of trees is described by mjData.tree_asleep (though see caveat below). A negative value means a tree is awake, non-negative means asleep. Maximally awake trees are given the value -⁠(1⁠+⁠mjMINAWAKE), and for every timestep where their velocity falls below the sleep tolerance, this integer is incremented, up to -1, which means “ready to sleep”. If all trees in an island are ready to sleep, they are put to sleep during state advancement and their associated values in tree_asleep are set to a (non-negative) index cycle: the “sleeping island”. If any tree in the island is woken, all are woken.

休眠策略#

Sleep policy

运动学树能否休眠由模型编译时确定的策略决定。编译器会自动将 策略 确定为“allowed”（允许）或“never”（从不），不过这些策略可以使用 body/sleep 属性覆盖（参见其中的文档）。此外还有一种特殊的“init”休眠策略，参见下一节。

The ability of a kinematic tree to sleep is governed by a policy determined at model compile time. The compiler automatically determines the policy to be either “allowed” or “never”, though these can be overridden using the body/sleep attribute (see documentation therein). There is also a special “init” sleep policy, see next section.

By setting the body/sleep attribute of a tree root to “init”, it is marked as “initialized asleep” and put to sleep during mjData initialization. This is useful for large models where waiting for many trees to fall asleep can be expensive.

由于共享接触或以其他方式处于同一个岛中的树必须一起休眠，因此如果一个岛中的某些树被初始化为休眠，则它们必须全部被如此标记。此模型 包含一个不满足该条件的 XML 示例。当树无法休眠时，无论是在编译期间还是之后的 mj_resetData 中（例如，因为某个控制回调对它们施加了力），都会发出警告，并且这些树会以唤醒状态开始。最后请注意，初始化为休眠的功能仅适用于默认配置（不适用于关键帧，参见下文的讨论）。

This model contains an example XML which does not meet this condition. Finally, note that the initialized-asleep feature is only available for the default configuration (and not keyframes, see discussion below).

唤醒#

Waking

唤醒发生在时间步的开始处，要么是在 mj_kinematics 期间，要么是在其后不久仿真流水线的 位置阶段 期间。休眠岛会根据以下准则被唤醒：

Waking happens at the beginning of the timestep, either during mj_kinematics or soon thereafter during the position stage of the simulation pipeline. A sleeping island is woken up according to the following criteria:

  • 与其相关联的构型 qpos 被用户更改，例如在仿真暂停时交互式地重新摆放构型。

    Its associated configuration qpos is changed by the user, for example when repositioning the configuration interactively when the simulation is paused.

  • 与其相关联的速度 qvel 或施加的力 qfrc_applied 或 xfrc_applied 被用户设置为非零值，例如在仿真过程中交互式地扰动模型。请注意，该检查是通过与 0 进行逐字节比较来执行的，因此将相关联的某个元素设置为浮点值 -0.0 会唤醒该岛，但没有其他副作用。

    Its associated velocity qvel or applied forces qfrc_applied or xfrc_applied are set by the user to a non-zero value, for example when perturbing the model interactively during simulation. Note that the check is performed by bytewise comparison to 0, so setting an associated element to the floating point value -0.0 will wake the island but have no other side-effects.

  • 它与一棵处于唤醒状态的树发生接触。由接触引起的唤醒会导致碰撞检测运行 两次，但仅限于其发生的那个时间步。这是为了检测岛内部以及岛与世界之间的接触，这些接触在第一次运行时因该岛被认为处于休眠状态而被跳过。

    It comes into contact with an awake tree. Waking due to contact leads to collision detection being run twice, but only on the timestep when it occurs. This is required in order to detect contacts inside the island and between the island and the world, which were skipped in the first run when it was deemed asleep.

  • 它与一个 mocap 刚体 发生接触，或者通过一个活动的等式约束与之相连。mocap 刚体视为唤醒状态，因为用户可以随时移动它们。

    It comes into contact with a mocap body, or is connected to one by an active equality constraint. Mocap bodies count as awake, since the user can move them at any time.

  • 它通过一个活动的等式约束（equality constraint）或有限位的肌腱（tendon）与一棵处于唤醒状态的树相连。

    It is connected to an awake tree by an active equality constraint or limited tendon.

  • 它通过一个等式约束与另一个岛中处于休眠状态的树相连。要发生这种情况，该等式约束必须在两棵树都进入休眠时处于禁用状态。

    It is connected by an equality constraint to a sleeping tree in a different island. For this to occur, the equality must have been disabled when both trees were put to sleep.

上面列出的自动唤醒准则旨在使休眠岛的行为如同处于唤醒状态一样，但情况并非总是如此。例如，如果地面上的自由刚体进入休眠，然后重力方向被反转，它们将保持原地休眠，直到因其他原因被唤醒。最极端的非物理例子是初始化为休眠的岛。它们可以被放置在半空中或深度碰撞之中，但在被唤醒之前不会移动。

The automatic wake criteria listed above are designed so that sleeping islands behave as if they were awake, but this is not always the case. For example, if free bodies on the floor are put to sleep and then gravity is reversed, they will remain sleeping in place until woken for another reason. The most extreme example of non-physicality are islands which are initialized asleep. These can be placed in mid-air or in deep collisions, but will not move until woken.

休眠的执行器
Sleeping actuators

正如 body/sleep 文档所解释的，带有执行器的树默认不允许休眠，但用户可以覆盖这一设置。默认不允许休眠的原因是：一旦某个执行器被标记为休眠，唤醒它所需的计算就不再执行。即便执行了（即无论执行器的休眠状态如何，始终为所有执行器计算驱动力），该计算也发生在加速度/力阶段，而此时唤醒一棵树已经为时过晚，因为唤醒必须发生在位置阶段。因此，如果允许带有执行器的树休眠，则必须如上所述通过触碰其相关联的速度或力来手动唤醒。

As explained in the body/sleep documentation, trees with actuators are by default not allowed to sleep, but this can be overridden by the user. The reason sleeping is not allowed by default is that once an actuator is marked as asleep, the computation required to wake it is no longer performed. Even if it were performed (i.e. if actuation forces were always computed for all actuators, regardless of their sleep state), this computation happens in acceleration/force stage, by which time it is already too late to wake a tree, since waking must happen in the position stage. Therefore, if a tree with actuators is allowed to sleep, waking must be done manually by touching the associated velocities or forces, as described above.

暂定的选择
Provisional choices

某些实现上的选择是暂定的，可能会发生变化。

Some implementation choices are provisional and subject to change.

一个具体的例子是，我们决定将 mjMINAWAKE 的值硬编码，而不是将其作为运行时选项暴露给用户。这样做有两个原因。首先，在我们的实验中，我们发现更改该值等价于更改 sleep_tolerance，而后者是更有用的调节旋钮。其次，有人可能会主张采用以时间为单位、而不是以整数个时间步为单位的入睡时间语义。在有明确证据表明其中一个或两个原因不成立之前，我们选择了一个简单的数值常量。

A concrete example is the decision to hard-code the value of mjMINAWAKE instead of exposing it to the user as a runtime option. This was done for two reasons. First, in our experiments, we’ve found that changing this value is equivalent to changing the sleep_tolerance, which is the more useful knob. Second, one could argue for a time-to-sleep semantic that is in units of time rather than an integer number of timesteps. Until there is clear evidence that one or both of these reasons are invalid, we’ve opted for a simple numeric constant.

被违反的假设
Violated assumptions

休眠打破了 MuJoCo 核心中内置的若干假设（而在禁用休眠时这些假设仍然成立）。

Sleeping breaks several assumptions that are baked into the core of MuJoCo (and continue to hold if sleeping is disabled).

流水线阶段：通常可以保证，在位置阶段结束之前不会读取与速度相关的量，在速度阶段结束之前不会读取与力相关的量。这一假设是 mj_step1/mj_step2 拆分的核心，但在 mj_kinematics 中读取 qvel、qfrc_applied 和 xfrc_applied 时被违反了。

Pipeline stages: It is usually guaranteed that no velocity-related quantities will be read before the end of the position stage and that no force-related quantities will be read before the end of velocity stage. This assumption, which lies at the heart of the mj_step1/mj_step2 split, is violated by the reading of qvel, qfrc_applied and xfrc_applied in mj_kinematics.

紧凑状态：虽然休眠状态名义上由 mjData.tree_asleep 给出，但这只是一种假象。一旦某个岛进入休眠，mjData 中与之相关联的整个位置和速度相关量的子集就成为一种预先计算好的潜在状态，处于“等待该岛被唤醒”的状态。因此，完整保存和恢复含有休眠元素的仿真状态的唯一方法，是 复制 整个 mjData 结构。这也是休眠初始化仅适用于默认配置而不适用于关键帧的原因。请注意，使用 标准工具 保存和加载状态仍然是有效的操作，只是休眠岛会被隐式唤醒。

Compact state: While the sleep state is notionally given by mjData.tree_asleep, this is a mirage. Once an island is asleep, the entire subset of position and velocity-dependent quantities in mjData associated with it becomes a pre-computed latent state that is “waiting for the island to wake up”. For this reason, the only way to fully save and restore the state of a simulation with sleeping elements is to copy the entire mjData structure. This is also the reason why sleep initialization is only available for the default configuration and not for keyframes. Note that saving and loading the state using the standard tools remains a valid operation, merely that sleeping islands will be implicitly woken up.

坐标系与变换#

Coordinate frames and transformations

MuJoCo 中使用了多种坐标系。最上层的区别在于关节坐标与笛卡尔坐标。从关节坐标向量到所有刚体的笛卡尔位置和朝向的映射称为正运动学（forward kinematics），它是物理流水线的第一步。相反的映射称为逆运动学，但它不是唯一确定的，MuJoCo 中也没有实现。请回忆，切空间之间的映射（即从关节速度和力到笛卡尔速度和力）由刚体雅可比矩阵给出。

There are multiple coordinate frames used in MuJoCo. The top-level distinction is between joint coordinates and Cartesian coordinates. The mapping from the vector of joints coordinates to the Cartesian positions and orientations of all bodies is called forward kinematics and is the first step in the physics pipeline. The opposite mapping is called inverse kinematics but it is not uniquely defined and is not implemented in MuJoCo. Recall that mappings between the tangent spaces (i.e., joint velocities and forces to Cartesian velocities and forces) are given by the body Jacobians.

这里我们进一步解释坐标系的微妙之处和细分，并概述可用的变换函数。在关节坐标中，唯一的复杂之处在于，由于四元数关节的存在，位置向量 mjData.qpos 与速度和加速度向量 mjData.qvel 和 mjData.qacc 的维数不同。函数 mj_differentiatePos 对两个关节位置向量做“减法”并返回一个速度向量。反过来，函数 mj_integratePos 接收一个位置向量和一个速度向量，并返回一个按给定速度发生位移之后的新位置向量。

Here we explain further subtleties and subdivisions of the coordinate frames, and summarize the available transformation functions. In joint coordinates, the only complication is that the position vector mjData.qpos has different dimensionality than the velocity and acceleration vectors mjData.qvel and mjData.qacc due to quaternion joints. The function mj_differentiatePos “subtracts” two joint position vectors and returns a velocity vector. Conversely, the function mj_integratePos takes a position vector and a velocity vector, and returns a new position vector which has been displaced by the given velocity.

笛卡尔坐标更为复杂，因为我们使用三种不同的坐标系：局部坐标系、全局坐标系和基于质心（com-based）的坐标系。局部坐标在 mjModel 中用于表示父刚体与子刚体之间的静态偏移，以及刚体与附着其上的任何 geom、site、相机和灯光之间的静态偏移。这些静态偏移是在任何关节变换之外额外施加的。因此 mjModel.body_pos、mjModel.body_quat 以及 mjModel 中所有其他空间量都是在局部坐标中表示的。正运动学的任务是沿运动学树累积关节变换和静态偏移，并计算出全局坐标中的所有位置和朝向。mjData 中以“x”开头的量是在全局坐标中表示的。它们包括 mjData.xpos、mjData.geom_xpos 等。坐标系的朝向通常存储为 3 行 3 列矩阵（xmat），但刚体的朝向还以单位四元数 mjData.xquat 的形式存储。给定该刚体四元数，附着在该刚体上的所有其他对象的四元数都可以通过四元数乘法重构出来。函数 mj_local2Global 将局部刚体坐标转换为全局笛卡尔坐标。

Cartesian coordinates are more complicated because there are three different coordinate frames that we use: local, global, and com-based. Local coordinates are used in mjModel to represent the static offsets between a parent and a child body, as well as the static offsets between a body and any geoms, sites, cameras and lights attached to it. These static offsets are applied in addition to any joint transformations. So mjModel.body_pos, mjModel.body_quat and all other spatial quantities in mjModel are expressed in local coordinates. The job of forward kinematics is to accumulate the joint transformations and static offsets along the kinematic tree and compute all positions and orientations in global coordinates. The quantities in mjData that start with “x” are expressed in global coordinates. These are mjData.xpos, mjData.geom_xpos etc. Frame orientations are usually stored as 3-by-3 matrices (xmat), except for bodies whose orientation is also stored as a unit quaternion mjData.xquat. Given this body quaternion, the quaternions of all other objects attached to the body can be reconstructed by a quaternion multiplication. The function mj_local2Global converts from local body coordinates to global Cartesian coordinates.

位姿（pose）是一个三维位置与一个单位四元数朝向的组合。没有单独的数据结构；这种组合是逻辑上的。它表示空间中的一个位置和朝向，换句话说就是一个空间坐标系。请注意，OpenGL 使用 4 行 4 列矩阵来表示相同的信息，只不过这里我们用四元数来表示朝向。函数 mju_mulPose 将两个位姿相乘，意思是用第二个位姿对第一个位姿进行变换（顺序很重要）。mju_negPose 构造相反的位姿，而 mju_trnVecPose 用一个位姿变换一个三维向量，如果把该位姿看作一个坐标系，就是将向量从局部坐标映射到全局坐标。如果我们只想处理朝向部分，可以使用类似的四元数工具函数 mju_mulQuat、mju_negQuat 和 mju_rotVecQuat 来完成。

A pose is a grouping of a 3D position and a unit quaternion orientation. There is no separate data structure; the grouping is in terms of logic. This represents a position and orientation in space, or in other words a spatial frame. Note that OpenGL uses 4-by-4 matrices to represent the same information, except here we use a quaternion for orientation. The function mju_mulPose multiplies two poses, meaning that it transforms the first pose by the second pose (the order is important). mju_negPose constructs the opposite pose, while mju_trnVecPose transforms a 3D vector by a pose, mapping it from local coordinates to global coordinates if we think of the pose as a coordinate frame. If we want to manipulate only the orientation part, we can do that with the analogous quaternion utility functions mju_mulQuat, mju_negQuat and mju_rotVecQuat.

最后是基于质心的坐标系。它用于表示 6 维空间向量，其中包含一个三维角速度或角加速度或力矩，后接一个三维线速度或线加速度或力。请注意这个逆向的顺序：旋转在前，平移在后。mjData.cdof 和 mjData.cacc 就是此类向量的例子；它们的名称以“c”开头。这些向量在多关节动力学计算中起着关键作用。对此进行解释超出了我们这里的范围；请参阅 Featherstone 关于该主题的精彩 幻灯片。一般来说，用户应避免直接处理这类量。而应使用函数 mj_objectVelocity、mj_objectAcceleration 以及底层的 mju_transformSpatial 来获得给定刚体的线速度和角速度、加速度和力。不过，对于感兴趣的读者，我们概述一下“c”类量最不寻常的方面。假设我们想表示一个原地自旋的刚体。人们可能会期望其空间速度具有非零角速度和零线速度。然而事实并非如此。旋转被解释为绕一条穿过坐标系中心的轴发生，而该中心位于刚体之外（我们使用运动学树的质心）。这样的旋转不仅会使刚体旋转，还会使其平移。因此，空间向量必须具有非零线速度，以补偿绕刚体之外的轴旋转所产生的副作用。如果你调用 mj_objectVelocity，得到的 6 维量将在一个以刚体为中心、与世界对齐的坐标系中表示。这样，线速度分量就会如预期那样为零。该函数还会把平移放在旋转之前，这是我们对局部坐标和全局坐标采用的约定。

Finally, there is the com-based frame. This is used to represent 6D spatial vectors containing a 3D angular velocity or acceleration or torque, followed by a 3D linear velocity or acceleration or force. Note the backwards order: rotation followed by translation. mjData.cdof and mjData.cacc are example of such vectors; the names start with “c”. These vectors play a key role in the multi-joint dynamics computation. Explaining this is beyond our scope here; see Featherstone’s excellent slides on the subject. In general, the user should avoid working with such quantities directly. Instead use the functions mj_objectVelocity, mj_objectAcceleration and the low-level mju_transformSpatial to obtain linear and angular velocities, accelerations and forces for a given body. Still, for the interested reader, we summarize the most unusual aspect of the “c” quantities. Suppose we want to represent a body spinning in place. One might expect a spatial velocity that has non-zero angular velocity and zero linear velocity. However this is not the case. The rotation is interpreted as taking place around an axis through the center of the coordinate frame, which is outside the body (we use the center of mass of the kinematic tree). Such a rotation will not only rotate the body but also translate it. Therefore the spatial vector must have non-zero linear velocity to compensate for the side-effect of rotation around an off-body axis. If you call mj_objectVelocity, the resulting 6D quantity will be represented in a frame that is centered at the body and aligned with the world. Thus the linear component will now be zero as expected. This function will also put translation in front of rotation, which is our convention for local and global coordinates.
